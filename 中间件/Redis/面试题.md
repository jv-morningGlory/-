# Redis 常见面试题

---

## 1. 基础概念

### Q1：Redis 是什么？有什么特点？

Redis（Remote Dictionary Server）是一个基于**内存**的 **key-value** 存储系统，主要特点：

- **高性能**：内存操作，单线程模型（6.0+ 引入多线程 IO），每秒 10w+ QPS
- **数据结构丰富**：String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、Geo、Stream
- **持久化**：支持 RDB 快照和 AOF 日志
- **高可用**：主从复制、哨兵模式、Cluster 集群
- **功能丰富**：发布订阅、Lua 脚本、事务、Pipeline

### Q2：Redis 为什么这么快？

| 原因 | 说明 |
|------|------|
| **纯内存操作** | 数据存在内存中，无磁盘 IO 瓶颈 |
| **单线程模型** | 没有多线程的上下文切换和锁竞争 |
| **IO 多路复用** | 一个线程通过 epoll/kqueue 管理多个连接 |
| **高效数据结构** | 底层数据结构经过专门优化（SDS、跳表、压缩列表等） |

### Q3：Redis 是单线程还是多线程？

- **4.0 之前**：完全单线程
- **4.0**：引入后台线程（异步删除 unlink、flushdb async）
- **6.0**：引入多线程 IO，但**命令执行仍然是单线程**
- **7.0**：继续增强多线程 IO

> Redis 的核心瓶颈不是 CPU，而是网络 IO 和内存带宽。

## 2. 数据类型

### Q4：Redis 有哪些数据类型？各自适用什么场景？

> 详见 [Redis基础 - 4. Redis 五种基本数据类型](Redis基础.md#4-redis-五种基本数据类型)

**① String — 最基础，什么都能干**

| 场景 | 说明 | 关键命令 |
|------|------|---------|
| **缓存** | 查 DB 前先查 Redis，命中直接返回 | `SET` / `GET` |
| **计数器** | 文章阅读量、点赞数 | `INCR` / `INCRBY` |
| **分布式锁** | 利用 SETNX 互斥特性 | `SET key val NX EX` |
| **限流** | 记录单位时间内的请求次数 | `INCR` + `EXPIRE` |

```java
// 缓存：先查缓存，未命中查 DB 并回写
String cache = redisTemplate.opsForValue().get("user:" + userId);
if (cache != null) return JSON.parseObject(cache, User.class);
User user = userMapper.selectById(userId);
redisTemplate.opsForValue().set("user:" + userId, JSON.toJSONString(user), 30, TimeUnit.MINUTES);

// 计数器：每篇文章阅读量 +1
redisTemplate.opsForValue().increment("article:read:" + articleId);

// 分布式锁：SET NX EX
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent("lock:order:" + orderId, uuid, 30, TimeUnit.SECONDS);
```

**② Hash — 存对象**

| 场景 | 说明 |
|------|------|
| **用户信息** | userId 做 key，name/age/email 做 field |
| **购物车** | userId 做 key，商品 ID 做 field，数量做 value |
| **文章计数器** | articleId 做 key，read/like/comment 做 field |

```java
// 购物车：添加商品
redisTemplate.opsForHash().put("cart:" + userId, "sku_1001", 2);
redisTemplate.opsForHash().put("cart:" + userId, "sku_1002", 1);
// 修改数量（HINCRBY）
redisTemplate.opsForHash().increment("cart:" + userId, "sku_1001", 1);
// 查购物车全部商品
Map<Object, Object> cart = redisTemplate.opsForHash().entries("cart:" + userId);
```

> 相比 String 存 JSON，Hash 的好处是**可以单独修改某个字段**，不需要取出整个 JSON 再写回去。

**③ List — 有序队列**

| 场景 | 说明 |
|------|------|
| **消息队列** | 生产者 RPUSH，消费者 BLPOP 阻塞等待 |
| **最新列表** | 朋友圈时间线（LPUSH + LTRIM 保留最近 N 条） |
| **栈** | LPUSH + LPOP = 后进先出 |

```java
// 生产者：往右入队
redisTemplate.opsForList().rightPush("queue:task", JSON.toJSONString(task));

// 消费者：阻塞式左出队（timeout=0 无限等待）
Object task = redisTemplate.opsForList()
    .rightPop("queue:task", 0, TimeUnit.SECONDS);

// 最新动态 Top 100
redisTemplate.opsForList().leftPush("feed:" + userId, postId);
redisTemplate.opsForList().trim("feed:" + userId, 0, 99);  // 只保留前 100
```

**④ Set — 无序去重集合**

| 场景 | 说明 |
|------|------|
| **标签系统** | 给文章打标签，SINTER 做交集推荐 |
| **共同好友** | SINTER 取交集 |
| **抽奖** | SRANDMEMBER 随机取 / SPOP 随机弹出 |
| **点赞去重** | user ID 存 Set，SISMEMBER 判重 |

```java
// 文章标签
redisTemplate.opsForSet().add("article:tags:1001", "Java", "Redis", "Spring");
// 交集：同时有 "Java" 和 "Redis" 标签的文章
Set<String> related = redisTemplate.opsForSet()
    .intersect("tag:Java:articles", "tag:Redis:articles");

// 共同好友
Set<String> common = redisTemplate.opsForSet()
    .intersect("friends:" + userA, "friends:" + userB);

// 抽奖：随机取 3 个不重复中奖者
redisTemplate.opsForSet().distinctRandomMembers("lottery:pool", 3);
```

**⑤ ZSet — 有序 + 去重，按 score 排序**

| 场景 | 说明 |
|------|------|
| **排行榜** | score = 积分，ZREVRANGE 取 Top N |
| **延迟队列** | score = 执行时间戳，ZRANGEBYSCORE 拉取到期任务 |
| **分页查询** | score = 时间戳/ID，按 score 范围分页 |

```java
// 排行榜：更新积分
redisTemplate.opsForZSet().incrementScore("rank:points", userId, 10);
// Top 100
Set<String> top = redisTemplate.opsForZSet()
    .reverseRange("rank:points", 0, 99);
// 查某人排名
Long rank = redisTemplate.opsForZSet().reverseRank("rank:points", userId);

// 延迟队列：score = 执行时间戳
redisTemplate.opsForZSet().add("delay:task", taskId, executeTime);
// 拉取到期任务
Set<String> due = redisTemplate.opsForZSet()
    .rangeByScore("delay:task", 0, System.currentTimeMillis());
```

**⑥ Bitmap — 位图，极省空间**

| 场景 | 说明 |
|------|------|
| **签到** | 每天一个 key，userId 做 offset |
| **在线状态** | 在线=1，离线=0 |
| **布隆过滤器** | 多个 hash 函数写位图 |

```java
// 签到
redisTemplate.opsForValue().setBit("checkin:2024-06-01", userId, true);
// 是否签到
boolean signed = redisTemplate.opsForValue().getBit("checkin:2024-06-01", userId);
// 签到总人数
long count = redisTemplate.opsForValue().bitCount("checkin:2024-06-01");
```

> 1 亿用户的签到数据，Bitmap 只用 12MB（1 亿 bit ≈ 12.5MB），而用 Set 存签到 userId 需要几个 GB。

**⑦ HyperLogLog — 基数统计，有误差但极省内存**

| 场景 | 说明 |
|------|------|
| **UV 统计** | 每个页面一个 key，只统计不重复访客数 |
| **搜索热词去重** | 统计不同搜索词的个数 |

```java
// 记录访客
redisTemplate.opsForHyperLogLog().add("uv:page:home", userId);
// 统计 UV
long uv = redisTemplate.opsForHyperLogLog().size("uv:page:home");
```

> 每个 key 只占 12KB，标准误差 0.81%。百万级 UV 统计不需要建表跑 SQL。

**⑧ Geo — 地理位置**

| 场景 | 说明 |
|------|------|
| **附近的人** | 上报坐标，GEORADIUS 搜索附近 |
| **附近门店** | 存门店位置，按距离排序 |

```java
// 上报位置
redisTemplate.opsForGeo().add("user:location", new Point(lng, lat), userId);
// 附近 5 公里的人
redisTemplate.opsForGeo()
    .radius("user:location", new Circle(new Point(lng, lat), new Distance(5, Metrics.KILOMETERS)),
        RedisGeoCommands.GeoRadiusCommandArgs.newGeoRadiusArgs()
            .includeDistance().sortAscending().limit(50));
```

> Geo 底层就是 ZSet，用 Geohash 将经纬度编码为一维数值作为 score。

## 3. 持久化

### Q7：RDB 和 AOF 有什么区别？为什么这样设计？

Redis 是内存数据库，数据都在内存里，一旦宕机数据就丢了。所以需要**持久化**把数据存到磁盘上。Redis 提供了两种思路——快照和日志，对应 RDB 和 AOF。

**一句话理解两种思路：**

```
RDB：内存的"照片"，隔一段时间拍一张，恢复快但可能丢最后一帧的画面
AOF：操作的"录像"，把每条写命令都录下来，数据安全但录像带会越来越大
```

**① RDB（Redis Database）—— 内存快照**

原理：

```
┌──────────────┐      fork()       ┌──────────────┐
│   主进程      │ ───────────────→ │   子进程      │
│  (处理请求)   │                  │  (写 RDB 文件) │
│              │   COW 共享内存    │              │
│   ┌──────┐   │ ← ─ ─ ─ ─ ─ ─ → │  scan 内存    │
│   │ 内存  │   │    copy-on-write │  写入 dump.rdb│
│   └──────┘   │                  │              │
└──────────────┘                  └──────────────┘
```

- 主进程 `fork()` 出一个子进程
- 父子进程共享同一块内存（COW，写时复制）
- 子进程遍历内存数据，序列化写入 `dump.rdb` 文件
- 主进程继续处理请求，如果需要修改某页内存，OS 会先复制那一页（COW），主进程改复制后的页面，子进程仍读原来的
- 触发方式：`save`（阻塞）/ `bgsave`（后台异步）/ `save 900 1`（自动配置，900秒内至少1次修改）

**② AOF（Append Only File）—— 写操作日志**

原理：

```
客户端 → SET name "zhangsan"
              │
              ↓
        主进程执行命令
              │
              ↓
        追加到 AOF 缓冲区
              │
              ↓  (根据 fsync 策略)
        写入 appendonly.aof 文件
```

- 每一条**写命令**执行成功后，追加到 AOF 文件末尾
- 恢复时，逐条回放 AOF 中的命令重建内存数据
- `appendfsync` 三种策略：

| 策略 | 行为 | 性能 | 安全性 |
|------|------|------|--------|
| **always** | 每条命令都 fsync 刷盘 | 最慢 | 最高，最多丢一条 |
| **everysec** | 每秒刷一次 | 适中 | 最多丢 1 秒数据 |
| **no** | 交给 OS 决定何时刷 | 最快 | 最不安全 |

**③ AOF 重写（Rewrite）—— 解决 AOF 文件膨胀**

AOF 记录每次写操作，文件中会有很多冗余。比如对一个 key 的 10 次 INCR，最终只需要 1 条 SET key 10。重写就是**用当前内存数据反向生成最小命令集**：

```
原始 AOF（膨胀）：                 重写后（精简）：
SET key 0                         SET key 100
INCRBY key 1         →
... (重复 100 次)                  SET list a b c d
LPUSH list a                      SET hash name zhangsan age 28
LPUSH list b          →
LPUSH list c
LPUSH list d
```

重写过程：
1. `fork()` 子进程，子进程读取当前内存数据
2. 子进程将数据以最精简的 SET 命令写入**新的临时文件**
3. 主进程同时将重写期间的新命令写入**旧 AOF + 重写缓冲区**
4. 子进程完成后，主进程将重写缓冲区的内容追加到新文件
5. `rename` 原子替换旧 AOF 文件

**④ RDB vs AOF 对比**

| 维度 | RDB | AOF |
|------|-----|-----|
| **比喻** | 定时拍照 | 持续录像 |
| **原理** | fork 子进程，dump 内存快照 | 记录每条写命令 |
| **恢复速度** | 快（二进制直接加载到内存） | 慢（逐条回放命令） |
| **数据安全性** | 两次快照之间的数据可能丢失 | `everysec` 最多丢 1 秒 |
| **文件大小** | 小（压缩的二进制） | 大（文本命令，可 rewrite 压缩） |
| **对性能影响** | fork 瞬间阻塞 + COW 内存翻倍风险 | 取决于 fsync 策略，everysec 几乎无感 |
| **适用场景** | 备份、灾备、数据恢复 | 对数据完整性要求高 |

**⑤ Redis 的设计思路——为什么要搞两套方案？**

这是 Redis 设计中一个典型的"鱼与熊掌"问题：

```
目标矛盾：
  数据安全  ⟺  高性能

纯 RDB  → 性能好,但可能丢数据
纯 AOF  → 数据安全,但文件大/恢复慢

Redis 的选择：两者都支持，用户按需组合
```

更深层的设计考量：

| 设计考量 | Redis 的做法 |
|----------|-------------|
| **不能拖慢主线程** | 两种持久化都 fork 子进程处理，主线程只负责少量的缓冲写入 |
| **写时复制（COW）** | 利用 OS 的 COW 机制，fork 时不需要复制整个内存，只有被修改的页才复制 |
| **AOF 膨胀问题** | 设计了 bgrewriteaof，后台自动压缩，保证文件不会无限增长 |
| **启动恢复优先级** | AOF 比 RDB 优先（因为 AOF 数据更新），Redis 启动时如果同时存在，优先加载 AOF |

**⑥ 混合持久化（Redis 4.0+）**

```
RDB 文件头（快照时刻的全量数据）
         +
AOF 文件尾（快照时刻之后的增量命令）
         =
混合持久化文件
```

- 本质：rewrite 时，子进程先把当前内存以 RDB 格式写入文件头，再把 rewrite 期间的增量以 AOF 格式追加
- 优点：结合 RDB 的**快速加载** + AOF 的**数据安全**，恢复时先加载 RDB 部分（快），再回放少量 AOF 尾部（也快）

**⑦ 生产实践建议**

```
开启方式：RDB + AOF 同时开（或直接用混合持久化）

RDB：
  save 900 1      # 15 分钟至少 1 次修改
  save 300 10     # 5 分钟至少 10 次修改
  save 60 10000   # 1 分钟至少 1 万次修改

AOF：
  appendonly yes
  appendfsync everysec              # 每秒刷盘，折中方案
  auto-aof-rewrite-percentage 100   # AOF 大小增长 100% 触发 rewrite
  auto-aof-rewrite-min-size 64mb    # AOF 至少 64MB 才触发 rewrite

Redis 7.0+：
  aof-use-rdb-preamble yes          # 开启混合持久化（推荐）
```

> **核心思想**：RDB 解决"快速恢复"，AOF 解决"数据安全"，混合持久化两个都要。这个设计权衡在分布式系统中非常经典——没有银弹，只有取舍。

### Q8：AOF 重写（rewrite）的原理是什么？

> 详见上方 [Q7 第③点](#q7rdb-和-aof-有什么区别为什么这样设计)，已有完整说明。

核心步骤：fork 子进程 → 子进程以当前内存数据生成最小 SET 命令集 → 写入新文件 → 主进程同时缓冲 rewrite 期间的写命令 → 子进程完成后追加缓冲命令 → 原子替换。

实际由 `auto-aof-rewrite-percentage` 和 `auto-aof-rewrite-min-size` 参数自动触发。

## 4. 缓存问题

### Q9：缓存穿透 / 击穿 / 雪崩 是什么？怎么解决？

> 详见 [Redis基础 - 8. 缓存三大问题](Redis基础.md#8-缓存三大问题)

| 问题 | 一句话 | 核心方案 |
|------|--------|---------|
| **穿透** | 查不存在的数据 | 布隆过滤器 / 空值缓存 |
| **击穿** | 一个热点 key 过期 | 互斥锁 / 逻辑过期 |
| **雪崩** | 大量 key 同时过期 / Redis 宕机 | TTL 加随机值 / 多级缓存 / 高可用 |

## 5. 分布式锁

### Q10：Redis 如何实现分布式锁？

```java
// 加锁：SET lock_key unique_value NX EX 30
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, lockValue, 30, TimeUnit.SECONDS);

// 解锁：Lua 脚本保证原子性
String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                "return redis.call('del', KEYS[1]) else return 0 end";
redisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
    Collections.singletonList(lockKey), lockValue);
```

**关键点**：
- `SET NX EX` 一条命令保证加锁+过期原子性
- value 用 UUID，解锁时校验，防止误删
- 解锁用 Lua 脚本，保证 check + delete 原子性

### Q11：Redisson 的看门狗（Watch Dog）机制是什么？

默认锁过期时间 30s，如果客户端还持有锁，**watch dog 每隔 10s 自动续期到 30s**，直到业务执行完主动释放。

> 既不会因业务执行时间长而自动释放，也不会因宕机永久死锁（watch dog 随客户端一起死）。

### Q12：RedLock 是什么？

主从模式下，主节点获取锁后宕机但数据未同步到从节点，新主节点没有锁信息，其他线程能再次获取锁。

RedLock：向 N 个独立 Redis 节点（非主从）依次加锁，超过 **N/2+1** 个节点成功才算获取锁成功。

## 6. 集群与高可用

### Q13：Redis 集群模式有哪些？

> 详见 [Redis基础 - 7. 高可用架构](Redis基础.md#7-高可用架构)

| 模式 | 特点 |
|------|------|
| **主从复制** | 读写分离，故障需手动切换 |
| **Sentinel** | 自动故障转移，至少 3 个哨兵 |
| **Cluster** | 水平扩展，16384 个 hash slot，数据分片 |

### Q14：Redis Cluster 的数据分片原理？

- key 通过 **CRC16** hash 到 0-16383 的 slot
- 每个 master 节点负责一部分 slot
- 客户端计算 `CRC16(key) % 16384`，直连对应 master

```
Master1: slot 0-5460
Master2: slot 5461-10922
Master3: slot 10923-16383
```

### Q15：哨兵模式的选举过程？

1. **主观下线（SDOWN）**：某个哨兵发现 master 未响应
2. **客观下线（ODOWN）**：quorum 个哨兵都认为 master 下线
3. **Leader 选举**：哨兵中选 leader（Raft 变体）
4. **故障转移**：leader 哨兵选从节点升级为新 master
5. **通知**：通知其他从节点和客户端

## 7. 过期策略与内存淘汰

### Q16：Redis 的过期删除策略是什么？

**惰性删除 + 定期删除**：

| 策略 | 做法 |
|------|------|
| **惰性删除** | 访问 key 时才检查是否过期 |
| **定期删除** | 每隔 100ms 随机抽取一批 key 检查 |

> 不用定时删除的原因：每个 key 设定时器 CPU 开销太大。

### Q17：内存淘汰策略有哪些？

> 详见 [Redis基础 - 5.2 缓存淘汰策略](Redis基础.md#52-缓存淘汰策略)

| 策略 | 说明 |
|------|------|
| `noeviction` | 不淘汰，内存满时报错 |
| `allkeys-lru` | 所有 key 中淘汰最近最少使用的 |
| `volatile-lru` | 有过期时间的 key 中淘汰 LRU |
| `allkeys-lfu` | 所有 key 中淘汰最不经常使用的 |
| `volatile-lfu` | 有过期时间的 key 中淘汰 LFU |
| `volatile-ttl` | 有过期时间的 key 中淘汰 TTL 最短的 |

> LRU 看"最近"，LFU 看"频率"。通用场景推荐 `allkeys-lru`。

## 8. 事务与管道

### Q18：Redis 事务的特点？

用 `MULTI` / `EXEC` / `DISCARD` / `WATCH` 实现：

- **不支持回滚**：某条命令失败不影响其他命令
- **单线程保证原子性**：事务中命令不会被其他客户端打断
- **WATCH 实现乐观锁**：监控的 key 被修改则 EXEC 失败

```bash
WATCH balance:user1
MULTI
DECRBY balance:user1 100
INCRBY balance:user2 100
EXEC
```

### Q19：Pipeline 是什么？和事务有什么区别？

**Pipeline**：客户端将多条命令打包一次发送，减少网络 RTT。

| 维度 | Pipeline | Transaction |
|------|----------|-------------|
| **原子性** | 不保证 | 保证 |
| **目的** | 减少网络开销 | 保证命令连续执行 |

### Q20：Redis 怎么做延迟队列？

用 **ZSet**，score = 执行时间戳，定时拉取到期任务：

```java
redisTemplate.opsForZSet().add("delay_queue", taskId, executeTime);
Set<String> tasks = redisTemplate.opsForZSet()
    .rangeByScore("delay_queue", 0, System.currentTimeMillis());
```

> Redis 6.2 引入 **Stream**，支持消费者组和 ACK 机制。

### Q21：大 key 和热 key 怎么处理？

> 详见 [Redis基础 - 8.5 bigkey / 8.6 hotkey](Redis基础.md#85-bigkey)

| 问题 | 方案 |
|------|------|
| **大 key** | 拆分（大 Hash 拆小 Hash）、设置过期时间 |

### Q22：Redis 和数据库的双写一致性怎么保证？

**经典方案：先更新 DB，后删除缓存**

```
写：更新 DB → 删除缓存
读：查缓存 → 有返回 → 无则查 DB → 写入缓存
```

**延时双删**（要求更严格时）：
```
1. 删除缓存 → 2. 更新 DB → 3. 延迟 N ms → 4. 再次删除缓存
```

> 最终一致方案：**Canal + MQ** 监听 MySQL binlog，异步更新/删除缓存。

### Q23：缓存淘汰策略 LRU 和 LFU 的区别？

**LRU（Least Recently Used）**：最近最少使用，看"最近一次访问时间"。一个 key 被访问后就排到队头，淘汰队尾。

**LFU（Least Frequently Used）**：最不经常使用，看"访问频率"。即使最近访问过，如果历史访问频率低也会被淘汰。

> LRU 的问题：一个冷门 key 被偶尔访问一次就排到队头，真正热 key 反而被淘汰。LFU 解决这个问题。
