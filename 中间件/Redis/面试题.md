# Redis 常见面试题

---

## 1. 基础概念

### Q1：Redis 是什么？有什么特点？

Redis（Remote Dictionary Server）是一个基于**内存**的 **key-value** 存储系统，主要特点：

- **高性能**：内存操作，单线程模型（6.0+ 引入多线程 IO），每秒 10w+ QPS
- **数据结构丰富**：String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、Geo、Stream
- **持久化**：支持 RDB 快照和 AOF 日志
- **高可用**：主从复制、哨兵模式、Cluster 集群
- **功能丰富**：发布订阅、Lua 脚本、事务、Pipeline

### Q2：Redis 为什么这么快？

| 原因 | 说明 |
|------|------|
| **纯内存操作** | 数据存在内存中，无磁盘 IO 瓶颈 |
| **单线程模型** | 没有多线程的上下文切换和锁竞争（6.0 之前命令执行是单线程） |
| **IO 多路复用** | 一个线程通过 epoll/kqueue 管理多个连接 |
| **高效数据结构** | 底层数据结构经过专门优化（SDS、跳表、压缩列表等） |

### Q3：Redis 是单线程还是多线程？

- **4.0 之前**：完全单线程（命令处理 + IO）
- **4.0**：引入后台线程（异步删除 unlink、flushdb async）
- **6.0**：引入多线程 IO，提升网络读写性能，但**命令执行仍然是单线程**
- **7.0**：继续增强多线程 IO

> Redis 的核心瓶颈不是 CPU，而是网络 IO 和内存带宽，所以用单线程执行命令就足够了。

## 2. 数据类型

### Q5：Redis 有哪些数据类型？各自适用什么场景？

| 类型 | 适用场景 | 示例 |
| --- | --- | --- |
| **String** | 缓存、计数器、分布式锁、限流 | 文章缓存、PV 统计 |
| **Hash** | 对象存储 | 用户信息、购物车 |
| **List** | 消息队列、最新列表 | 粉丝列表、评论列表 |
| **Set** | 去重、标签、共同好友 | 点赞用户、好友推荐 |
| **ZSet** | 排行榜、延迟队列 | 积分排行、延时任务 |
| **Bitmap** | 签到、在线状态 | 用户签到统计 |
| **HyperLogLog** | UV 统计 | 页面独立访客数 |
| **Geo** | 地理位置 | 附近的人 |

### Q6：ZSet 的底层实现是什么？

| 条件 | 编码 |
|------|------|
| 元素数量 < 128 且所有元素长度 < 64 字节 | `ziplist`（压缩列表）→ 7.0 后改为 `listpack` |
| 不满足以上条件 | `skiplist`（跳表）+ `dict`（字典） |

> **跳表**实现范围查询（O(logN)），**字典**实现单个分值查询（O(1)），两者共用同一份数据。

### Q7：Hash 的底层实现是什么？

| 条件 | 编码 |
|------|------|
| 元素数量 < 512 且所有元素长度 < 64 字节 | `ziplist` → 7.0 后 `listpack` |
| 不满足以上条件 | `hashtable` |

## 3. 持久化

### Q8：RDB 和 AOF 的区别？

| 维度 | RDB | AOF |
|------|-----|-----|
| **原理** | 定期 fork 子进程，将内存数据快照写入磁盘 | 记录每次写操作命令，追加到日志文件 |
| **文件** | `dump.rdb` | `appendonly.aof` |
| **恢复速度** | 快（直接加载二进制数据） | 慢（逐条回放命令） |
| **数据丢失** | 可能丢失最后一次快照到宕机之间的数据 | 最小可到 1 秒（`appendfsync everysec`） |
| **文件大小** | 小 | 大（可通过 rewrite 压缩） |

> **生产实践**：同时开启 RDB 和 AOF。RDB 用于备份和快速恢复，AOF 保证数据不丢失。

### Q9：AOF 重写（rewrite）的原理是什么？

AOF 文件会越来越大，rewrite 就是创建一个新的 AOF 文件：

1. fork 子进程，读取当前内存数据
2. 子进程将数据写入临时文件（以 SET 命令形式，而不是回放历史命令）
3. 主进程将 rewrite 期间的写命令同时写入旧 AOF + rewrite 缓冲区
4. 子进程完毕后，主进程将 rewrite 缓冲区的命令追加到新文件
5. 原子替换旧 AOF 文件

> rewrite 不会阻塞主进程，且新 AOF 文件更小、恢复更快。

## 4. 缓存问题

### Q10：什么是缓存穿透？怎么解决？

**现象**：查询不存在的数据，缓存和 DB 都查不到，请求直接打穿到 DB。

**解决方案**：

| 方案 | 说明 |
|------|------|
| **空值缓存** | 查不到的数据也缓存 null，过期时间设短一点（60s） |
| **布隆过滤器** | 先用布隆过滤器判断 key 是否存在，不存在直接返回 |
| **参数校验** | 对非法参数（-1、超长 ID）直接拦截 |

### Q11：什么是缓存击穿？怎么解决？

**现象**：某个热点 key 过期瞬间，大量请求同时打到 DB。

**解决方案**：

| 方案 | 说明 |
|------|------|
| **互斥锁** | 查不到缓存时，只有一个线程能去查 DB，其余等待 |
| **逻辑过期** | value 中存一个逻辑过期时间，过期后异步更新，旧值仍然可用 |
| **永不过期** | 热点 key 不设过期时间，通过异步任务更新 |

### Q12：什么是缓存雪崩？怎么解决？

**现象**：大量 key 同时过期，或 Redis 宕机，所有请求打到 DB。

**解决方案**：

- **过期时间加随机值**：避免集中过期，`expire = 基础时间 + random(0, 300)秒`
- **多级缓存**：Caffeine 本地缓存 + Redis 远程缓存
- **限流降级**：用 Resilience4j / Sentinel 限制打到 DB 的流量
- **高可用**：Redis 主从 + 哨兵，保证服务不挂

## 5. 分布式锁

### Q13：Redis 如何实现分布式锁？

```java
// 加锁：SET lock_key unique_value NX EX 30
String lockKey = "lock:order:" + orderId;
String lockValue = UUID.randomUUID().toString();
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, lockValue, 30, TimeUnit.SECONDS);

// 解锁：用 Lua 脚本保证原子性（检查 value + delete）
String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                "return redis.call('del', KEYS[1]) else return 0 end";
redisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
    Collections.singletonList(lockKey), lockValue);
```

**关键点**：
- `SET NX` 保证互斥
- `EX` 设置过期时间，防止死锁
- **value 用唯一标识**（UUID），解锁时校验，防止误删别人的锁
- **解锁用 Lua 脚本**，保证 check + delete 的原子性

### Q14：Redisson 的看门狗（Watch Dog）机制是什么？

`SETEX` 设置的锁时间太短，业务没执行完锁就过期了；太长，宕机又会有死锁问题。

Redisson 的 watch dog 机制：默认锁过期时间 30s，如果客户端还持有锁，**watch dog 每隔 10s 自动续期到 30s**，直到业务执行完主动释放。

> 这样既不会因业务执行时间过长而自动释放，也不会因为宕机导致永久死锁（watch dog 进程随客户端一起死）。

## 6. 集群与高可用

### Q15：Redis 集群模式有哪些？

| 模式 | 结构 | 特点 |
|------|------|------|
| **主从复制** | 一主多从 | 读写分离，故障需手动切换 |
| **Sentinel（哨兵）** | 主从 + 哨兵节点 | 自动故障转移，至少 3 个哨兵 |
| **Cluster（集群）** | 多主多从，数据分片 | 水平扩展，16384 个 hash slot |

### Q16：Redis Cluster 的数据分片原理？

- 将 key 通过 **CRC16 算法** hash 到一个 0-16383 的 slot
- 每个 master 节点负责一部分 slot
- 客户端计算 key 的 slot = `CRC16(key) % 16384`
- 直接连接到对应的 master 节点操作

```
slot 分配示例：
  Master1: slot 0-5460
  Master2: slot 5461-10922
  Master3: slot 10923-16383
```

### Q17：哨兵模式的选举过程？

1. **主观下线（SDOWN）**：某个哨兵发现 master 在规定时间未响应
2. **客观下线（ODOWN）**：多个哨兵（quorum 数量）都认为 master 下线
3. **Leader 选举**：哨兵中选出一个 leader（Raft 算法变体）
4. **故障转移**：leader 哨兵选择一个从节点升级为新 master
5. **通知**：通知其他从节点复制新 master，通知客户端新的 master 地址

## 7. 过期策略与内存淘汰

### Q18：Redis 的过期删除策略是什么？

**惰性删除 + 定期删除**：

| 策略 | 做法 |
|------|------|
| **惰性删除** | 访问 key 时才检查是否过期，过期则删除 |
| **定期删除** | 每隔 100ms 随机抽取一批 key 检查，过期则删除 |

> 为什么不用定时删除？如果每个 key 都设一个定时器，CPU 开销太大，Redis 单线程扛不住。

### Q19：内存淘汰策略有哪些？

| 策略 | 说明 |
|------|------|
| `noeviction` | 不淘汰，内存满时写入报错 |
| `allkeys-lru` | 所有 key 中淘汰最近最少使用的 |
| `volatile-lru` | 有过期时间的 key 中淘汰 LRU |
| `allkeys-lfu` | 所有 key 中淘汰最不经常使用的 |
| `volatile-lfu` | 有过期时间的 key 中淘汰 LFU |
| `volatile-ttl` | 有过期时间的 key 中淘汰 TTL 最短的 |
| `allkeys-random` | 所有 key 中随机淘汰 |
| `volatile-random` | 有过期时间的 key 中随机淘汰 |

> LRU vs LFU：LRU（Least Recently Used）看"最近"，LFU（Least Frequently Used）看"频率"。

## 8. 事务与管道

### Q20：Redis 事务的特点？

用 `MULTI` / `EXEC` / `DISCARD` / `WATCH` 实现：

- **不支持回滚**：某条命令失败不影响其他命令执行
- **单线程保证原子性**：事务中的命令不会被其他客户端的命令打断
- **WATCH 实现乐观锁**：监控 key，如果 key 被其他客户端修改，则 EXEC 失败

```bash
WATCH balance:user1
MULTI
DECRBY balance:user1 100
INCRBY balance:user2 100
EXEC
# 如果 user1 的余额在执行前被修改，EXEC 返回 nil
```

### Q21：Pipeline 是什么？和事务有什么区别？

**Pipeline**：客户端将多条命令打包一次发送，减少 RTT（网络往返时间）。

| 维度 | Pipeline | Transaction（MULTI/EXEC） |
|------|----------|---------------------------|
| **原子性** | 不保证 | 保证（命令不被打断） |
| **目的** | 减少网络开销 | 保证命令连续执行 |
| **错误处理** | 单条失败不影响后续 | 同上（也不回滚） |

> Pipeline 只是性能优化，不是原子性保证。

## 9. 其他高频问题

### Q22：Redis 怎么做延迟队列？

用 **ZSet**，score 为任务执行时间戳，定时任务按 score 范围拉取：

```java
// 添加延时任务
redisTemplate.opsForZSet().add("delay_queue", taskId, executeTime);

// 定时拉取到期任务
Set<String> tasks = redisTemplate.opsForZSet()
    .rangeByScore("delay_queue", 0, System.currentTimeMillis());
```

> Redis 6.2 引入 **Stream** 类型，支持更完善的消息队列功能（消费者组、ACK 机制）。

### Q23：大 key 和热 key 怎么处理？

**大 key**：单个 key 的 value 过大（String > 10KB 或集合元素 > 1w）

- **拆分**：大 Hash 拆成多个小 Hash，大 List 拆成多个小 List
- **定期清理**：设置过期时间，避免只增不减

**热 key**：某个 key 被大量请求集中访问

- **本地缓存**：Caffeine 缓存热点数据，减少 Redis 访问
- **读写分离**：增加从节点分摊读压力
- **复制热 key**：将热 key 复制到多个分片，客户端随机访问

### Q24：Redis 和数据库的双写一致性怎么保证？

**经典方案：先更新 DB，后删除缓存**

```
写操作：更新 DB → 删除缓存
读操作：查缓存 → 有则返回 → 无则查 DB → 写入缓存 → 返回
```

**延时双删**：如果要求更严格的一致性

```
1. 删除缓存
2. 更新 DB
3. 延迟 N 毫秒（等待其他线程读 DB 回写缓存结束）
4. 再次删除缓存
```

> 如果要保证最终一致，可以用 **Canal + MQ** 监听 MySQL binlog，异步更新/删除缓存。
