## 场景 1：缓存三兄弟 —— 穿透 / 击穿 / 雪崩

### 场景描述

你的电商系统首页需要展示商品列表。某天运营做了一次"整点秒杀"活动，活动开始瞬间：

- 秒杀商品的请求量暴涨 100 倍
- 首页缓存在活动开始前刚刚过期
- 数据库 CPU 飙到 100%，大量请求超时

请分析这个场景中出现了哪些缓存问题，以及如何解决。

### 分析

这是一个综合场景，包含了三种缓存问题的叠加：

1. **缓存雪崩**：首页多个缓存在相近时间过期，请求集中打到 DB
2. **缓存击穿**：秒杀商品是热点 key，过期瞬间大量请求穿透
3. **缓存穿透**：可能有恶意请求查询不存在的商品 ID

### 解决方案

**短期止血**：
```
1. 秒杀商品缓存设置逻辑过期，不设物理过期
2. 首页缓存过期时间加随机值：expire = 10min + random(0, 120)秒
3. 对不存在商品的请求返回空对象，缓存 60 秒
```

**长期方案**：

```
┌─────────────────────────────────────────────────────┐
│  请求 → Nginx 限流 → 本地缓存(Caffeine) → Redis → DB   │
│                                                      │
│  1. 本地缓存兜底（击穿/雪崩）                            │
│  2. 空值缓存（穿透）                                    │
│  3. 布隆过滤器（穿透）                                  │
│  4. 互斥锁更新（击穿）                                  │
│  5. 过期时间加随机值（雪崩）                              │
└─────────────────────────────────────────────────────┘
```

**关键代码思路**：

```java
// 热点 key 逻辑过期方案
public Product getProduct(Long id) {
    // 1. 查缓存
    String cacheJson = redisTemplate.opsForValue().get("product:" + id);
    if (StrUtil.isNotBlank(cacheJson)) {
        CacheData data = JSON.parseObject(cacheJson, CacheData.class);
        // 逻辑过期 → 返回旧数据 + 异步更新
        if (data.getExpireTime() < System.currentTimeMillis()) {
            asyncRefresh(id);  // 异步线程去查 DB 刷新缓存
        }
        return data.getValue();
    }
    // 2. 缓存没有 → 分布式锁 → 查 DB → 写缓存
    return queryWithMutex(id);
}
```

## 场景 2：分布式锁

### 场景描述

你负责的订单系统，用户在支付成功后会触发两个操作：
- 更新订单状态为"已支付"
- 给用户增加积分

某天发现部分用户支付一次，积分却加了两次。排查后发现是消息重复投递导致的：同一条支付消息被 MQ 投递了两次，两个 Consumer 并发处理了同一订单。

**问题**：如何用 Redis 实现一个可靠的分布式锁来解决这个问题？

### 分析

核心需求：
- **互斥性**：同一时刻只有一个线程能处理同一订单
- **防死锁**：如果线程挂了，锁能自动释放
- **防误删**：A 的锁不能被 B 释放
- **可重入**（可选）：同一个线程可以多次获取同一把锁

### 方案设计

**基础版（SETNX + EXPIRE）**：

```java
public String processOrder(Long orderId) {
    String lockKey = "lock:order:pay:" + orderId;
    String lockValue = UUID.randomUUID().toString();
    
    // 加锁：SET lock_key unique_value NX EX 30
    Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, lockValue, 30, TimeUnit.SECONDS);
    
    if (Boolean.FALSE.equals(locked)) {
        // 未获取锁，返回或重试
        return "订单正在处理中";
    }
    
    try {
        // 检查订单是否已处理（幂等性）
        if (isOrderProcessed(orderId)) {
            return "订单已处理";
        }
        updateOrderStatus(orderId);
        addUserPoints(orderId);
        markOrderProcessed(orderId);
    } finally {
        // 解锁：Lua 脚本保证原子性
        String script = 
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('del', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";
        redisTemplate.execute(
            new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList(lockKey), lockValue);
    }
    return "处理成功";
}
```

**进阶：生产级方案（Redisson）**：

```java
RLock lock = redissonClient.getLock("lock:order:pay:" + orderId);
try {
    // tryLock(等待时间, 过期时间, 时间单位)
    if (lock.tryLock(5, 30, TimeUnit.SECONDS)) {
        // 处理业务... Redisson 会自动续期
        processOrderBusiness(orderId);
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

### 关键点

| 问题 | 解法 |
|------|------|
| SETNX + EXPIRE 不是原子操作 | 用 `SET key value NX EX time` 一条命令 |
| 误删别人的锁 | value 存唯一标识（UUID），删除前校验 |
| 检查 + 删除不是原子操作 | 用 Lua 脚本 |
| 业务执行超时锁过期 | Redisson Watch Dog 自动续期 |
| 主从切换导致锁丢失 | **RedLock 算法**：向多个独立 Redis 实例加锁 |

### 面试追问：RedLock 是什么？

当 Redis 主从模式下，在主节点获取锁后，主节点宕机但数据还没同步到从节点，新主节点没有锁信息，其他线程又能获取锁。

RedLock 解法：向 N 个独立 Redis 节点（不是主从）依次加锁，当超过 N/2+1 个节点加锁成功，才算获取锁成功。

## 场景 3：排行榜

### 场景描述

运营需要一个"积分排行榜"功能：
- 实时显示全球前 100 名用户积分
- 能查询任意用户的排名
- 日活 100w+，积分变动频繁（每秒数百次更新）
- 每天零点清零重新计算

### 分析

这是一个典型的 ZSet 使用场景。

**为什么不用 MySQL？**
- 100w 行数据 `ORDER BY score DESC LIMIT 100` 走索引还好
- 但每秒数百次更新 + 查询，MySQL 压力会很大
- 需要实时反映积分变化

### 方案设计

```java
public class LeaderboardService {
    private static final String LEADERBOARD_KEY = "leaderboard:points:daily";
    
    // 更新积分
    public void addPoints(Long userId, int points) {
        redisTemplate.opsForZSet()
            .incrementScore(LEADERBOARD_KEY, userId.toString(), points);
    }
    
    // Top 100
    public List<TopUser> getTop100() {
        Set<ZSetOperations.TypedTuple<String>> top = redisTemplate.opsForZSet()
            .reverseRangeWithScores(LEADERBOARD_KEY, 0, 99);
        return top.stream()
            .map(t -> new TopUser(Long.parseLong(t.getValue()), t.getScore()))
            .collect(Collectors.toList());
    }
    
    // 查某个用户的排名（从 0 开始）
    public Long getUserRank(Long userId) {
        return redisTemplate.opsForZSet()
            .reverseRank(LEADERBOARD_KEY, userId.toString());
    }
    
    // 查某个用户的积分
    public Double getUserScore(Long userId) {
        return redisTemplate.opsForZSet()
            .score(LEADERBOARD_KEY, userId.toString());
    }
    
    // 每日零点清零：使用不同的 key（带日期后缀）
    // leaderboard:points:2024-01-15
    // leaderboard:points:2024-01-16
}
```

### 大数据量优化

1. **分桶存储**：100w 用户按 ID hash 到 10 个 ZSet 桶，查 Top 100 时先查每个桶的 Top 100，再合并排序
2. **Key 按日期隔离**：每天新 key，自动清零
3. **冷数据归档**：历史排行榜数据定期迁移到 MySQL

## 场景 4：秒杀系统

### 场景描述

设计一个秒杀系统，秒杀商品库存 100 件，预计 10w 人同时抢购。

**核心挑战**：
- 高并发下如何保证不超卖
- 如何尽量少地访问 DB
- 如何防止黄牛脚本

### 方案设计

```
用户 → 限流（令牌桶）→ Redis 扣库存 → 消息队列 → DB 创建订单
         ↓ 拦截          ↓ 失败               ↑
      超过限流阈值    库存不足返回         异步处理
```

**Redis 预减库存**：

```java
public class SeckillService {
    
    // 预热：活动开始前将库存加载到 Redis
    public void preheat() {
        redisTemplate.opsForValue()
            .set("seckill:stock:10086", "100");
    }
    
    // 扣库存（Lua 脚本保证原子性）
    public SeckillResult seckill(Long productId, Long userId) {
        String script = 
            "local key = KEYS[1] " +
            "local stock = tonumber(redis.call('get', key)) " +
            "if stock == nil or stock <= 0 then " +
            "    return -1 " +  // 库存不足
            "end " +
            "redis.call('decr', key) " +
            "return stock - 1";  // 返回剩余库存
        
        Long remaining = redisTemplate.execute(
            new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList("seckill:stock:" + productId));
        
        if (remaining == null || remaining < 0) {
            return new SeckillResult(false, "库存不足");
        }
        
        // 去重：一人一单
        Boolean firstSeckill = redisTemplate.opsForValue()
            .setIfAbsent("seckill:user:" + productId + ":" + userId, 
                "1", 10, TimeUnit.MINUTES);
        if (Boolean.FALSE.equals(firstSeckill)) {
            return new SeckillResult(false, "已参与过秒杀");
        }
        
        // 发送 MQ 异步创建订单
        rocketMQTemplate.asyncSend("seckill-order", 
            new SeckillMessage(productId, userId));
        
        return new SeckillResult(true, "排队中");
    }
}
```

### 关键设计点

| 要点 | 方案 |
|------|------|
| **超卖** | Lua 脚本原子扣库存 |
| **重复下单** | Redis Set 记录已秒杀用户 |
| **高并发** | Redis 扣库存在内存完成，不碰 DB |
| **流量削峰** | MQ 缓冲，异步创建订单 |
| **防黄牛** | 限流 + 用户黑名单 + 验证码 |
| **热点 key** | 库存 key 分散到多个 slot |
| **失败回补** | 下单失败，Redis 库存 +1 |

## 场景 5：计数系统

### 场景描述

你的内容平台需要展示文章的阅读量、点赞数、评论数。要求：
- 计数实时展示
- 10w+ 篇文章，每篇都有 3 个计数器
- 写入量很大（点赞每秒上千次）
- 不需要精确到个位（可以接受少量误差）

### 方案设计

**Redis Hash — 一篇文章一个 Hash**：

```java
public class CounterService {
    
    // 阅读量 +1
    public void incrReadCount(Long articleId) {
        redisTemplate.opsForHash()
            .increment("counter:article:" + articleId, "read", 1);
    }
    
    // 点赞（带去重）
    public LikeResult like(Long articleId, Long userId) {
        // 1. 检查是否已点赞
        Boolean liked = redisTemplate.opsForSet()
            .isMember("like:article:" + articleId, userId.toString());
        if (Boolean.TRUE.equals(liked)) {
            return LikeResult.alreadyLiked();
        }
        // 2. 记录点赞 + 计数
        redisTemplate.opsForSet().add("like:article:" + articleId, userId.toString());
        redisTemplate.opsForHash()
            .increment("counter:article:" + articleId, "like", 1);
        return LikeResult.success();
    }
    
    // 获取计数
    public ArticleCount getCount(Long articleId) {
        Map<Object, Object> counts = redisTemplate.opsForHash()
            .entries("counter:article:" + articleId);
        // ...
    }
}
```

**HyperLogLog — UV 统计（允许误差）**：

```java
// 记录访问
public void recordUV(Long articleId, Long userId) {
    redisTemplate.opsForHyperLogLog()
        .add("uv:article:" + articleId, userId.toString());
}

// 获取 UV
public long getUV(Long articleId) {
    return redisTemplate.opsForHyperLogLog()
        .size("uv:article:" + articleId);
}
```

> HyperLogLog 每个 key 只占 12KB，标准误差 0.81%，非常适合百万级别的去重统计。

**Bitmap — 日签到统计**：

```java
public class CheckinService {

    public void checkin(Long userId) {
        String key = "checkin:" + LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);

    // 今日签到人数
    public long checkinCount() {
        String key = "checkin:" + LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);

    }
}
```

## 场景 6：消息队列

### 场景描述

某些旧系统没有引入专业的 MQ（RocketMQ / Kafka），但需要一个简单的异步任务队列。

**需求**：用户导入 Excel 后，异步解析并入库，支持：
- FIFO 顺序处理
- 多个 Worker 并行消费
- 任务失败可重试

### Redis List 方案

```java
// Producer：往队尾塞任务
public void submitTask(ImportTask task) {
    redisTemplate.opsForList()
        .rightPush("queue:import:task", JSON.toJSONString(task));
}

// Consumer：从队头取任务（阻塞式）
public void consumeTask() {
    while (true) {
        // BLPOP 阻塞等待，timeout=0 表示无限等待
        String taskJson = (String) redisTemplate.opsForList()
            .rightPop("queue:import:task", 0, TimeUnit.SECONDS);
        
        try {
            processImport(JSON.parseObject(taskJson, ImportTask.class));
        } catch (Exception e) {
            // 失败重试：塞到重试队列
            redisTemplate.opsForList()
                .leftPush("queue:import:task:retry", taskJson);
        }
    }
}
```

### Redis Stream（6.2+，推荐）

相比 List，Stream 支持消费者组、ACK 确认、消息回溯：

```java
// 创建消费者组
redisTemplate.opsForStream()
    .createGroup("stream:import", "worker-group");

// 消费
List<MapRecord<String, Object, Object>> records = redisTemplate.opsForStream()
    .read(Consumer.from("worker-group", "worker-1"),
          StreamOffset.create("stream:import", ReadOffset.lastConsumed()));

// 确认
redisTemplate.opsForStream()
    .acknowledge("stream:import", "worker-group", record.getId());
```

### 方案对比

| 特性 | Redis List | Redis Stream | RocketMQ / Kafka |
|------|------------|-------------|-----------------|
| ACK 确认 | 无（pop 即删） | 支持 | 支持 |
| 消费者组 | 无 | 支持 | 支持 |
| 持久化 | 需开 AOF/RDB | 同左 | 天生持久化 |
| 吞吐量 | 低 | 中 | 高 |
| 适用 | 简单场景 | 中等场景 | 核心业务 |

> 对于核心业务，建议直接上 RocketMQ / Kafka。

## 场景 7：附近的人（GEO）

### 场景描述

社交应用需要展示"附近的人"，按距离排序，支持筛选距离范围。

### Redis GEO 方案

```java
// 添加用户位置
public void updateLocation(Long userId, double longitude, double latitude) {
    redisTemplate.opsForGeo()
        .add("user:location", new Point(longitude, latitude), userId.toString());
}

// 查询附近的人（半径 5 公里，带距离）
public List<NearbyUser> nearbyUsers(double lng, double lat, double radiusKm) {
    Circle circle = new Circle(
        new Point(lng, lat),
        new Distance(radiusKm, Metrics.KILOMETERS));
    
    RedisGeoCommands.GeoRadiusCommandArgs args = 
        RedisGeoCommands.GeoRadiusCommandArgs.newGeoRadiusArgs()
            .includeDistance()
            .includeCoordinates()
            .sortAscending()
            .limit(50);
    
    GeoResults<RedisGeoCommands.GeoLocation<String>> results = 
        redisTemplate.opsForGeo()
            .radius("user:location", circle, args);
    
    return results.getContent().stream()
        .map(r -> new NearbyUser(
            Long.parseLong(r.getContent().getName()),
            r.getDistance().getValue()))
        .collect(Collectors.toList());
}
```

> GEO 底层也是 ZSet，用 Geohash 将经纬度编码为 score，查询效率 O(logN)。

## 场景 8：接口防刷 / 限流

### 场景描述

某个公开 API 被恶意刷量，1 分钟内同一个 IP 调用了上千次。需要实现一个简单的限流器。

### 滑动窗口限流

```java
public class RateLimiter {
    
    /**
     * 滑动窗口限流
     * @param key 限流标识（如 IP 或 userId）
     * @param windowSeconds 窗口时间（秒）
     * @param maxRequests 窗口内最大请求数
     */
    public boolean isAllowed(String key, int windowSeconds, int maxRequests) {
        String redisKey = "ratelimit:" + key;
        long now = System.currentTimeMillis();
        long windowStart = now - windowSeconds * 1000L;
        
        // Lua 脚本：删除窗口外的记录 + 计数 + 判断
        String script = 
            "redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1]) " +
            "local count = redis.call('ZCARD', KEYS[1]) " +
            "if count < tonumber(ARGV[3]) then " +
            "    redis.call('ZADD', KEYS[1], ARGV[2], ARGV[2]) " +
            "    redis.call('EXPIRE', KEYS[1], ARGV[4]) " +
            "    return 1 " +
            "end " +
            "return 0";
        
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList(redisKey),
            String.valueOf(windowStart),       // ARGV[1]
            String.valueOf(now),               // ARGV[2]
            String.valueOf(maxRequests),       // ARGV[3]
            String.valueOf(windowSeconds * 2)); // ARGV[4]: key 存活时间
        
        return Long.valueOf(1).equals(result);
    }
}

// 使用
if (!rateLimiter.isAllowed("api:getData:" + ip, 60, 100)) {
    throw new ServiceException("请求过于频繁，请稍后再试");
}
```

### 方案对比

| 方案 | 原理 | 精度 | Redis 命令 |
|------|------|------|-----------|
| 固定窗口 | 每分钟重置计数 | 低（临界点问题） | INCR + EXPIRE |
| 滑动窗口 | ZSet 记录请求时间戳 | 高 | ZREMRANGEBYSCORE + ZADD + ZCARD |
| 令牌桶 | 固定速率放入令牌，请求需获取令牌 | 高 | Lua 脚本 |
| 漏桶 | 固定速率漏水（处理请求） | 高 | Lua 脚本 |
