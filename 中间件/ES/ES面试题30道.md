## 一、基础概念（第 1-10 题）

### 1. 什么是 Elasticsearch？请简单介绍一下

Elasticsearch 是一个基于 **Apache Lucene** 构建的**分布式搜索与分析引擎**。它提供：

- **全文搜索**：基于倒排索引，毫秒级返回
- **近实时（NRT）**：写入后默认 1 秒可搜索
- **RESTful API**：通过 HTTP JSON 交互
- **水平扩展**：数据分片分布在多节点，支持 PB 级数据

---

### 2. ES 和 MySQL 有什么区别？为什么 ES 搜索快？

| 维度 | MySQL | Elasticsearch |
|------|-------|---------------|
| **核心索引** | B+ 树 | 倒排索引 |
| **全文搜索** | `LIKE '%keyword%'`，全表扫描 | 查倒排索引，O(1) 定位 |
| **分词** | 不支持 | 内置分词器（IK、Standard） |
| **相关性排序** | 无 | TF-IDF / BM25 算法 |
| **适用场景** | 事务型 OLTP | 搜索型 OLAP |

**ES 搜索快的原因**：倒排索引将"搜索词 → 文档列表"预先建好，搜索时直接查索引而非遍历数据。

---

### 3. 倒排索引是什么？实现原理是什么？⭐

**定义**：倒排索引是一种将**词条映射到包含它的文档**的数据结构。

**三大组件**：

| 组件 | 数据结构 | 作用 |
|------|----------|------|
| Posting List | FOR 压缩 + Roaring Bitmap | 存储 Term 对应的 DocID 列表 |
| Term Dictionary | 排序数组 + 二分查找 | 所有 Term 的排序字典 |
| Term Index | FST（有限状态转换器） | Term Dictionary 的前缀索引，内存占用极小 |

**搜索流程**：搜索词 → Term Index 定位 Term 范围 → Term Dictionary 二分查找 Term → Posting List 获取 DocID → 返回文档。

---

### 4. text 和 keyword 类型的区别？⭐

| 维度 | text | keyword |
|------|------|---------|
| **分词** | 会分词 | 不分词，原样存储 |
| **索引** | 建立倒排索引 | DocValues 正排索引 |
| **搜索** | `match` 全文搜索 | `term` 精确匹配 |
| **排序** | ❌ 不支持 | ✅ 支持 |
| **聚合** | ❌（需 fielddata，耗内存） | ✅ 支持 |

**最佳实践**：字符串字段一般配两个类型 —— `"type": "text"` 用于搜索 + `"fields": {"keyword": {"type": "keyword"}}` 用于排序聚合。

---

### 5. ES 为什么这么快？（高吞吐原理）⭐

| 机制 | 说明 |
|------|------|
| **倒排索引** | 搜索词到文档的直接映射，O(1) 查找 |
| **FST 前缀索引** | Term Index 以 FST 结构存在内存，极快定位 |
| **Segment 不可变** | 写入后 Segment 只读，不需要锁，可并发读取 |
| **文件系统缓存** | OS Page Cache 缓存 Segment 文件，减少磁盘 IO |
| **跳跃表（SkipList）** | Posting List 中跳跃定位，加速 AND/OR 位运算 |
| **分布式并行** | 查询分发到多个分片并行执行 |

---

### 6. query 和 filter 的区别？

| 维度 | Query | Filter |
|------|-------|--------|
| **计分** | ✅ 计算 _score（相关性评分） | ❌ 不计分 |
| **缓存** | ❌ 不缓存 | ✅ 自动缓存（BitSet） |
| **性能** | 较慢 | 较快 |

**最佳实践**：全文搜索用 Query，精确条件用 Filter。

### 7. ES 的基本概念有哪些？

| 概念 | 说明 | 类比 MySQL |
|------|------|-----------|
| Cluster | 集群，由多个节点组成 | 数据库实例 |
| Node | 节点，单个 ES 实例 | 数据库进程 |
| Index | 索引，文档的集合 | Table |
| Shard | 分片，Index 的物理切分 | 分表 |
| Replica | 副本，分片的复制 | 从库 |
| Document | 文档，JSON 格式记录 | Row |
| Field | 字段 | Column |
| Mapping | 字段类型定义 | Schema |

---

### 8. 分片（Shard）和副本（Replica）有什么区别？

| 维度 | 分片（Primary Shard） | 副本（Replica Shard） |
|------|----------------------|----------------------|
| **作用** | 水平拆分数据，提升写入吞吐 | 数据冗余，提升查询吞吐 |
| **数量** | 创建 Index 时指定，不可修改 | 可动态调整 |
| **读写** | 负责写入 | 只读（从 Leader 同步） |

**规划原则**：主分片数 = 节点数的 1.5~3 倍；副本数 ≥ 1。

---

### 9. 详细描述 ES 索引文档的过程（写入流程）⭐

```
1. 客户端发送写入请求 → 协调节点
2. 协调节点通过路由公式定位主分片：shard = hash(_id) % num_primary_shards
3. 请求到达主分片 → 写入 Memory Buffer + 同时写入 Translog
4. 主分片将请求转发到所有副本分片
5. 所有副本写入完成后 → 主分片返回 ACK
6. Refresh（1s）后，数据从 Memory Buffer 刷新到 Filesystem Cache，变为可搜索
7. Flush（30min/512MB translog）后，数据 fsync 到磁盘 Segment
```

> **关键**：Translog（事务日志）是写入可靠性的保障 —— 节点宕机后从 Translog 恢复未 Flush 的数据。

---

### 10. Refresh 和 Flush 的区别？⭐

| 维度 | Refresh | Flush |
|------|---------|-------|
| **操作** | Memory Buffer → Filesystem Cache | Filesystem Cache → 磁盘 Segment |
| **触发频率** | 默认 1s | 默认 30min 或 Translog ≥ 512MB |
| **数据可搜索** | 是（Refresh 后才可搜） | — |
| **数据持久化** | 否 | 是 |
| **性能影响** | 频繁 Refresh 影响写入 | 频繁 Flush 影响 IO |

## 二、集群与架构（第 11-15 题）

### 11. ES 集群架构是怎样的？

```
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │  Master Node │  │  Data Node 1 │  │  Data Node 2 │
  │  (4C8G)      │  │  P0,P1(Rep)  │  │  P1,P0(Rep)  │
  └──────┬───────┘  └──────────────┘  └──────────────┘
         │                ▲                  ▲
         └────────────────┴──────────────────┘
                    集群元数据管理

  ┌──────────────┐
  │Coordinating   │  接收客户端请求，分发查询，聚合结果
  │Node (2台)     │  计算密集操作隔离，防止 OOM 扩散
  └──────────────┘
```

**角色分离**：

| 节点类型 | 职责 | 硬件建议 |
|----------|------|----------|
| Master | 集群管理、元数据维护 | 4C8G |
| Data | 数据存储、查询执行 | 16C64G + NVMe SSD |
| Coordinating | 请求路由、结果聚合 | 8C16G |
| Ingest | 数据预处理（Pipeline） | 按需配置 |

---

### 12. ES 如何实现 Master 选举？脑裂怎么解决？

**选举机制**（基于 Bully 算法的改进版）：

1. 所有候选节点按 nodeId 排序
2. 每个节点 Ping 所有其他节点
3. 如果发现超过 `discovery.zen.minimum_master_nodes` 个节点都认为当前 Master 存活，则接受
4. 否则发起新一轮选举

**脑裂防护**（7.x 前）：

```yaml
# elasticsearch.yml
discovery.zen.minimum_master_nodes: N/2+1   # N = 候选 Master 节点数
```

- 3 个 Master 节点 → `minimum_master_nodes = 2`
- 只有获得 ≥ 2 票的节点才能成为 Master，避免双主

> ES 7.x+ 已移除该参数，改用新的 `cluster.initial_master_nodes` 引导配置，脑裂防护内化。

---

### 13. 客户端如何自动发现集群节点？

- ES 节点间通过 **Zen Discovery** 模块互相发现
- 客户端只需配置**一个或多个种子节点地址**，首次连接后拉取完整集群拓扑
- 后续自动感知节点上下线，更新路由表

---

### 14. 数据倾斜（热点问题）如何处理？

**现象**：某个分片数据量远大于其他分片，导致该节点成为性能瓶颈。

**原因**：
- `_id` 路由不均匀
- 使用了 `routing` 但 Key 分布不均
- 默认 Hash 取模在特殊 Key 下倾斜

**解决方案**：

```
1. 使用随机 _id（自动生成）而非业务 ID
2. 自定义 routing Key 分布均匀
3. 利用 _split API 拆分热点分片
4. 冷热分离架构（Hot-Warm-Cold）
```

---

### 15. 分片数量怎么规划？

**黄金法则**：

| 原则 | 说明 |
|------|------|
| 单分片 30-50GB | 太小元数据爆炸，太大故障恢复慢 |
| 单节点分片数 ≤ 磁盘GB × 20 | JVM 只管理分片元数据，过载影响性能 |
| 主分片 = 节点数 × (1.5~3) | 充分利用并行能力 |
| 副本 ≥ 1 | 核心索引建议设 2 |

**日增量计算公式**：

```
主分片数 = (日增量GB × 保留天数 × 1.4) / 40GB
```

## 三、查询与搜索（第 16-20 题）

### 16. 详细描述 ES 的搜索过程（Query Then Fetch）⭐

```
阶段1：Query Phase（查询阶段）
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ 协调节点启动│→│广播到所有 │→│每个分片返回│
  │          │  │相关分片   │  │(docId,_score)│
  └──────────┘  └──────────┘  └──────────┘
                     ↓
  Coordinator 排序后确定全局 Top N（如 Top 10）

阶段2：Fetch Phase（获取阶段）
  ┌──────────┐  ┌──────────┐
  │按 docId 到│→│返回完整文档│→ 响应客户端
  │对应分片拉取│  │(_source)  │
  └──────────┘  └──────────┘
```

> Query 阶段只传 `docId + _score`，不传 `_source`，减少网络开销。

### 17. ES 的深度分页问题怎么解决？⭐

**问题**：`from=10000, size=10` → Coordinator 要从每个分片取 10010 条，内存排序后取第 10000~10010 条。数据量越大越慢。

**硬限制**：`index.max_result_window=10000`。

**解决方案**：

| 方案 | 说明 | 适用场景 |
|------|------|----------|
| **search_after** | 基于上一页最后一条的 sort 值翻页（推荐） | 实时翻页 |
| **Scroll** | 生成快照游标（已废弃） | 批量导出 |
| **PIT（Point In Time）** | ES 7.10+，快照视图 + search_after | 大数据量遍历 |

```json
// search_after 实现
GET /products/_search
{
  "size": 10,
  "query": { "match": { "title": "手机" } },
  "sort": [{ "price": "asc" }, { "_id": "asc" }],
  "search_after": [4999, "product_123"]
}
```

### 18. match 和 term 的区别？

| 维度 | match | term |
|------|-------|------|
| **分词** | ✅ 对搜索词分词 | ❌ 不分词 |
| **匹配方式** | 词条匹配（部分匹配） | 精确匹配（完全一致） |
| **适用字段** | text | keyword / 数值 / 日期 |
| **示例** | `match: {title: "华为手机"}` → 匹配含"华为"或"手机"的文档 | `term: {brand: "华为"}` → brand 字段必须是"华为" |

### 19. 分词器的分词流程是怎样的？

```
输入文本 → Character Filter → Tokenizer → Token Filters → 词条列表

"<p>华为最新手机</p>"
  ↓ Character Filter（去除 HTML 标签）
"华为最新手机"
  ↓ Tokenizer（分词）
["华为", "最新", "手机"]
  ↓ Token Filters（停用词移除）
["华为", "最新", "手机"]
  ↓ Token Filters（小写转换，英文适用）
["华为", "最新", "手机"]
```

### 20. ES 支持事务吗？

**不支持**传统数据库意义上的 ACID 事务。

- 单文档级别：**原子性**保证（写入要么全成功要么全失败）
- 跨文档/跨索引：不支持 ACID
- 可通过版本控制（`_version` / `if_seq_no + if_primary_term`）实现乐观锁

## 四、性能优化（第 21-25 题）

### 21. 索引写入性能如何提升？⭐

| 优化措施 | 配置 | 说明 |
|----------|------|------|
| **批量写入** | `_bulk` API | 每批 1000~5000 条 |
| **调大 refresh_interval** | `refresh_interval=30s` | 减少 Refresh 次数 |
| **异步 Translog** | `translog.durability=async` | 不每次 fsync |
| **关闭副本** | `number_of_replicas=0` | 初始加载时关闭，加载完后开启 |
| **增加分片** | 合理规划分片数 | 并行写入 |

```json
// 大批量写入时的索引设置
PUT /my_index
{
  "settings": {
    "refresh_interval": "30s",
    "number_of_replicas": 0,
    "translog": { "durability": "async" }
  }
}
// 写入完成后恢复
PUT /my_index/_settings
{ "refresh_interval": "1s", "number_of_replicas": 1 }
```

### 22. 查询性能如何优化？⭐

| 优化措施 | 说明 |
|----------|------|
| **Filter 代替 Query** | 精确条件用 Filter，利用缓存，不计分 |
| **_source 过滤** | `"_source": ["field1","field2"]` 只返回需要的字段 |
| **禁用通配符前缀** | `*keyword` 性能极差，避免使用 |
| **keyword 聚合** | 聚合用 keyword 而非 text |
| **限制聚合 size** | `"size": 10` 而非默认 10000 |
| **查询 Profile** | `"profile": true` 分析慢查询 |

### 23. ES 索引数据多了怎么调优？

| 策略 | 说明 |
|------|------|
| **Rollover** | 按时间/大小滚动创建新索引（`logs-000001` → `logs-000002`） |
| **冷热分离** | Hot 节点（SSD，最近数据）+ Warm 节点（HDD，历史数据） |
| **Force Merge** | 强制合并 Segment（只读索引适用） |
| **Shrink** | 冷数据减少分片数，降低元数据开销 |
| **ILM** | 索引生命周期管理：Hot → Warm → Cold → Delete |

### 24. JVM 堆内存为什么建议设 31GB？

**原因**：**Compressed Oops（压缩普通对象指针）**。

- JVM 对象指针默认 8 字节
- 堆 ≤ **32GB** 时，JVM 自动将指针压缩为 4 字节（节省一半内存）
- 但实际上触发压缩的阈值约 **31GB**（给非堆空间留余地）
- **超过 32GB 后指针恢复到 8 字节**，内存利用率反而下降

> 结论：堆内存设为 31GB，剩余内存留给 OS Page Cache 用于文件缓存加速。

### 25. ES 的 Segment 和 Merge 机制是什么？

**Segment（段）**：

- ES 以 Segment 为单位存储数据，一个分片包含多个 Segment
- 每个 Segment 是不可变的倒排索引
- 写入时生成新 Segment，删除时标记删除（不立即物理删除）

**Merge（段合并）**：

- 后台自动将多个小 Segment 合并为大 Segment
- 合并时真正删除被标记的文档，释放空间
- 合并消耗 IO 和 CPU，应避开高峰期执行

## 五、数据同步与实战（第 26-30 题）

### 26. MySQL 数据如何同步到 ES？

| 方案 | 说明 | 优缺点 |
|------|------|--------|
| **Logstash JDBC** | 定时 SQL 查询全量/增量 | 简单但有延迟，大数据量压力大 |
| **Canal** | 伪装 MySQL Slave，解析 Binlog 推送变更 | 实时性好，阿里开源，生产主流 |
| **MQ 双写** | 应用层同时写 MySQL 和 MQ → ES | 实时性好，需处理数据一致性 |
| **Flink CDC** | 基于 Flink 的 CDC Connector | 流式计算，支持复杂转换 |

---

### 27. ES 和 MySQL 的数据一致性如何保证？

**Canal + MQ 方案**：

```
MySQL 变更 → Canal 解析 Binlog → MQ(Kafka) → ES 消费者写入
```

**一致性保障**：

```
1. 顺序保证：同一行的变更发往 MQ 同一分区
2. 幂等处理：ES 写入用 _id 作为主键（相同 _id 覆盖）
3. 对账机制：定时全量对账（对比 MySQL 和 ES 数据）
4. 最终一致性：接受秒级延迟，不追求强一致
```

---

### 28. 并发情况下 ES 如何保证读写一致？

ES 使用**乐观锁 + 版本号**机制：

```json
// 写入时带版本号
PUT /products/_doc/1?version=5
{ "title": "华为手机", "price": 5999 }
// 如果当前版本号不是 5 则返回 409 Conflict

// 新版推荐使用 seq_no + primary_term
PUT /products/_doc/1?if_seq_no=10&if_primary_term=2
{ "title": "华为手机", "price": 5999 }
```

**内部机制**：

- 每次写入 `_version` 自增 1
- 写入时比对 `_version` / `if_seq_no`，冲突则拒绝
- 应用层收到 409 后自行决定重试或放弃

### 29. Elasticsearch 索引文档多了怎么办？（超大索引优化）

**问题表现**：单索引 1TB+ → 分片过大 → 查询慢 + 恢复慢。

**解决**：**Rollover + 索引别名**

```
1. 创建索引别名 orders_write
2. 别名指向最新索引 orders-000001
3. Rollover 条件（满足其一）：
   - 索引大小 > 50GB
   - 文档数 > 1亿
   - 时间跨度 > 1天
4. 触发 Rollover → 创建 orders-000002，别名指向新索引
5. 查询时用 orders_read 别名（指向所有索引）
```
