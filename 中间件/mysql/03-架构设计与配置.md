## 分布式 ID 方案

### 五种方案对比

| 方案 | 有序性 | 唯一性 | 插入性能 | 分库分表友好 | 依赖 | 缺点 |
|------|--------|--------|----------|-------------|------|------|
| **自增 ID** | 严格递增 | 单库唯一 | 高 | 差 | 数据库 | 分库分表会冲突 |
| **UUID v4** | 完全无序 | 全局唯一 | 差 | 好 | 无 | 无序导致频繁页分裂，索引性能差 |
| **雪花算法** | 严格递增 | 全局唯一 | 高 | 好 | 系统时钟 | 时钟回拨可能重复；workerId 需协调 |
| **号段模式** | 严格递增 | 全局唯一 | 高 | 好 | 数据库 | 依赖数据库，重启可能浪费号段 |
| **ULID / UUID v7** | 趋势递增 | 全局唯一 | 高 | 好 | 无 | 同一毫秒内不严格递增 |





## 分库分表

### 为什么要拆分？

InnoDB 数据页默认 16KB，单行数据过大会导致每页存储行数减少、B+ 树层数增加、查询性能下降。当数据量超过单节点承载能力时，需要拆分。

### 垂直拆分

将单行数据中的大字段或不同业务模块拆到不同的表/库中。

- **目的**：减小单行数据体积，提高数据页密度
- **局限**：缓解问题但无法根治，数据量持续增长仍需水平拆分

> 应在设计初期就考虑是否需要拆分，避免后期改造成本。

### 水平拆分

将一个表的数据按水平维度切割到多个表/库中。

### 分片算法

| 算法 | 原理 | 范围查询 | 数据均匀性 | 动态伸缩 | 推荐 |
|------|------|----------|-----------|----------|------|
| **哈希分片** | 对分片键取哈希，根据哈希值分配 | 不适合 | 均匀 | 不友好（新增节点需重新分布） | 不推荐 |
| **范围分片** | 按区间分配（如 ID 1~30W、30W~60W） | 适合 | 可能不均匀（热点问题） | 友好 | 视业务场景 |
| **映射表分片** | 独立表存储分片键与位置的映射 | 支持 | 取决于规则 | 灵活 | 不推荐（额外开销） |
| **一致性哈希** | 环形结构，顺时针分配到最近节点 | 一般 | 较均匀 | 友好（解决传统哈希伸缩问题） | **推荐** |

> 一般根据业务选择**范围分片**或**一致性哈希分片**。范围分片适合按时间/ID 有序的场景，一致性哈希适合随机读写场景。

## 多数据源与分库分表实现方案

面临两个不同的场景，有两套方案：

| 场景 | 方案 | 代表 |
|------|------|------|
| **分库分表** — 单表太大需要拆 | SQL 解析自动路由 | ShardingSphere |
| **多数据源** — 不同业务连不同库 | AOP + ThreadLocal 手动切换 | 苞米豆 dynamic-datasource |

### 分库分表中的 ID 生成（雪花算法代码）

分库分表后，自增 ID 在不同分片上会冲突，需要**分布式 ID**。雪花算法是生产环境最常用的方案，以 Hutool 的 `Snowflake` 实现为例：

**关键常量定义：**

```java
private static final long WORKER_ID_BITS = 5L;         // 机器 ID 占 5 位
private static final long DATA_CENTER_ID_BITS = 5L;    // 数据中心 ID 占 5 位
private static final long SEQUENCE_BITS = 12L;          // 序列号占 12 位

// 用位运算计算各部分的最大值
private static final long MAX_WORKER_ID = -1L ^ (-1L << WORKER_ID_BITS);          // 31
private static final long MAX_DATA_CENTER_ID = -1L ^ (-1L << DATA_CENTER_ID_BITS); // 31

// 各字段的左移位数
private static final long WORKER_ID_SHIFT = SEQUENCE_BITS;                                                    // 12
private static final long DATA_CENTER_ID_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS;                              // 17
private static final long TIMESTAMP_LEFT_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS + DATA_CENTER_ID_BITS;        // 22

// 序列掩码：低 12 位全为 1，用于序列满归零
private static final long SEQUENCE_MASK = ~(-1L << SEQUENCE_BITS);   // 4095
```

**ID 生成核心代码：**

```java
public synchronized long nextId() {
    long timestamp = genTime();

    // 同一毫秒内，序列号自增；满 4096 归零，等待下一毫秒
    if (timestamp == this.lastTimestamp) {
        long sequence = (this.sequence + 1) & SEQUENCE_MASK;   // & 运算实现满归零
        if (sequence == 0) {
            timestamp = tilNextMillis(lastTimestamp);            // 等到下一毫秒
        }
        this.sequence = sequence;
    } else {
        sequence = 0L;                                          // 新毫秒，序列归零
    }

    lastTimestamp = timestamp;

    // 用 | 运算将四部分拼接到一个 long 中
    return ((timestamp - twepoch) << TIMESTAMP_LEFT_SHIFT)
            | (dataCenterId << DATA_CENTER_ID_SHIFT)
            | (workerId << WORKER_ID_SHIFT)
            | sequence;
}
```

> **位运算贯穿整个雪花算法**：`^` 计算最大值、`<<` 预留位段、`&` 满归零、`|` 拼接字段、`>>` + `&` 反解字段。详见 [算法/位运算.md](../../算法/位运算.md)。

### 方案一：ShardingSphere（SQL 解析自动路由）

#### 五个角色

| 角色 | 是什么 | 谁提供的 | 职责 |
|------|--------|----------|------|
| **DataSource** | `javax.sql.DataSource` 接口 | JDK | 提供 JDBC Connection |
| **ShardingSphereDataSource** | DataSource 的实现类（**代理**） | ShardingSphere | 拦截 SQL，触发解析→路由→改写→执行→归并 |
| **HikariDataSource / DruidDataSource** | DataSource 的实现类 | 连接池 | 管理每个分片的物理连接（每个分片独立连接池） |
| **SQLParserEngine** | SQL 解析引擎 | ShardingSphere | 解析 SQL 语义，提取表名、分片键、条件 |
| **ShardingRouter** | 分片路由器 | ShardingSphere | 根据分片算法 + 分片键值，计算目标库和目标表 |

> ShardingSphereDataSource 是**代理层**，它不管理连接，只拦截和改写 SQL；真实的连接由底层连接池管理。

```
没有 ShardingSphere：
  SqlSessionFactory → HikariDataSource → Connection → 执行 SQL

有 ShardingSphere：
  SqlSessionFactory → ShardingSphereDataSource（代理）
                        ├── "ds_0" → HikariDataSource → Connection → db_0
                        └── "ds_1" → HikariDataSource → Connection → db_1
                       代理层              连接池层（每个分片独立）
```

#### 核心原理

整个原理可以拆成三步：**启动时代理 → 运行时拦截 → 五阶段处理**。

**第 1 步：启动时 — ShardingSphereDataSource 替换真实 DataSource**

```java
// ShardingSphere 启动时注册 DataSource（简化）
@Configuration
@AutoConfigureBefore(DataSourceAutoConfiguration.class)   // 抢在 SpringBoot 默认配置之前
public class ShardingSphereAutoConfiguration {

    @Bean
    @Primary
    public DataSource shardingSphereDataSource(ShardingSphereProperties props) {
        // ① 根据 YAML 配置，为每个分片创建独立连接池
        Map<String, DataSource> dataSourceMap = new HashMap<>();
        dataSourceMap.put("ds_0", createHikariDS(props.getDatasource().get("ds_0")));
        dataSourceMap.put("ds_1", createHikariDS(props.getDatasource().get("ds_1")));

        // ② 创建代理 DataSource，包装所有真实数据源
        return ShardingSphereDataSourceFactory.createDataSource(dataSourceMap, rules, props);
    }
}
```

启动后容器中的 Bean 状态：

```
IoC 容器
├── ShardingSphereDataSource    (@Primary，唯一的 DataSource Bean)
│     └── Map<String, DataSource>
│           ├── "ds_0" → HikariDataSource@1   (db_0 连接池)
│           └── "ds_1" → HikariDataSource@2   (db_1 连接池)
│
├── SqlSessionFactory           (注入了上面的代理数据源)
└── ...
```

> 和苞米豆一样，`@AutoConfigureBefore` 抢在 SpringBoot 默认配置前注册 `@Primary` DataSource，阻止默认 HikariDataSource 创建。

**第 2 步：运行时 — 拦截 SQL，触发五阶段处理**

```
应用发出 SQL: SELECT * FROM user WHERE id = 5
       │
       ▼
ShardingSphereDataSource（代理）
       │
       ▼
① 解析 — SQLParserEngine 解析 SQL 语义
   → 表名: user, 条件: id = 5
       │
       ▼
② 路由 — ShardingRouter 根据分片算法决定目标
   → id=5, 分库算法 5%2=1 → ds_1
   → id=5, 分表算法 5%4=1 → user_1
       │
       ▼
③ 改写 — SQLRewriteEngine 将逻辑表名换成真实表名
   → SELECT * FROM user_1 WHERE id = 5
       │
       ▼
④ 执行 — 在 ds_1.user_1 上执行
       │
       ▼
⑤ 归并 — MergeEngine 合并多表结果后返回
```

对应源码：

```java
// ShardingSpherePreparedStatement（简化）
public class ShardingSpherePreparedStatement {

    @Override
    public ResultSet executeQuery() throws SQLException {
        // ① 解析 SQL → 提取表名、分片键值
        SQLStatementContext context = parseSQL(sql);

        // ② 路由 → 根据分片算法计算目标库和表
        RouteContext routeContext = route(context);
        //   routeContext = { "ds_1.user_1" }

        // ③ 改写 → 逻辑表名 user → 物理表名 user_1
        List<ExecutionUnit> units = rewrite(routeContext);
        //   units = [ ExecutionUnit{ds="ds_1", sql="SELECT * FROM user_1 WHERE id = 5"} ]

        // ④ 执行 → 从 ds_1 的连接池拿连接，执行改写后的 SQL
        List<QueryResult> results = execute(units);

        // ⑤ 归并 → 合并多个分片的结果
        return merge(results, context);
    }
}
```

**第 3 步：执行时 — getConnection 路由到真实分片**

```
Mapper 执行 SQL
    │
    ▼
① SqlSession.selectList()
    │
    ▼
② SimpleExecutor.doQuery()
    │
    ▼
③ BaseExecutor.getConnection()
    │  调用 transaction.getConnection()
    ▼
④ SpringManagedTransaction.getConnection()
    │  调用 DataSourceUtils.getConnection(dataSource)
    │  dataSource 就是 ShardingSphereDataSource
    ▼
⑤ ShardingSphereDataSource.getConnection()
    │
    ├── 5a. 根据②的路由结果，知道要访问 ds_1
    ├── 5b. 从 Map 中取出 ds_1 的 HikariDataSource
    └── 5c. HikariDataSource.getConnection() → ds_1 的物理连接
    │
    ▼
⑥ 用 ds_1 的 Connection 执行改写后的 SQL
```

```java
// 第⑤步：ShardingSphereDataSource 内部路由（简化）
public Connection getConnection(String dsName) throws SQLException {
    DataSource realDS = dataSourceMap.get(dsName);     // HikariDataSource@2
    return realDS.getConnection();                      // ds_1 的物理连接
}
```

> **关键理解**：ShardingSphere 的路由决策发生在 **SQL 执行时**（解析 SQL 内容后），而不是方法入口。这和苞米豆不同——苞米豆在 Service 方法入口就决定了用哪个库，此时 SQL 还没生成。

#### 面试回答：ShardingSphere 分库分表的原理是什么

> 1. 启动时，ShardingSphere 通过 `@AutoConfigureBefore` 抢在 SpringBoot 默认配置前，创建 `ShardingSphereDataSource`（代理数据源）并注册为 `@Primary`，替代真实的单库 DataSource
> 2. 代理数据源内部为每个分片维护独立的连接池（HikariDataSource），通过 Map 管理
> 3. SQL 执行时，`ShardingSpherePreparedStatement` **拦截 SQL**，经过**解析→路由→改写→执行→归并**五个阶段
> 4. 解析阶段用 `SQLParserEngine` 提取表名和分片键值，路由阶段用 `ShardingRouter` 根据分片算法计算目标库和表，改写阶段将逻辑表名替换为物理表名
> 5. 最终从目标分片的连接池拿连接，执行改写后的 SQL；如果是多分片查询，还要归并结果

一句话总结：**代理 DataSource 拦截 SQL，通过解析→路由→改写→执行→归并五阶段，自动将逻辑 SQL 路由到正确的物理分片。**

#### 读写分离

读写分离是分库分表的附带能力，不需要开发者手动指定，框架根据 **SQL 类型**自动路由：

```
SELECT ...   → 自动走 slave
INSERT/UPDATE/DELETE ... → 自动走 master
```

事务内读操作强制走主库，避免主从延迟导致读到旧数据：

```yaml
rules:
  readwrite-splitting:
    data-sources:
      read_write_db:
        type: Static
        props:
          write-data-source-name: ds_master
          read-data-source-names: ds_slave_0
          transactional-read-query-strategy: PRIMARY   # 事务内读走主库
```

#### 分库分表配置示例

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds_0,ds_1
      ds_0:
        url: jdbc:mysql://localhost:3306/db_0
      ds_1:
        url: jdbc:mysql://localhost:3306/db_1

    rules:
      sharding:
        tables:
          user:                                        # 逻辑表名
            actual-data-nodes: ds_0.user_$->{0..3},ds_1.user_$->{0..3}
            database-strategy:                         # 分库策略
              standard:
                sharding-column: id
                sharding-algorithm-name: db-mod
            table-strategy:                            # 分表策略
              standard:
                sharding-column: id
                sharding-algorithm-name: table-mod

        sharding-algorithms:
          db-mod:
            type: MOD                                  # id % 2 → ds_0 或 ds_1
            props:
              sharding-count: 2
          table-mod:
            type: MOD                                  # id % 4 → user_0 ~ user_3
            props:
              sharding-count: 4
```

路由示例：`id=5` → 分库 `5%2=1` → ds_1，分表 `5%4=1` → user_1，实际执行 `ds_1.user_1`。

#### 聚合查询的处理

```
原始 SQL: SELECT COUNT(*) FROM user WHERE age > 18

广播到所有分片执行：
  ds_0.user_0: SELECT COUNT(*) → 10
  ds_0.user_1: SELECT COUNT(*) → 20
  ds_1.user_0: SELECT COUNT(*) → 15
  ds_1.user_1: SELECT COUNT(*) → 25

归并结果: 10 + 20 + 15 + 25 = 70
```

> Druid 连接池不能引 `druid-spring-boot-starter`，会自动注入空 DataSource 与 ShardingSphere 冲突，直接用 `druid` 原生依赖。

### 方案二：苞米豆 dynamic-datasource（AOP 手动切换）

#### 五个角色

| 角色 | 是什么 | 谁提供的 | 职责 |
|------|--------|----------|------|
| **DataSource** | `javax.sql.DataSource` 接口 | JDK | 提供 JDBC Connection |
| **HikariDataSource** | DataSource 的实现类 | HikariCP（连接池） | 管理连接的创建、复用、销毁 |
| **DruidDataSource** | DataSource 的实现类 | Druid（连接池） | 管理连接 + SQL 监控、防火墙、慢查询记录 |
| **DynamicRoutingDataSource** | DataSource 的实现类 | 苞米豆 dynamic-datasource | 运行时选择用哪个真实 DataSource |
| **SqlSessionFactory** | MyBatis 顶层工厂 | MyBatis Plus | 创建 SqlSession，持有 DataSource 和所有 SQL 配置 |

> HikariDataSource 和 DruidDataSource 是**同级**的，都是连接池，二选一。
> 连接池负责管连接，SqlSessionFactory 负编著 SQL，路由数据源负责选库，三者互不干扰。

```
没有多数据源包：
  SqlSessionFactory → HikariDataSource → Connection
  SqlSessionFactory → DruidDataSource  → Connection     （连接池二选一）

有多数据源包：
  SqlSessionFactory → DynamicRoutingDataSource
                         ├── "master" → HikariDataSource → Connection
                         └── "slave"  → DruidDataSource  → Connection    （甚至可以混用）
                 路由层        连接池层（每个数据源独立一个连接池）
```

> MyBatis Plus **没有**任何 DataSource 实现类，它只管 SQL 的生成和执行，不管连接从哪来。

#### 动态数据源原理

整个原理可以拆成三步：**启动时创建 → 运行时标记 → 执行时路由**。

**第 1 步：启动时 — 创建所有数据源，组装成路由数据源**

```java
// 苞米豆 DynamicDataSourceAutoConfiguration（简化）
@Configuration
@AutoConfigureBefore(DataSourceAutoConfiguration.class)  // 抢在 SpringBoot 默认配置之前
public class DynamicDataSourceAutoConfiguration {

    @Bean
    @Primary
    public DynamicDataSource dynamicDataSource(DataSourceProperties properties) {
        DynamicRoutingDataSource routing = new DynamicRoutingDataSource();

        // 遍历 YAML 配置，为每个库创建独立的连接池
        Map<String, DataSource> dataSourceMap = new HashMap<>();
        for (Map.Entry<String, DataSourceProperty> entry : properties.getDatasource().entrySet()) {
            String name = entry.getKey();           // "master", "slave"
            DataSource ds = dataSourceCreator.createDataSource(entry.getValue());
            dataSourceMap.put(name, ds);            // 每个 value 都是 HikariDataSource
        }

        routing.setDefaultTargetDataSource(dataSourceMap.get(properties.getPrimary()));
        routing.setTargetDataSources(dataSourceMap);
        return routing;
    }
}
```

启动后容器中的 Bean 状态：

```
IoC 容器
├── DynamicRoutingDataSource    (@Primary，唯一的 DataSource Bean)
│     └── Map<String, DataSource>
│           ├── "master" → HikariDataSource@1   (master 库连接池)
│           └── "slave"  → HikariDataSource@2   (slave 库连接池)
│
├── SqlSessionFactory           (注入了上面的路由数据源)
└── ...
```

> 为什么 SpringBoot 默认的 HikariDataSource 不会创建？
> 因为苞米豆的 `@AutoConfigureBefore` 先执行，注册了 `@Primary` 的 DataSource。
> SpringBoot 的 `@ConditionalOnMissingBean(DataSource.class)` 条件不满足，直接跳过。

**第 2 步：运行时 — AOP 拦截 @DS 注解，标记当前线程要用哪个库**

```java
// 苞米豆 DynamicDataSourceAnnotationInterceptor（简化）
public class DynamicDataSourceAnnotationInterceptor implements MethodInterceptor {

    @Override
    public Object invoke(MethodInvocation invocation) throws Throwable {
        // 1. 读方法/类上的 @DS 注解，拿到数据源名称
        String dsKey = getDSKey(invocation.getMethod());   // 例如 "slave"

        // 2. 压入 ThreadLocal 栈（用栈支持嵌套调用）
        DynamicDataSourceContextHolder.push(dsKey);

        try {
            // 3. 执行业务方法（此时 ThreadLocal 中已经标记了 "slave"）
            return invocation.proceed();
        } finally {
            // 4. 弹出，恢复上一层的数据源
            DynamicDataSourceContextHolder.poll();
        }
    }
}
```

```java
// DynamicDataSourceContextHolder（简化）
public class DynamicDataSourceContextHolder {

    // 用 Deque（栈）而不是单个 String，支持嵌套 @DS
    private static final ThreadLocal<Deque<String>> LOOKUP_KEY_HOLDER = new ThreadLocal<>();

    public static void push(String dsKey) {
        Deque<String> stack = LOOKUP_KEY_HOLDER.get();
        if (stack == null) {
            stack = new ArrayDeque<>();
            LOOKUP_KEY_HOLDER.set(stack);
        }
        stack.push(dsKey);
    }

    public static String peek() {
        Deque<String> stack = LOOKUP_KEY_HOLDER.get();
        return stack == null || stack.isEmpty() ? "master" : stack.peek();
    }

    public static void poll() {
        Deque<String> stack = LOOKUP_KEY_HOLDER.get();
        if (stack != null) stack.poll();
        if (stack == null || stack.isEmpty()) LOOKUP_KEY_HOLDER.remove();
    }
}
```

对应源码：

```java
// 第⑤步：BaseExecutor（MyBatis 源码）
public abstract class BaseExecutor implements Executor {
    protected Transaction transaction;    // ← 就是 SpringManagedTransaction

    protected Connection getConnection(Log statementLog) throws SQLException {
        Connection connection = transaction.getConnection();  // → 第⑥步
        return connection;
    }
}

// 第⑥步：SpringManagedTransaction（MyBatis-Spring 源码）
public class SpringManagedTransaction implements Transaction {
    private final DataSource dataSource;  // ← DynamicRoutingDataSource

    public Connection getConnection() throws SQLException {
        if (this.connection == null) {
            this.connection = DataSourceUtils.getConnection(this.dataSource);
            //                                      ↑
            //                          调用 DynamicRoutingDataSource.getConnection()
        }
        return this.connection;
    }
}

// 第⑦步：DynamicRoutingDataSource（苞米豆源码，简化）
public class DynamicRoutingDataSource extends AbstractRoutingDataSource {

    private Map<String, DataSource> dataSources;

    public Connection getConnection() throws SQLException {
        String key = DynamicDataSourceContextHolder.peek();   // "slave"
        DataSource ds = dataSources.get(key);                 // HikariDataSource@2
        return ds.getConnection();                            // slave 库的 Connection
    }
}
```

> **关键理解**：数据源的决策发生在 **Service 方法入口**（AOP 拦截时），不是在 Mapper 执行时。Mapper 执行时只是去 ThreadLocal 读结果。

#### 面试回答：动态数据源的原理是什么

> 1. Spring 提供了 `AbstractRoutingDataSource`，定义了路由框架——`getConnection()` 时调 `determineCurrentLookupKey()` 拿一个 key，再从 Map 里取真实 DataSource
> 2. 苞米豆的 `dynamic-datasource` 继承了它，把 YAML 里配置的每个数据源都创建成独立的连接池（HikariDataSource），存入一个 Map
> 3. 运行时通过 **AOP 切面**拦截 `@DS` 注解，把注解里的数据源名称压入 **ThreadLocal**
> 4. 执行 SQL 时，`BaseExecutor` 调 `SpringManagedTransaction.getConnection()`，最终走到路由数据源的 `getConnection()`，从 **ThreadLocal 读 key**，再从 **Map 中取出真实 DataSource**，拿到连接

一句话总结：**AOP 在方法入口把数据源名称存入 ThreadLocal，执行 SQL 时路由数据源从 ThreadLocal 读 key 去 Map 中选出真实连接池。**

#### 怎么切换数据源

**方式 1：@DS 注解（最常用）**

```java
// 方法级（优先级最高）
@DS("slave")
public List<User> listUser() {
    return userMapper.selectList(null);    // 走 slave
}

// 类级（对类内所有方法生效）
@DS("order")
@Service
public class OrderService {
    public List<Order> listOrder() { ... }   // 走 order
    public int addOrder(Order o) { ... }     // 走 order
}
```

**方式 2：Mapper 层加 @DS（也可以）**

```java
@Mapper
public interface UserMapper extends BaseMapper<User> {

    @DS("slave")
    @Select("SELECT * FROM user")
    List<User> selectAll();          // → 走 slave

    @DS("master")
    int insert(User user);           // → 走 master

    // 无注解 → 走 primary 默认数据源
    User selectById(Long id);
}
```

**方式 3：手动编程式切换**

```java
DynamicDataSourceContextHolder.push("slave");
try {
    userMapper.selectList(null);    // 走 slave
} finally {
    DynamicDataSourceContextHolder.poll();    // 必须清除
}
```



**嵌套调用场景**

```java
@DS("master")
public void createOrder() {             // ThreadLocal: [master]
    orderMapper.insert(order);          // 走 master

    stockService.deduct();              // 调用另一个 @DS 方法
}

@DS("slave")
public void deduct() {                  // ThreadLocal: [master, slave]
    stockMapper.selectById(1);          // 走 slave
}                                       // 返回后 poll → [master]

// createOrder() 继续执行，仍然是 master
```

### 两种方案对比

| | ShardingSphere | 苞米豆 dynamic-datasource |
|---|---|---|
| **路由方式** | 解析 SQL 语义自动路由 | AOP + ThreadLocal 手动指定 |
| **路由时机** | SQL 执行时（知道 SQL 内容） | 方法调用前（SQL 还没生成） |
| **分库分表** | 支持（逻辑表 ↔ 物理表自动映射） | 不支持 |
| **读写分离** | 支持（根据 SELECT/DML 自动判断） | 需要手动 @DS 指定 |
| **SQL 改写** | 支持（改表名、补条件） | 不改写，原样执行 |
| **结果归并** | 支持（多表查询合并） | 不需要 |
| **开发者感知** | 不用管，框架全自动 | 要记住每个方法加 @DS |
| **适用场景** | 单表数据量大需要拆分 | 不同业务模块连不同库 |
| **代理 DataSource** | ShardingSphereDataSource | DynamicRoutingDataSource |

**一句话：ShardingSphere 解决的是"一张表太大怎么拆"的问题，苞米豆解决的是"连多个库"的问题。**
