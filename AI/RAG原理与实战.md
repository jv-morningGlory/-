## 一、什么是 RAG

### RAG 到底是什么

**RAG 是一个架构模式（流程），不是一个算法。** 它没有发明任何新技术，只是把已有技术按特定顺序串起来，解决"LLM 回答私有数据问题"这个场景。

```
它不是：一个新算法、一个新模型
它是：  一套组合流程 = Embedding + 向量检索 + Prompt + LLM
```

> 类比：就像微服务架构不是新技术，是服务拆分 + HTTP 通信 + 服务发现的组合。RAG 也是这样，没有哪个环节是 RAG 专属的。

**一句话理解（开发者视角）：**

> 我有个 LLM，想用它回答公司内部问题。但公司资料不能上传给 AI（安全风险），每次更新还得重传（不现实）。
>
> RAG 的思路：**资料留在自己服务器上，用户提问时现搜相关内容，只把搜到的几段文字发给 LLM 参考。** LLM 自始至终没见过你的完整资料库，只看到跟当前问题相关的片段。

```
传统做法（有问题）：公司全部资料 → 上传给 AI → AI 记住 → 回答问题
                         ↑ 不安全，更新需重传

RAG 做法（正确）：   公司资料 → 存本地向量库
                   用户提问 → 搜出相关片段 → 只发片段给 LLM → 回答
                         ↑ 资料不出服务器，更新即时生效
```

### 名字拆解

**RAG = Retrieval-Augmented Generation = 检索增强生成**

| 单词 | 含义 |
|------|------|
| **Retrieval（检索）** | 从知识库中"搜"出跟用户问题相关的内容 |
| **Augmented（增强）** | 把搜到的内容"塞进" Prompt，作为 LLM 的参考资料 |
| **Generation（生成）** | LLM 基于参考资料 + 用户问题，生成最终答案 |

一句话：**检索负责"找资料"，生成负责"写答案"。**

### 它解决了什么问题

**没有 RAG 的时候，LLM 有两个致命缺陷：**

| 问题 | 举例 |
|------|------|
| **知识截止** | 训练数据停在某个时间点，不知道最新信息。比如 GPT-4 的 2023 年 4 月之后的事一概不知 |
| **私有数据盲区** | 不知道你公司的内部制度、产品文档、项目代码。你不可能把公司数据喂给 OpenAI 训练 |

直接问 LLM 内部问题，它要么说"我不知道"，要么**一本正经地编造**（幻觉）。

**有了 RAG 之后：**

```
用户问："入职5年的员工有多少天年假？"

没有 RAG → LLM 瞎猜："可能是5天吧..."（幻觉）
有了 RAG → 系统先搜到员工手册相关段落 → 塞进 Prompt → LLM 照着文档回答："10天"（准确、可溯源）
```

### RAG 本质上干了什么

```
传统方式：用户问题 → LLM → 答案（全靠 LLM 记忆）

RAG 方式：用户问题 → 检索相关文档 → 文档 + 问题 → LLM → 答案（有据可查）
```

> **类比：** RAG 相当于给 LLM 配了一个图书管理员。你问问题，管理员先翻书找到相关章节，把书摊开递给 LLM："这是相关资料，请基于此回答。"LLM 不用背全书，照着面前的资料回答就行。

### 为什么需要 RAG（而不是微调）

| 对比维度 | RAG | 微调（Fine-tuning） |
|---------|-----|-------------------|
| 知识更新 | 更新文档即可，即时生效 | 需要重新训练 |
| 数据安全 | 文档不出你的服务器 | 数据要上传训练 |
| 可解释性 | 能回溯到原文 | 黑盒，不知道怎么得出的 |
| 成本 | 低（只调检索） | 高（GPU 训练） |
| 适用场景 | 内部知识库、实时数据 | 风格定制、特定领域术语 |

> **结论：** 大部分企业内部知识问答场景，RAG 是首选方案。微调是加分项，不是必需品。

## 二、RAG 完整链路 — 数据怎么流

### 链路全景图

```
┌─────────────────────────────────────────────────────────────────┐
│                      离线阶段（文档入库）                          │
│                                                                 │
│  .pdf/.docx/.txt ──→ ①文档加载 ──→ ②切分(Chunk) ──→ ③Embedding  │
│                                                                 │
│              ┌──────────┐                                       │
│              │ 向量数据库 │ ←── ④存储（向量 + 原始文本）             │
│              └────┬─────┘                                       │
│                   │                                             │
├───────────────────┼─────────────────────────────────────────────┤
│                   ▼          在线阶段（用户提问）                    │
│                                                                 │
│  用户提问 ──→ ⑤Embedding(同样模型) ──→ ⑥相似度检索 ──→ Top-K Chunk │
│                                                                 │
│  Top-K Chunk + 用户问题 ──→ ⑦拼装Prompt ──→ ⑧LLM生成 ──→ 最终答案 │
└─────────────────────────────────────────────────────────────────┘
```

### 各环节干了什么

| 环节 | 做了什么 | 你该关注什么 |
|------|---------|-------------|
| ① 文档加载 | 读取 PDF/Word/HTML/TXT，提取纯文本 | 不同格式提取质量不同，PDF 表格容易乱 |
| ② 切分 | 把长文档切成小段（Chunk） | **RAG 效果的核心变量**，见第三章 |
| ③ Embedding | 每段文本转成向量 | 和查询必须用同一个模型 |
| ④ 存储 | 向量 + 原始文本一起存 | 最终给 LLM 看的是原始文本，向量只用来搜 |
| ⑤ 查询向量化 | 用户问题也转成向量 | 和入库用同一个 Embedding 模型 |
| ⑥ 相似度检索 | 余弦相似度找 Top-K | K 太小缺信息，K 太大噪声多 |
| ⑦ 拼装 Prompt | 把搜到的文本塞进 Prompt 模板 | 模板设计影响回答质量 |
| ⑧ LLM 生成 | 基于提供的文档内容生成答案 | 防止幻觉：要求 LLM 引用原文 |

> **关键认知：** RAG 的本质是把"检索"和"生成"拆开。检索负责找到相关材料，生成负责用材料写出好答案。两个环节各司其职。

### Top-K 是什么

K 是一个数字，表示"从向量库里取相似度最高的前 K 个 Chunk"。

```
用户提问 → 转成向量 → 和库里所有 Chunk 算余弦相似度 → 按相似度从高到低排序 → 取前 K 个

比如 K=5：
  Chunk-12  相似度 0.92  ← 第1名
  Chunk-45  相似度 0.87  ← 第2名
  Chunk-3   相似度 0.81  ← 第3名   ──→ 这5个发给 LLM
  Chunk-78  相似度 0.76  ← 第4名
  Chunk-21  相似度 0.71  ← 第5名
  ────────────────────────────── 第6名以后丢弃，不进 Prompt
  Chunk-56  相似度 0.48
  ...
```

| K 值 | 效果 | 问题 |
|------|------|------|
| 太小（如 K=1） | 只给 LLM 最相关的一段 | 可能缺上下文，回答不完整 |
| 太大（如 K=20） | 信息多，覆盖面广 | Prompt 太长、噪声多、稀释重点 |
| 经验值 | **K=3~8 起步** | 根据实际效果调整 |

## 三、Chunk 切分策略 — 为什么搜不准往往是切的问题

### 一个直观例子

**先理解 Chunk 是什么：**

Chunk（文本块）= 把一篇长文档按一定规则切成 N 个小段，每一段就是一个 Chunk。

```
原文（一篇 5000 字文档）
  → 切成每段 500 字 →
    Chunk-1（第 1~500 字）
    Chunk-2（第 501~1000 字）
    Chunk-3（第 1001~1500 字）
    ...
```

> 为什么要切？因为你不能把整篇 5000 字的文档塞进 Prompt（太长、噪声多、费 token），也不能把整篇文档转成向量（一个 Embedding 只会生成一个向量，整篇太长语义会稀释）。切成小段后，每段单独转向量，检索时就能精准找到相关的那一小段。

现在看一个具体例子。假设公司制度文档里有一段：

```
第五条 年假规定
1. 入职满1年的员工享有5天年假
2. 入职满5年的员工享有10天年假
3. 入职满10年的员工享有15天年假
4. 年假需提前一周申请，经直属领导审批
```

如果切分在第 2 条和第 3 条之间断开了：

- 用户搜"10 年员工年假"，第 3 条和第 4 条可能分在**两个 Chunk** 里
- 检索返回了第 3 条的 Chunk，但第 4 条"需提前一周申请"丢失了
- LLM 只看到天数，看不到申请要求 → **回答不完整**

这就是切分质量直接影响 RAG 效果的原因。

### 三种切分策略对比

| 策略 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **固定长度** | 每 N 字切一段 | 简单，好控制 | 可能在句子中间断开 | 通用场景，最常用 |
| **按语义** | 按段落/句子/标题切 | 每段语义完整 | 长度不均，有的太长 | 结构化文档（Markdown） |
| **滑动窗口（固定长度 + 重叠）** | 每 N 字切一段，相邻 Chunk 有部分重叠 | 兼顾语义完整性和上下文 | 存储多 20%~30% | 通用场景，**最常用** |

> **滑动窗口就是"固定长度 + 重叠"**，是目前最常用的方案。重叠确保关键信息不会因切分边界而断裂：
>
> ```
> Chunk 大小：500 字，重叠 50 字
>
> ...第3条年假...│[===Chunk 1 (500字)===]...第4条申请...
>                 │   [===Chunk 2 (500字)===]...
>                 │← 重叠 50 字 →│
> ```

### 参数调优指南

| 参数 | 太小 | 太大 | 经验值 |
|------|------|------|--------|
| Chunk 大小 | 检索精度高，但缺上下文 | 上下文完整，但噪声多 | 300~800 字起步 |
| 重叠大小 | 边界断裂风险高 | 存储冗余大 | Chunk 大小的 10%~20% |
| Top-K | LLM 缺信息 | Prompt 太长，稀释重点 | 3~8 条起步 |

> **思路和对后端调优一样：** 没有银弹，先跑起来，看效果，再调。效果不好先怀疑切分，其次怀疑检索 K 值。
