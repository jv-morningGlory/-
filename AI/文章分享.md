## 1.1 Context Engineering — 真正的护城河

**核心论点**：模型能力趋同，真正拉开差距的是 **Context Engineering** 能力。

Context Engineering 不是"把代码扔给 AI"，而是一套系统化方法：
- **识别**关键信息
- **结构化组织**项目级和模块级上下文
- 在有限 token 窗口内**精准传递**最相关信息
- 随项目发展**持续优化**上下文

> 关键洞察：它无法被模型升级替代，只能通过持续实践积累。不是依赖更大上下文窗口，而是掌握正确协作方式。

## 子文章一：TRAE 基于渐进式索引实现业务上下文管理

**来源**：手册内嵌文章 + [甲子光年报道](https://zhuanlan.zhihu.com/p/2015405976048640443)

### 核心问题

企业代码中，许多关键业务语义、约束和决策依据分散在代码之外。如果简单粗暴地向 Agent 输入所有文档 → **上下文过载**。

### 解决方案：渐进式索引（Progressive Indexing）

借鉴 Anthropic Skills 的 **渐进式披露（Progressive Disclosure）** 思想：

| 策略 | 说明 |
|------|------|
| **按需加载** | 不一次性加载全部文档，根据任务需要精准定位 |
| **分层读取** | 先提供轻量级"目录"，让 AI 按需读取详细信息 |
| **分层管理** | 驻留区（核心信息）→ 工作区（当前任务）→ 冷存区（索引/摘要）|

### 实战验证

TRAE 团队对 32 个业务 Bug 进行对比测试：
- **启用 Skills（含业务 Context）**：修复 32/32，修复率 **100%**
- **不使用 Skills**：修复 19/32，成功率 **不足 60%**

> 结论：业务 Context 是提升 Loop 自动修复率的决定性因素。Bug 本身也可作为 Context 迭代的 Benchmark。

## 子文章二：用第一性原理拆解 Agentic Coding（上）

**来源**：[知乎专栏 - 小夏（TRAE 技术专家）](https://zhuanlan.zhihu.com/p/1992996507633354122)

### 1. LLM 的本质

LLM 工作方式：**逐个预测下一个 token（自回归生成）**

由此带来的本质特征：
- **没有独立于输出的"思考"过程**：边说边想，所以 CoT（Chain-of-Thought）有效
- **上下文就是全部记忆**：窗口之外的内容对模型不存在
- **生成具有概率性**：同样输入可能产生不同输出

### 2. Coding Agent 的五大固有问题

| 问题 | 表现 |
|------|------|
| **局部最优** | 一步步"续写" ≠ 全局规划，多文件重构容易接口不一致 |
| **偏差滚雪球** | 早期误读需求 → 后续每步都在错误世界观里自洽 |
| **无法回头修改** | 擅长"写新文件"，不擅长精确局部编辑，倾向整体重写 |
| **约束满足能力有限** | "看起来合理"的实现，边界条件、并发、错误处理易出错 |
| **单线程思考** | 方案选择早早押注一个方向，缺少系统性对比 |

### 3. Attention 机制与上下文约束

- Attention 是"动态聚光灯"，对不同位置分配不同权重
- **注意力是稀疏的**：大部分位置权重接近零
- **计算复杂度 O(n²)**：上下文长度翻倍，计算量变四倍

> 关键数据：有效上下文远小于标称值。200K 模型在超过 80K-100K 后出现明显性能退化。

### 4. 强化学习（RL）的作用

预训练教会模型"说"，RL 教会模型"做"：
- 尝试 → 反馈 → 调整的循环
- 不定义"正确步骤"，只定义"什么算成功"
- 模型自主探索通往成功的路径

### 5. Coding Agent 实现架构

**API 结构**：`system`（行为准则）→ `user`（输入）→ `assistant`（回复）→ `tool`（工具结果）

**Agent Loop 核心循环**：调用模型 → 检查是否需要工具 → 执行工具 → 结果返回模型 → 重复直到最终响应

**Prompt Caching 最佳实践**：
```
稳定内容（system prompt + tool 定义）→ 相对稳定（项目 context）→ 动态（对话历史 + 当前输入）
```

### 6. 常见问题与解决方案

| 问题 | 解决方案 |
|------|---------|
| **会话间失忆** | 结构化任务追踪 + 会话结束生成状态摘要 |
| **上下文窗口耗尽** | Observation Masking（遮蔽旧观察）+ LLM Summarization（摘要压缩）|
| **有效上下文 < 标称值** | 实际只能有效利用 10-15%，超过 20% 急剧恶化 |
| **Dumb Zone** | 上下文中间 40-60% 区域模型能力下降 |
| **新发现的任务被丢弃** | 外部工具实时记录发现的问题 |
| **过早宣告完成** | 将计划保存在上下文外的固定位置 |

## 子文章三：用第一性原理拆解 Agentic Coding（下）

**来源**：[火山引擎开发者社区 - 小夏（TRAE 技术专家）](https://developer.volcengine.com/articles/7598410716190375962)

### 实操最佳实践

#### 1. 短对话优于长对话

> **最重要的一条实践。**

- 每个对话只做一件事，只包含完成这件事所需的上下文
- 对话超过 80K-100K token 时，考虑开始新对话
- 拆分对话 = 拆分任务，这是软件工程的永恒最佳实践

**以对话为单位组织工作**：
```
功能：用户登录后的会话管理
  ├── [对话 1] 调研现有代码结构
  ├── [对话 2] 实现基础功能
  ├── [对话 3] 添加错误处理
  ├── [对话 4] 编写测试
  ├── [对话 5] 代码审查
  └── [对话 6] 清理和重构
```

对话间共享上下文：引用前次结论 / Git 状态 / 项目文档（AGENTS.md）/ #mention 文件

#### 2. 编写有效的项目配置文件

配置文件 = **每次会话的入职培训文档**，应回答三个问题：
- **WHAT**：技术栈、项目结构、各模块职责
- **WHY**：设计决策背景
- **HOW**：运行、测试、验证方式

> 关键原则：**少即是多**。控制在 300 行以内，越短越好。使用渐进式披露策略。

**不要让 Agent 做 Linter 的工作**：用真正的 linter/formatter，LLM 做格式检查既慢又贵。

#### 3. Compounding Engineering（复利工程）

> 普通 AI 工程让你今天更高效，复利工程让你之后的每一天都更高效。

核心理念：每次 bug 修复 → 记录到项目文档 → 成为永久教训 → Agent 自动应用

实践方式：
- 将经验沉淀到 `AGENTS.md`（代码风格、已知陷阱、成功模式）
- 让 bug 修复产生长期价值（lint 规则、测试、文档）
- 从代码审查中提取可复用模式
- 建立可复用的工作流程

#### 4. 对人难的事，对 AI 也难

所有提升开发者体验的工作，对 AI 同样有价值：
- **更好的文档**：减少 AI 在代码库中反复搜索的时间
- **更清晰的代码结构**：清晰命名、单一职责、显式依赖
- **更快的反馈循环**：秒级单元测试 >> 10 分钟全量测试

> 投资回报是双倍的：既帮助人类，也帮助 AI。

#### 5. 为 AI 专门设计

有时需要**专门为 AI 设计工具和接口**：
- API 设计：提供便捷函数 + 底层函数两套，引导 Agent 优先用便捷函数
- CLI 输出：用 `--json` 等结构化格式
- 用工程约束"驯服" Agent（git hooks 拦截 `--no-verify`）
- 错误信息：给 AI 明确的错误代码、原因和解决方案

#### 6. 刻意练习

AI 就像乐器——投入刻意练习才能精通：
- 创造干净的实验环境（个人项目）
- 从失败中提取教训
- 观察和模仿高手的实践
- 建立肌肉记忆
- 持续投入时间

### 未来人才画像：Expert Generalist（专家型通才）

核心特征：
- **跨领域发现模式**：识别不同技术领域的共同基础
- **第一性原理思维**：快速抓住本质
- **机械同理心**：对底层特性有直觉性理解
- **全局视野**：看到完整图景

> LLM 让 Expert Generalist 价值倍增——像钢铁侠的 Jarvis 外骨骼。
