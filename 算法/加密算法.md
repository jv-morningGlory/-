# 加密算法

> 解决同一个问题的三种工具：**怎么让数据不被人看懂（加密）**、**怎么证明数据没被改过（摘要）**。它们各自只能干一件事，真正的安全系统是把它们组合起来用。

---

## 三类算法各管什么

很多人把"加密"和"摘要"混为一谈，其实它们的根本目的不同：

| 类型 | 核心问题 | 能否还原原文 | 有没有密钥 | 典型代表 |
|------|---------|-------------|-----------|---------|
| **对称加密** | 别人偷看我的数据 | ✅ 能（用同一个密钥解密） | 1 把（加解密共用） | AES、DES |
| **非对称加密** | 密钥怎么安全传给对方 | ✅ 能（公钥加密、私钥解密） | 2 把（公钥 + 私钥） | RSA、ECC |
| **摘要算法**（Hash） | 数据有没有被篡改 | ❌ 不能（单向不可逆） | 无密钥 | MD5、SHA-256 |

> **一句话区分**：能解密回原文的才叫"加密"；摘要算法是"指纹"，不可逆，根本不算加密。

## 实战：Spring Security 存密码（摘要算法）

密码**只能哈希、不能加密**——加密可逆，密钥泄露则全员密码裸奔；哈希不可逆，拖库也算不回明文。Spring Security 默认用 **BCrypt**。

**密文长这样（固定 60 字符）**：

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

| 段 | 含义 |
|----|------|
| `2a` / `10` | 算法版本 / cost 成本因子 |
| 22 位 | **盐（salt）**，随机生成 |
| 31 位 | 哈希结果 |

> 盐直接拼在密文里，**不用单独建 salt 字段**。BCrypt 自带随机盐 + 可调 cost，防彩虹表、扛暴力破解。

**登录时怎么匹配**（密码没有"解密"，全程靠重算 + 比对）：

```
用户输入账号 + 明文密码
        ↓
按账号查数据库，取出密文 $2a$10$盐+哈希
        ↓
从密文里提取【盐】和【cost】
        ↓
用这个盐 + cost，对【输入的明文】重新哈希一遍
        ↓
新算的哈希  vs  数据库里那 31 位哈希
        ↓  相等 → 密码正确；不等 → 拒绝
```

> 关键：数据库密码**永远不解密**，而是把输入的明文用同样的盐重算一遍，比对两个哈希值。

## 实战：一对多数据下发加密（数据提供方）

你是中央数据系统 A，给 B/C/D 多个子系统提供接口，**返回数据加密，只有请求的那个子统能解开**。

> 光上 HTTPS 不够（网关/日志仍打印明文），敏感数据要在**内容层再加密**。每个子系统**独立密钥对**：隔离、可吊销、别共用。

**密钥归属**：子系统分配 `appId`，**自己生成 RSA 密钥对**——私钥自己留、绝不外传，公钥上传给 A。A 存 `appId → 公钥`。

**A 给 B 传数据时，密钥怎么流转**：

```
【B 的密钥】私钥自己留，公钥交给 A

A 发数据：
  ① 临时生成 AES 密钥（用完即扔）
  ② AES 密钥  → 用【B 的公钥】加密   （只有 B 的私钥能解）
  ③ 业务数据  → 用【AES 密钥】加密
  ④ 发送：加密的 AES 密钥 + 加密的数据

B 收数据：
  ⑤ 加密的 AES 密钥 → 用【B 的私钥】解 → 拿到 AES 密钥
  ⑥ 加密的数据     → 用【AES 密钥】解 → 拿到明文
```

> 为什么绕这一圈：AES 快但密钥不能明文传（会被截获），RSA 能安全传密钥但太慢。所以 **用 RSA 递 AES 钥匙、用 AES 锁数据**——非对称管"递钥匙"，对称管"锁数据"。

## 实战：数字签名验签（防篡改 + 防伪造 + 防否认）

非对称加密的第二个用途：**私钥签名、公钥验签**，管"可信"（前面加密管"保密"）。

> 纠误区：签名不是"私钥加密整个内容"，而是**私钥加密【内容的摘要】**（内容太大、RSA 有长度限制）。这步把「摘要」和「非对称」串起来。

**密钥归属**：B 自己生成 RSA 密钥对——私钥自己留、绝不外传，公钥交给 A。

```
B 签名（发数据）：
  ① 对原始数据算摘要：digest = SHA256(数据)
  ② 用【B 的私钥】加密摘要 → 得到 sign
  ③ 发送：原始数据 + sign

A 验签（收数据）：
  ④ 对【收到的数据】重算摘要：digest' = SHA256(数据)   ← 必须自己算，不能信 B 传的
  ⑤ 用【B 的公钥】解密 sign → 还原 B 算的 digest
  ⑥ 比对 digest' == digest → 相等则验签通过
```

> A 必须**自己拿收到的内容重算摘要**，不能信 B 传来的——否则中间人把数据和摘要一起改就破防。

**防三件事**：篡改（摘要对不上）、伪造（无私钥签不出）、否认（只有私钥持有者能签 → **不可抵赖**）。

| 维度 | 加密（保密） | 签名（验签） |
|------|------------|-------------|
| 公钥 | **加密**数据 | **验签**（解密签名） |
| 私钥 | **解密**数据 | **签名**（加密摘要） |

> 口诀：私钥永远干核心动作（解密/签名），公钥的活随场景变（锁/验）。落地见支付宝、微信支付的商户私钥签名 + 平台验签。
