# 秒杀系统并发排坑实战

> 一份"中级开发写得出来、自测能过、一上量就崩"的抢购代码,逐个排查并修复。**正向设计**见《如何设计一个秒杀系统》,本篇是**反向排坑**——10 个生产事故级 bug,每个都对应《并发安全判断指南》里的一条原理。

## 部署假设

> 很多 bug 离开这个假设就看不出来:本案例假设 **3 台 Tomcat 节点 + 单 Redis + MySQL + Kafka**。凡是"单机状态"在多节点下都会失效。

## 原始问题代码（满身是坑）

> 先看全貌：下面这份就是排坑对象——分层完整、自测能过，但 10 个生产事故级 bug 藏在各处。注释里的 `← #N` 对应后文逐个分析。

```java
// ===================== SeckillController =====================
@RestController
@RequestMapping("/seckill")
public class SeckillController {
    @Autowired private SeckillService seckillService;

    @PostMapping("/rush")
    public Result<OrderVO> rush(@RequestBody @Valid SeckillRequest req) {
        if (!RateLimiter.tryAcquire()) { return Result.fail("系统繁忙"); }   // ← #10
        return Result.ok(seckillService.doSeckill(req.getUserId(), req.getGoodsId()));
    }
}

// ===================== RateLimiter =====================
@Component
public class RateLimiter {
    private static final AtomicInteger COUNTER = new AtomicInteger(0);   // ← #10 每节点独立计数
    private static final int MAX = 1000;
    public static boolean tryAcquire() {
        return COUNTER.incrementAndGet() <= MAX;
    }
}

// ===================== SeckillService（重灾区）=====================
@Service
@Slf4j
public class SeckillService {
    @Autowired private StringRedisTemplate redis;
    @Autowired private SeckillMapper seckillMapper;
    @Autowired private KafkaTemplate<String, String> kafka;
    @Autowired private DistributedLock distributedLock;

    private final Map<String, Integer> localStockCache = new HashMap<>();   // ← #1 本地缓存

    private static final String STOCK_KEY  = "seckill:stock:%s";
    private static final String BOUGHT_KEY = "seckill:bought:%s:%s";

    @Transactional(rollbackFor = Exception.class)   // ← #5 方法级事务包了 Redis/Kafka
    public OrderVO doSeckill(String userId, String goodsId) {
        String stockKey  = String.format(STOCK_KEY,  goodsId);
        String boughtKey = String.format(BOUGHT_KEY, userId, goodsId);

        Integer local = localStockCache.get(goodsId);                // ← #1 本地缓存挡一层
        if (local != null && local <= 0) { throw new BizException("已售罄"); }

        Boolean first = redis.opsForValue().setIfAbsent(boughtKey, "1");   // ← #8 无过期
        if (Boolean.FALSE.equals(first)) { throw new BizException("您已经抢过了"); }

        // ← #3 get → 判断 → decrement 三步非原子
        String stockStr = redis.opsForValue().get(stockKey);
        int stock = stockStr == null ? 0 : Integer.parseInt(stockStr);
        if (stock <= 0) { redis.delete(boughtKey); throw new BizException("已售罄"); }
        redis.opsForValue().decrement(stockKey);
        if (local != null) { localStockCache.put(goodsId, local - 1); }

        // ← #6 相关：DB 失败时直接抛异常，Redis 已扣库存没有任何补偿 → 丢库存
        OrderVO order = deductDbStock(userId, goodsId);

        kafka.send("seckill-order", JSON.toJSONString(               // ← #5 事务内发消息
                new CreateOrderMsg(userId, goodsId, order.getOrderId())));
        return order;
    }

    private synchronized OrderVO deductDbStock(String userId, String goodsId) {   // ← #2 JVM 锁
        StockDO stockDO = seckillMapper.selectByGoodsId(goodsId);
        if (stockDO.getStock() <= 0) { throw new BizException("已售罄"); }
        seckillMapper.decrStock(goodsId);                            // ← #4 SQL 无 stock>0
        OrderDO order = new OrderDO(IdUtil.nextId(), userId, goodsId, 0);
        seckillMapper.insertOrder(order);
        return OrderVO.of(order.getOrderId());
    }
}

// ===================== DistributedLock =====================
@Component
public class DistributedLock {
    @Autowired private StringRedisTemplate redis;

    public boolean tryLock(String key, String value, long expireSec) {
        return Boolean.TRUE.equals(
            redis.opsForValue().setIfAbsent(key, value, expireSec, TimeUnit.SECONDS));
    }

    public void unlock(String key, String value) {                   // ← #9 get→delete 非原子
        String cur = redis.opsForValue().get(key);
        if (value.equals(cur)) { redis.delete(key); }
    }
}

// ===================== OrderMessageConsumer =====================
@Component
@Slf4j
public class OrderMessageConsumer {
    @Autowired private SeckillMapper seckillMapper;

    @KafkaListener(topics = "seckill-order", groupId = "seckill-group")
    public void onMessage(String msg) {                              // ← #7 无幂等
        CreateOrderMsg m = JSON.parseObject(msg, CreateOrderMsg.class);
        seckillMapper.updateOrderStatus(m.getUserId(), m.getGoodsId(), 1);
    }
}

// ===================== SeckillMapper =====================
@Mapper
public interface SeckillMapper {
    @Update("UPDATE seckill_stock SET stock = stock - 1 WHERE goods_id = #{goodsId}")   // ← #4
    int decrStock(String goodsId);

    @Select("SELECT * FROM seckill_stock WHERE goods_id = #{goodsId}")
    StockDO selectByGoodsId(String goodsId);
}
```

> 对照说明：`#6`（补偿失败）在原始代码里没有显式逻辑——它体现为"DB 失败时 Redis 库存**没有任何补偿就丢了**"，是在修复 #5 时引入补偿、进而发现"补偿本身也不可靠"才暴露的。

## 病根总览:10 个问题,四类病

| 类别 | 问题 | 破坏特性 | 一句话后果 |
|------|------|---------|-----------|
| **库存超卖** | #1 本地库存缓存 | 可见性(分布式) | 多节点各存一份 → 集群超卖 |
| | #2 `synchronized` 扣 DB | 原子性(分布式失效) | JVM 锁锁不住别的进程 |
| | #3 Redis 三步扣减非原子 | 原子性·复合操作 | 两线程同读余量 → 扣成负数 |
| | #4 扣库存 SQL 无条件 | DB 兜底失效 | 库存扣成负数 |
| **数据一致性** | #5 `@Transactional` 包远程调用 | 事务一致性 | 回滚时 Redis/Kafka 不回滚 |
| | #6 补偿也可能失败 | 最终一致 | 即时补偿失败 → 丢库存 |
| | #7 消费者无幂等 | 消息重复消费 | 重复消费 → 重复建单 |
| **资源/可靠性** | #8 防重标记无过期 | 资源泄漏 | key 永驻,撑爆 Redis |
| | #9 锁释放非原子 | 原子性·复合操作 | 锁被误删,等于没锁 |
| | #10 本地限流 | 分布式失效 | 集群放行 N×MAX |

> **主线**:笔记里的**单机三性(原子/可见/有序)**,在分布式抢购里升级成四件事——**本地状态 → 分布式可见性**、**复合操作 → 原子性下沉**、**跨系统一致 → 最终一致**、**资源管理 → 设过期 + 原子释放**。

## 一、库存超卖类

### 问题 1:本地库存缓存(集群超卖)

> **根因**:多节点各自维护 `localStockCache`,A 节点扣减后只更新自己,B/C 看不到 → 继续放行。这是《并发安全判断指南》"可见性"的分布式放大版;附带 `HashMap` 非线程安全。
> **后果**:集群超卖(最严重)。

```java
// ❌ 多节点各存一份,彼此不可见
private final Map<String, Integer> localStockCache = new HashMap<>();
Integer local = localStockCache.get(goodsId);
if (local != null && local <= 0) { throw new BizException("已售罄"); }

// ✅ 删掉本地缓存,库存判断交给 Redis(中心化单点)
```

> 库存这种"会变、要准、大家共抢"的强一致状态,绝不能用本地缓存。要省 Redis 调用,正解是**本地限流削峰**(少放请求进来),不是缓存库存值。

---

### 问题 2:`synchronized` 锁不住分布式

> **根因**:`synchronized` 是 JVM 内锁,只锁当前进程。3 节点各锁各的,跨进程完全失效;还给人"我加锁了"的错觉,比不加更危险。
> **后果**:DB 层超卖。

```java
// ❌ JVM 锁锁不住别的进程
private synchronized OrderVO deductDbStock(String userId, String goodsId) {
    seckillMapper.decrStock(goodsId);   // 乐观扣减
    seckillMapper.insertOrder(...);
}

// ✅ 去 synchronized,改乐观锁,让 DB 行锁保证跨节点原子
private OrderVO deductDbStock(String userId, String goodsId) {
    int affected = seckillMapper.decrStockSafe(goodsId);   // 带 stock>0 的原子 UPDATE
    if (affected == 0) { throw new BizException("已售罄"); }
    seckillMapper.insertOrder(...);
}
```

> 把"查 + 判断 + 扣"三步合并成一条带条件的原子 UPDATE,这就是**数据库版 CAS**——和单机 `AtomicInteger` 的 CAS 思想一脉相承,且天然跨节点。

---

### 问题 3:Redis 三步扣减非原子

> **根因**:`get → 判断 > 0 → decrement` 是 check-then-act 复合操作,三步之间能被插入。两线程同时读到 stock=1,都通过判断,都扣减 → 扣成负数。
> **后果**:Redis 层超卖。

```java
// ❌ 三步非原子
String stockStr = redis.opsForValue().get(stockKey);
if (Integer.parseInt(stockStr) <= 0) { redis.delete(boughtKey); throw new BizException("已售罄"); }
redis.opsForValue().decrement(stockKey);

// ✅ Lua 脚本:三步压成一条原子命令(Redis 单线程执行 Lua 期间不打断)
private static final DefaultRedisScript<Long> DEDUCT_SCRIPT = new DefaultRedisScript<>(
    "local s = tonumber(redis.call('get', KEYS[1])) " +
    "if (not s) or s <= 0 then return 0 end " +
    "redis.call('decr', KEYS[1]) return 1", Long.class);

Long ok = redis.execute(DEDUCT_SCRIPT, Collections.singletonList(stockKey));
if (ok == null || ok == 0) { redis.delete(boughtKey); throw new BizException("已售罄"); }
```

> 为什么不能光用 `decrement`?因为 `decr` 不带条件判断,stock=0 时还会继续减成负数。必须把"判断 + 扣"在 Lua 里合一。Lua 脚本要短,只碰少数 key——脚本跑久了会阻塞整个 Redis。

---

### 问题 4:扣库存 SQL 无条件兜底

> **根因**:`UPDATE ... SET stock=stock-1 WHERE goods_id=?` 没有 `stock>0` 条件,最后一道防线漏了。
> **后果**:即使前面防线全崩,库存也会扣成负数。
> **修复**:与问题 2 同一处改动。

```sql
-- ❌ 无条件,兜不住
UPDATE seckill_stock SET stock = stock - 1 WHERE goods_id = #{goodsId}

-- ✅ 带 stock > 0 条件,DB 行锁保证原子且跨节点
UPDATE seckill_stock SET stock = stock - 1 WHERE goods_id = #{goodsId} AND stock > 0
```

> 至此库存线闭环:Lua 保证 Redis 不超卖,乐观锁保证 DB 不扣成负数。无论前面怎么乱,DB 这一行不会负。

## 二、数据一致性类

### 问题 5:`@Transactional` 包了远程调用

> **根因**:`@Transactional` 只回滚 DB 操作,Redis/Kafka 不在管辖范围。Redis 扣了库存 → DB 抛异常回滚 → Redis 不回滚 = 永久丢库存;Kafka 在事务提交前发出 → 消费者查不到未提交的订单(可见性问题)。附带长事务持有 DB 连接/锁,性能雪崩。
> **后果**:Redis 与 DB 不一致,且性能崩溃。

```java
// ❌ 方法级事务包了 Redis/Kafka
@Transactional(rollbackFor = Exception.class)
public OrderVO doSeckill(...) {
    redis.execute(DEDUCT_SCRIPT, ...);        // Redis
    OrderVO order = deductDbStock(...);       // DB
    kafka.send("seckill-order", ...);         // Kafka
}

// ✅ 去方法级事务,远程调用移出,DB 操作用编程式事务精确包裹
public OrderVO doSeckill(...) {
    // Redis(事务外):防重 + 预扣
    ...
    // DB(编程式事务,只包 DB 操作)
    OrderVO order = transactionTemplate.execute(status -> {
        int affected = seckillMapper.decrStockSafe(goodsId);
        if (affected == 0) { throw new BizException("已售罄"); }
        seckillMapper.insertOrder(...);
        return OrderVO.of(...);
    });
    // Kafka(事务提交后发,保证消费者查得到已提交的订单)
    kafka.send("seckill-order", ...);
    return order;
}
```

> 铁律:**事务里只放 DB 操作,远程调用全部移出**。若改用"@Transactional 标注独立方法"的写法,同类自调用会让事务失效——要么 `TransactionTemplate`,要么拆到另一个 Bean。

---

### 问题 6:补偿也可能失败 → 本地消息表

> **根因**:DB 失败时即时补偿 `redis.increment` 自己也可能失败(Redis 挂/网络抖),try-catch 救不了所有场景。
> **后果**:库存丢失。
> **修复**:把即时补偿升级为**可靠的本地消息表**(事务性发件箱模式),失败靠 worker 重试兜底。

```java
// ❌ 即时补偿也可能失败
catch (RuntimeException e) {
    redis.opsForValue().increment(stockKey);   // 这步失败 → 库存还是丢
    throw e;
}

// ✅ 写补偿消息(独立小事务),交给 worker 可靠重试;顺手做一次即时补偿
catch (RuntimeException e) {
    rollbackTx.execute(status -> {
        msgMapper.insert(new LocalMessage(IdUtil.nextId(), "ROLLBACK_STOCK", stockKey, "{}", ...));
        msgMapper.insert(new LocalMessage(IdUtil.nextId(), "CLEAR_BOUGHT", boughtKey, "{}", ...));
        return null;
    });
    try { redis.opsForValue().increment(stockKey); redis.delete(boughtKey); } catch (Exception ignore) {}
    throw e;
}
```

> 完整机制(正向建单发消息 + 反向回滚库存 + worker 重试 + 幂等 + 对账兜底)见《事务性发件箱模式》。即时补偿管 99%,本地消息表 + 对账兜剩下 1%。

---

### 问题 7:消费者无幂等

> **根因**:消息投递是 at-least-once(至少一次),重复消费不可避免(崩溃重启、生产重试、ack 丢失)。消费端幂等是**业务自己**的责任,且只能业务保证。
> **后果**:重复建单/重复扣库存/重复通知。

```java
// ❌ 无幂等
seckillMapper.updateOrderStatus(m.getUserId(), m.getGoodsId(), 1);

// ❌ 应用层 check-then-act 也不行(并发下两个线程都查到"不存在",都插入)
if (orderMapper.selectByOrderId(id) == null) { orderMapper.insert(...); }

// ✅ DB 唯一索引 + INSERT IGNORE,把去重交给 DB 原子完成
int affected = orderMapper.insertIgnore(new Order(m.getOrderId(), m.getUserId(), m.getGoodsId(), 1));
if (affected == 0) { return; }   // 0 = 唯一键冲突 = 重复消息,跳过
stockMapper.decrStockSafe(m.getGoodsId());
```

> **判据**:幂等是否生效,看"重复执行后 DB 的影响行数/状态",用 `affected==0` 判重复。去重键必须是全局唯一且稳定的(`orderId`/`msgId`),**绝不能用 `userId+goodsId`**——用户合法地可以买多次。

## 三、资源/可靠性类

### 问题 8:防重标记无过期

> **根因**:`setIfAbsent(boughtKey, "1")` 无过期重载,key 永驻。抢成功的那批用户 key 永久占着。
> **后果**:Redis 内存泄漏(100w 用户 = 100w 永不过期 key)、老标记挡新活动、违背"活动级临时标记"本意。

```java
// ❌ 无过期
redis.opsForValue().setIfAbsent(boughtKey, "1");

// ❌ 两步设过期也不行:中间崩溃 → key 永驻(复合操作非原子)
redis.opsForValue().setIfAbsent(boughtKey, "1");
redis.expire(boughtKey, 24, TimeUnit.HOURS);

// ✅ 原子带过期(对应 SET ... NX EX,一条命令)
redis.opsForValue().setIfAbsent(boughtKey, "1", 24, TimeUnit.HOURS);
```

> 过期时间要覆盖"活动期 + 支付超时窗口"。Redis 防重是快路径,DB 唯一索引 `(user_id, goods_id, activity_id)` 才是兜底——要带场次维度,同用户不同场次可合法各抢一次。

---

### 问题 9:分布式锁释放非原子

> **根因**:`get → 判断 → delete` 两次网络往返,中间间隙里锁可能易主。`get` 时锁还是自己的,`delete` 时锁已是别人的 → 误删别人的锁。
> **后果**:锁被误删,临界区没保护,等于没锁。

```java
// ❌ get 与 delete 间隙锁易主 → 误删
public void unlock(String key, String value) {
    String cur = redis.opsForValue().get(key);
    if (value.equals(cur)) { redis.delete(key); }
}

// ✅ Lua 原子释放(value 必须是 UUID,否则比对无意义)
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT = new DefaultRedisScript<>(
    "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end",
    Long.class);
public void unlock(String key, String value) {
    redis.execute(UNLOCK_SCRIPT, Collections.singletonList(key), value);
}
```

> 自实现锁还有更多坑(业务没完锁就过期需看门狗续期、主从切换丢锁需 Redlock)。**生产直接用 Redisson**:`RLock` 自带 Lua 原子释放 + 看门狗 + 可重入。

---

### 问题 10:本地限流分布式失效

> **根因**:每节点一个独立 `AtomicInteger`,各算各的 MAX。3 节点 = 集群放行 3×MAX。和 #1/#2 同源——单机状态分布式失效。附带固定窗口算法有临界突发。
> **后果**:限流形同虚设,集群被打爆。

```java
// ❌ 每节点独立计数
private static final AtomicInteger COUNTER = new AtomicInteger(0);

// ✅ Redis + Lua 全局计数(incr 和 expire 必须原子,否则 key 永驻,见 #8)
private static final DefaultRedisScript<Long> RATE_SCRIPT = new DefaultRedisScript<>(
    "local c = redis.call('incr', KEYS[1]) " +
    "if c == 1 then redis.call('expire', KEYS[1], ARGV[2]) end " +
    "if c > tonumber(ARGV[1]) then return 0 else return 1 end", Long.class);
public boolean tryAcquire(String key, int max, int windowSec) {
    Long ok = redis.execute(RATE_SCRIPT, Collections.singletonList(key),
            String.valueOf(max), String.valueOf(windowSec));
    return Long.valueOf(1L).equals(ok);
}
```

> 最优架构是**放网关层**(Nginx `limit_req` / Spring Cloud Gateway + Redis / Sentinel),请求还没进应用就挡。本地限流不是没用,它适合保护单机;集群 QPS 上限必须全局。生产常是"网关全局限流 + 应用本地兜底"组合。

## 一条主线:单机三性 → 分布式升级

| 笔记里的单机原理 | 在本案例升级成 | 对应问题 |
|----------------|--------------|---------|
| 可见性:`volatile`/`synchronized` 让别的线程看见 | 别的**节点**是另一个 JVM → 用**中心化组件**(Redis/MySQL) | #1 #2 #10 |
| 原子性:`count++` 复合操作非原子 | check-then-act 在 Redis/DB 同样非原子 → **原子性下沉**(Lua/唯一键/条件 UPDATE) | #3 #7 #9 |
| 有序性/一致性:单机事务 | 跨系统无法一个事务 → **最终一致**(本地消息表/对账) | #5 #6 |
| — | 资源管理:**设过期要原子、释放要原子、限流要全局** | #8 #9 #10 |

> **处置优先级**(见《并发安全判断指南》第四节):能不共享就不共享 > `volatile`/CAS > 原子性下沉 > 加锁。本案例几乎每个修复都在践行"**能用基础设施原子解决,就别在应用层加锁**"。

## 面试答法

> 问:秒杀系统有哪些并发和一致性坑?
>
> 答:分四类。
>
> **库存超卖**最致命:本地缓存库存会因多节点不可见而超卖,得删掉以 Redis 为准;`synchronized` 锁不住分布式,扣库存要用乐观锁 `UPDATE WHERE stock>0`;Redis 侧的"读余量-判断-扣减"非原子,要用 Lua 压成一条命令。
>
> **数据一致性**:Redis 预扣和 DB 落库不能放在一个 `@Transactional` 里(远程调用不回滚),要把事务收紧到只包 DB;补偿失败要用**本地消息表**(事务性发件箱)保证最终一致;消费者必须**幂等**,靠 DB 唯一索引 + `INSERT IGNORE`,不能用应用层 if 判断。
>
> **资源可靠性**:防重标记要原子带过期、分布式锁释放要用 Lua 原子比对删除、限流要全局不能本地计数。
>
> 核心一句话:**单机的原子/可见/有序,在分布式下分别变成"中心化组件、原子性下沉、最终一致",能用 Redis/MySQL 的原子能力解决,就别在应用层加锁。**

| 关键词 | 记忆点 |
|--------|--------|
| 超卖防线 | Redis Lua + DB 乐观锁(`stock>0`) |
| 一致性 | 拆事务 + 本地消息表 + 消费幂等 |
| 幂等判据 | DB 唯一索引,`affected==0` 判重复 |
| 原子性下沉 | Lua 脚本是 Redis 侧的标准武器 |
| 生产锁 | 直接用 Redisson |
