# 事务性发件箱模式（Transactional Outbox）

> **一句话**：DB 操作 + 发消息（MQ）这种"一个要落库、一个要外发"的组合,无法用一个本地事务保证一致。**发件箱模式**的解法——把"要发的消息"和业务数据**在同一个 DB 事务里落库**,再**异步可靠地投递**到 MQ,保证**最终一致**。

> 📌 归类:**分布式架构模式**(不是 GoF 设计模式)。解决的是"跨系统/跨进程一致性",不是"类怎么设计"。

---

## 一、它解决什么问题

「**双写不一致**」:业务需要同时"写 DB"和"发 MQ",但两者无法放进同一个事务。

| 时序 | 失败点 | 后果 |
|------|--------|------|
| 先写 DB ✅ → 发 MQ ❌ | MQ 发送失败(网络/宕机) | DB 有数据、下游收不到消息 → **数据丢失** |
| 先发 MQ ✅ → 写 DB ❌ | DB 事务回滚 | 下游收到消息处理了、DB 却没数据 → **脏数据** |
| 写 DB ✅ → 发 MQ ✅ → 但消息在"事务提交前"已发 | 消费者秒级读到消息、查 DB 事务还没提交 | **查不到**(可见性问题) |

> 根因:**DB 事务只能回滚 DB 操作,回滚不了 MQ**。只要两者不在同一个原子边界内,就有一致性缝隙。

---

## 二、核心思想

> 类比现实**发件箱**:你**写信**(业务操作)时,顺手把信副本放进桌上的**发件箱**——这两步是一个动作,要么都做要么都不做(**同事务**)。然后**邮差**(worker / CDC)定期从发件箱取信**寄出去**——寄信是异步的、寄失败就再寄,但信绝不会丢,因为副本已经在发件箱里了。

**关键转化**:把"**不可靠的远程动作(发 MQ)**"降级为"**可靠的本地记录(写表) + 可重试的异步投递**"。

- DB 落库是可靠的(ACID)→ "记录要做的事"不会丢
- 异步 worker 不断重试 → 动作最终一定执行
- 从"**即时同步一致**"退到"**最终一致**"——分布式系统里强一致太贵,最终一致是主流

---

## 三、两种落地方式

| 方式 | 怎么做 | 优缺点 |
|------|--------|--------|
| **轮询式**(本地消息表) | 建 outbox 表,业务事务里写消息;定时任务扫表 → 发 MQ | 简单、零中间件依赖;有轮询延迟(秒级)、扫表有压力、worker 要自己写重试 |
| **CDC 式** | **Debezium / Canal 监听 DB binlog**,outbox 表一有新记录,变更直接推 MQ | 近实时(毫秒级)、对业务零侵入;要维护 CDC 组件 |

> 两者用**同一张 outbox 表**,差别只在"谁来把表里的消息搬出去":轮询式靠定时任务,CDC 式靠 binlog 监听。

---

## 四、轮询式实现（最常用）

### 1. outbox 表

```sql
CREATE TABLE outbox_message (
    id          BIGINT PRIMARY KEY,
    biz_type    VARCHAR(32),   -- 事件类型: ORDER_CREATED / STOCK_ROLLBACK
    biz_key     VARCHAR(64),   -- 业务键: orderId / stockKey
    payload     VARCHAR(512),  -- 消息内容(JSON)
    status      TINYINT,       -- 0=待处理 1=已投递 2=放弃(转人工)
    retry_count INT DEFAULT 0,
    next_retry  DATETIME,      -- 下次重试时间(指数退避,防疯狂重试)
    create_time DATETIME
);
```

### 2. 业务事务里,顺手写消息(同事务 = 原子)

```java
@Transactional
public void createOrder(OrderDTO dto) {
    orderMapper.insert(order);                    // 业务数据
    outboxMapper.insert(new OutboxMessage(         // ✅ 同事务写消息:DB 提交则消息一定在,回滚则一起回滚
        IdUtil.nextId(), "ORDER_CREATED", order.getId().toString(),
        JSON.toJSONString(order), 0, 0, LocalDateTime.now(), LocalDateTime.now()));
}
```

> ⚠️ 消息**必须和业务写在同一个 `@Transactional` 里**,不能用独立事务/事务外插入——否则又回到双写不一致。

### 3. 异步 worker:扫描 + 投递 + 重试

```java
@Scheduled(fixedDelay = 1000)
public void publish() {
    List<OutboxMessage> todos = outboxMapper.selectPending();   // status=0 AND next_retry<=NOW()
    for (OutboxMessage m : todos) {
        try {
            kafka.send(m.getBizType(), m.getPayload());         // 投递(Kafka 为例,RocketMQ 同理)
            outboxMapper.markDelivered(m.getId());              // ✅ 成功才标记,保证至少投递一次
        } catch (Exception e) {
            outboxMapper.incrRetry(m.getId());                  // retry_count+1,next_retry 退避
            if (m.getRetryCount() >= MAX_RETRY) outboxMapper.markFailed(m.getId());  // 告警转人工
        }
    }
}
```

### 4. 幂等是前提

> worker 是"**至少一次**"投递:投递成功但还没 `markDelivered` 就崩溃 → 重启后会**重复投递**。所以**消费方必须幂等**(唯一键 + `ON DUPLICATE KEY`、状态机、去重表),否则重复消息导致重复处理。

## 五、CDC 式（进阶）

```
应用 ──写业务+outbox表──▶ MySQL ──binlog──▶ Debezium ──▶ Kafka ──▶ 下游
                                          (监听变更,近实时)
```

- **Debezium** 把 outbox 表的新增当作 binlog 事件,直接发到 Kafka
- 业务代码**零侵入**:只管正常写表,不用写 worker、不用 `@Scheduled`
- 投递延迟从秒级降到毫秒级,且天然不漏(binlog 顺序可靠)
- 代价:要部署维护 Debezium / Canal 组件

## 六、适用场景

| 适用 ✅ | 不适用 ❌ |
|--------|----------|
| 订单创建后通知下游 | 强一致要求(如跨行转账,需 Saga/TCC) |
| 支付成功后发货 | 实时性要求极高(最终一致有秒级延迟) |
| 秒杀:Redis 预扣 → DB 落库 + 异步下单的最终一致 | |
| 用户注册后发欢迎邮件/短信 | |

> 📌 在秒杀里,发件箱模式补的是「**Redis 扣了库存、发 MQ 或消费者失败时,如何保证 Redis 与 DB 最终一致**」这一环。参见《如何设计一个秒杀系统》第四节。

## 面试答法

> 问:DB 写完还要发消息通知下游,怎么保证不丢?
>
> 答:用**事务性发件箱模式**。DB 操作和"要发的消息"在**同一个本地事务**里落库——这样要么都成功要么都回滚,消息绝不会丢。然后用一个**异步 worker 定时扫消息表**,把消息投递到 MQ,失败就重试、成功才标记完成,保证**至少投递一次**。消费方做**幂等**处理重复。本质是把"不可靠的发消息"降级成"可靠的落库 + 可重试的投递",从强一致退到**最终一致**。进阶可以用 **Debezium 监听 binlog** 代替轮询,近实时、业务零侵入。

| 要点 | 一句话 |
|------|--------|
| 解决 | DB + MQ 双写不一致 |
| 核心 | 同事务落库 + 异步可靠投递 |
| 一致性级别 | 最终一致 |
| 前提 | 消费方幂等 |
| 进阶 | CDC(Debezium / Canal) |
