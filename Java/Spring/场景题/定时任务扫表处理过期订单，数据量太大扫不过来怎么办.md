# 定时任务扫表处理过期订单，数据量太大扫不过来怎么办

> **核心思路**：从"全表扫"变成"只扫需要处理的数据"。

---

## 一、加索引，缩小扫描范围（最低成本）

在状态 + 过期时间上加**联合索引**，定时任务只扫需要处理的行：

```sql
ALTER TABLE orders ADD INDEX idx_status_expire (status, expire_time);
```

```sql
-- 走索引，不需要全表扫描
SELECT * FROM orders
WHERE status = '待支付' AND expire_time < NOW()
LIMIT 1000;
```

```java
// 伪代码：最简单版本
@Scheduled(cron = "0 */5 * * * ?")   // 每 5 分钟
public void closeExpiredOrders() {
    List<Order> orders = mapper.selectByStatusAndExpire("待支付", new Date());
    for (Order o : orders) {
        o.setStatus("已关闭");
        mapper.updateById(o);
    }
}
```

---

## 二、延迟队列（最常用的解耦方案）

不用扫表，下单时把订单丢进延迟队列，到期自动处理：

| 方案 | 实现方式 | 适用场景 |
|------|---------|---------|
| **Redis ZSet** | score = 过期时间戳，定时取 `score < now` 的数据 | 中小规模，不想引入 MQ |
| **RocketMQ 延迟消息** | `message.setDelayTimeLevel(18)`（18 = 30分钟） | 已有 RocketMQ 的项目 |
| **Redisson 延迟队列** | `RDelayedQueue`，基于 Redis 实现 | 用了 Redisson 的项目 |

### Redis ZSet 示例

```java
// 下单时：丢进延迟队列
redis.zadd("order:expire:queue", expireTime, orderId);

// 定时任务：每 5 秒取到期的
Set<String> ids = redis.zrangeByScore("order:expire:queue", 0, now());
for (String id : ids) {
    closeOrder(id);
    redis.zrem("order:expire:queue", id);
}
```

## 三、分页 / 游标 + 多机并行

| 策略 | 做法 |
|------|------|
| **游标法** | 记录上次扫到哪，每次只扫 `LIMIT 1000`，处理完继续 |
| **多机分片** | 按 `user_id % N` 分片，每台机器只扫自己的分片，互不冲突 |

```sql
-- 游标法：每次只取一批，避免一次性扫全表
SELECT * FROM orders
WHERE status = 'WAIT_PAY' AND expire_time < NOW() AND id > #{lastId}
ORDER BY id LIMIT 1000;
```

```java
// 伪代码：游标法
long lastId = 0;
while (true) {
    List<Order> list = mapper.selectExpired(lastId, 1000);
    if (list.isEmpty()) break;
    for (Order o : list) {
        closeOrder(o);
        lastId = o.getId();
    }
}
```

## 四、根本解法：延迟队列 + 兜底扫表

这是最成熟的组合：

> **主链路**：下单 → 延迟队列（30 分钟后触发）→ 检查 & 关单  
> **兜底**：凌晨低峰期全表扫一次，处理延迟队列遗漏的数据（如 MQ 故障）

| 方案 | 适用阶段 | 优点 | 缺点 |
|------|---------|------|------|
| **延迟队列** | 主力（99.9%） | 实时、精准、不扫表 | 依赖 MQ / Redis 可靠性 |
| **兜底扫表** | 兜底（0.1%） | 简单可靠，不漏数据 | 有延迟，低峰期执行 |

```java
// 伪代码：延迟队列 + 兜底扫表
// 主链路——下单时
void onOrderCreated(Order order) {
    mq.sendDelay("order-timeout", order.getId(), 30 * 60 * 1000); // 30分钟
}

// 主链路——消费者
void onTimeoutMsg(String orderId) {
    Order order = mapper.selectById(orderId);
    if (order.isUnpaid()) {
        closeOrder(order);
    }
}

// 兜底——每天凌晨 3 点扫一次
@Scheduled(cron = "0 0 3 * * ?")
void compensate() {
    List<Order> list = mapper.selectExpired(new Date());
    for (Order o : list) {
        closeOrder(o);
    }
}
```

> **一句话总结**：不要扫全表，用 **索引 + 延迟队列** 替代"定时扫全量"，延迟队列做主力、扫表做兜底。

## 五、本质提炼

四种方案剥开看，底层就两个方向：

| 本质思路 | 解决的问题 | 具体手段 |
|---------|-----------|---------|
| **找得快** | 怎么低成本地找出待处理数据 | 联合索引、状态字段、分区表、ES 检索 |
| **处理得动** | 怎么在有限的资源下处理完 | 延迟队列、MQ 削峰、分片并行、异步化 |

**1. 精准定位，而非全量扫描**

加索引、加状态字段，本质就是给数据打上**可快速检索的标识**，让"找到待处理数据"这个动作从 O(n) 全表扫变成 O(log n) 索引查。

**2. 改变处理时机，而非硬扛**

用延迟队列 / MQ，本质是把"即时批量处理"变成"分散逐条处理"——不是在定时任务那几秒硬扛百万数据，而是让它们在三十分钟的时间窗口里自然流过来。

> 几乎所有"数据量太大处理不过来"的问题，拆解到最后都是这两个方向。跳出具体方案看到这一层，比记住配置重要。
