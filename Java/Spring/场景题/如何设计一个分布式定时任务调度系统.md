# 如何设计一个分布式定时任务调度系统

> **面试回答**：我们项目用的是 XXL-JOB。配任务时最关键的三个配置——调度类型、运行模式、路由策略。

---

## 一、三个核心配置

### 1.1 调度类型 —— 决定"什么时候触发"

| 调度类型 | 含义 | 实际业务场景 |
|---------|------|------------|
| **CRON** | 到点触发 | ① 每天凌晨 2 点扫表关闭过期订单 ② 每天早 8 点生成前一日运营报表 ③ 每月 1 号生成账单 |
| **固定速度** | 固定间隔，不管上次跑没跑完就发 | ① 每 30 秒上报服务心跳到注册中心 ② 每 5 秒检查 Redis 集群节点是否存活 |
| **NONE** | 不自动触发，只通过 API 或控制台手动执行 | ① 用户下单后通过代码调 API 延时关单 ② 审批通过后调 API 触发后续流程 |

> ⚠️ XXL-JOB 只有这三类调度类型。所谓的"API 触发"不是独立类型，而是所有任务都支持的通用能力——任意任务都能通过 `POST /xxl-job-admin/run` 手动触发。

```
CRON：       |←── 每天 2:00 ──→|←── 每天 2:00 ──→|
固定速度：    |← 30s →|← 30s →|← 30s →|      （不管上次跑没跑完，到点就发）
NONE：       完全不自动，全靠手动/API 触发
```

> **选型口诀**：定时扫表用 CRON，心跳上报用固定速度，事件驱动设 NONE + 代码调 API。

**如何模拟固定延迟？—— FIX_RATE + Redis 锁**

XXL-JOB 没有固定延迟，但可以用 FIX_RATE 高频触发 + Redis 分布式锁实现：

```
FIX_RATE 每 5s 触发 →
  机器A 尝试拿锁 → 拿到 → 执行（耗时 4s）
  机器A 尝试拿锁 → 拿到 → 执行（耗时 8s，慢）
  机器A 尝试拿锁 → 上一次还没跑完，锁没释放 → 拿不到，跳过
  机器A 尝试拿锁 → 拿到 → 继续下一轮...
```

```java
@XxlJob("pollMessageJob")
public void execute() {
    // 拿锁，设过期时间 5 分钟（防止死锁）
    boolean locked = redis.setIfAbsent("job:poll:lock", "1", 5, TimeUnit.MINUTES);
    if (!locked) {
        XxlJobHelper.handleSuccess("上一轮还未结束，跳过");
        return;  // 拿不到锁说明上一次还在跑，直接跳过
    }
    try {
        // 干活
        List<Message> list = messageService.pollBatch(100);
        for (Message msg : list) {
            sendToMQ(msg);
        }
        XxlJobHelper.handleSuccess("处理完成: " + list.size());
    } finally {
        redis.delete("job:poll:lock");
    }
}
```

> 优点：不叠任务、不会死锁（锁设了超时）、实现简单。唯一注意锁的过期时间要比任务最长执行时间还长。

### 1.2 运行模式 —— 决定"代码写在哪里"

| 运行模式 | 代码位置 | 说明 |
|---------|---------|------|
| **BEAN** | 业务应用的 `@XxlJob` 方法中 | **最常用**，代码在应用里，类型安全、方便调试 |
| **GLUE(Java)** | 控制台在线写，存到 MySQL | 可以热更新，不用重启，适合小逻辑 |
| **GLUE(Shell)** | 控制台写 Shell 脚本 | 运维脚本，如清理日志、备份文件 |
| **GLUE(Python)** | 控制台写 Python 脚本 | 数据处理、报表脚本 |
| **GLUE(PHP/Node.js/PowerShell)** | 同上 | 跨语言场景 |

```
BEAN 模式（99% 的场景）：
  业务应用 ─── @XxlJob 方法 ─── 调度中心远程触发

GLUE 模式（1% 的场景）：
  调度中心 ─── 在线编辑代码 ─── 下发到执行器执行
  好处：不重启就能改代码，适合临时脚本
```

> **选型建议**：正常业务用 BEAN；需要频繁改、不想发版的零散逻辑用 GLUE。大部分项目只用 BEAN。

### 1.3 路由策略 —— 决定"哪个执行器来跑"

调度中心触发任务后，在多个执行器中选一台 / 全部来执行。

---

**分两派：选一台跑 vs 全都要跑**

| 类型 | 路由策略 | 行为 | 适用场景 |
|------|---------|------|---------|
| 选一台 | **第一个** | 固定打第一台注册的机器 | 单机任务，只在一台跑 |
| 选一台 | **最后一个** | 固定打最后一台注册的机器 | 同上，基本不用 |
| 选一台 | **轮询** | A→B→C→A 轮流来 | 简单负载均衡 |
| 选一台 | **随机** | 随机挑一台 | 跟轮询差不多 |
| 选一台 | **一致性哈希** | 同 userId 的请求粘在同一台 | 需要粘性场景 |
| 选一台 | **故障转移** | 正常打 A，A 挂了自动切 B | **最常用**，高可用 |
| 选一台 | **忙碌转移** | 机器线程满了就换一台，都不空闲就排队 | 防止单机积压 |
| 全都要 | **分片广播** | 同时发所有机器，各处理各的分片 | 海量数据，N 倍速 |

---

**逐个细说：**

**① 故障转移（最常用）** —— 只要有一台活着，任务就不会漏。

```
正常： 调度中心 → 机器A 执行
故障： 调度中心 → 机器A（挂了）→ 自动切机器B → 执行
恢复： 调度中心 → 机器A 执行（切回来）
```

> 绝大多数定时任务都用这个，因为只要不重复跑就行。

**② 轮询** —— 均匀分配，但不会故障转移。

```
3 台机器，触发 6 次：
机器A 执行第1、4次
机器B 执行第2、5次
机器C 执行第3、6次
```

> 场景：每台机器的任务互相独立，不需要高可用。

**③ 忙碌转移 vs 故障转移**：

```
故障转移：机器A活着就死磕，挂了才换
忙碌转移：机器A线程满了就换B，都不空闲才排队
```

> 批量任务场景用忙碌转移更合理——哪台空闲用哪台。

**④ 分片广播（面试重点）** —— 其他路由都是"选一台"，这个是"全都要"。

```
任务：关闭 100w 条过期订单
路由选"分片广播"，3 台机器

机器 0：MOD(id, 3) = 0 → 处理 33.3w 条
机器 1：MOD(id, 3) = 1 → 处理 33.3w 条
机器 2：MOD(id, 3) = 2 → 处理 33.4w 条

耗时：原 30 分钟 → 3 台 10 分钟搞定，互不重复
```

```java
// 分片广播时，代码里这样拿分片参数
@XxlJob("batchProcessJob")
public void execute() {
    ShardingUtil.ShardingVO shard = ShardingUtil.getShardingVO();
    int index = shard.getIndex();   // 当前分片 0/1/2
    int total = shard.getTotal();   // 总分片 3

    // 只处理自己的分片
    List<Order> orders = mapper.selectShard(index, total);
    for (Order o : orders) {
        process(o);
    }
}
```

```sql
-- 对应的 SQL：每台机器只查自己的数据
SELECT * FROM orders
WHERE status = 'WAIT_PAY'
  AND MOD(id, #{total}) = #{index}
LIMIT 1000;
```

**⑤ 一致性哈希** —— 谁用谁知道。

```
场景：需要把同一个 user 的任务粘在一台机器上处理
user_100 → 哈希 → 机器B
下次 user_100 又来 → 哈希 → 还是机器B
```

> 很少用，除非业务真的需要粘性。

---

**场景速查：**

| 你的场景 | 选哪个 |
|---------|--------|
| 清理过期订单，3 台机器加一起才能跑完 | **分片广播** |
| 每天凌晨发报表，只在一台跑就行 | **故障转移** |
| 批量发短信，哪台空闲用哪台 | **忙碌转移** |
| 3 台机器均匀分配，跑不同的数据 | **轮询** |

> **一句话**：只要一台跑用故障转移，要 N 倍速用分片广播，其他基本不用管。

---

### 1.4 调度过期策略 —— 决定"调度中心挂了，任务错过了怎么办"

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **忽略** | 错过了就错过了，跳过不补 | 心跳、监控检查等错过一次无所谓 |
| **立即执行一次** | 调度中心恢复后立即补跑一次 | 报表、对账等最好不要漏的任务 |

```
场景：调度中心挂了，凌晨 2 点的任务没触发生效

忽略策略：   2:00 任务 ──×── 跳过 ──→ 等明天 2:00
立即执行：   2:00 任务 ──×── 4:00 恢复 → 立即补跑一次 → 下次还是 2:00
```

> 大部分任务用"忽略"就够了，重要任务用"立即执行一次"。

---

### 1.5 阻塞处理策略 —— 决定"上次还没跑完，新的一轮又触发了怎么办"

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **单机串行** | 排队，等上次跑完再跑下一次 | 不能丢的批处理任务 |
| **丢弃后续** | 直接扔掉新的触发 | 固定速度 + Redis 锁的兜底策略 |
| **覆盖之前** | 终止上一次正在跑的，跑新的 | 数据会丢失，慎用 |

```
场景：任务 FIX_RATE 每 5s 触发一次，但执行一次要 8s

单机串行：   [===8s===] [===8s===]        一次一次排队跑
丢弃后续：   [===8s===] ×× ×× [===8s===]  上次没跑完，新的跳过
覆盖之前：   [==3s==×] [===8s===]         终止上一次，跑新的
```

```java
// 丢弃策略 + Redis 锁 = 最佳搭档（和 1.1 节末尾的 Redis 锁方案一致）
// 阻塞策略设"丢弃后续"，锁拿不到的直接跳过
@XxlJob("pollMessageJob")
public void execute() {
    if (!redis.setIfAbsent("job:poll:lock", "1", 5, TimeUnit.MINUTES)) {
        return; // 丢弃
    }
    try { doWork(); } finally { redis.delete("job:poll:lock"); }
}
```

| 常见搭配 | 阻塞策略 | 说明 |
|---------|---------|------|
| FIX_RATE + Redis 锁 | 丢弃后续 | 拿不到锁跳过，拿到就执行 |
| **FIX_RATE + 单机串行** | 单机串行 | **效果 ≈ 固定延迟**（跑完自动接下一棒，不叠任务） |
| 海量分片任务 | 单机串行 | 排队慢慢跑，不丢数据 |

> **FIX_RATE + 单机串行 ≈ 固定延迟**：FIX_RATE 到点触发，单机串行保证本次没跑完就排队，跑完立马接下一棒。和固定延迟的唯一区别是中间没有主动空闲等待，但防堆积效果一致。

## 二、面试答法

> 我们项目用的是 XXL-JOB。架构上调度中心管触发，执行器嵌在业务应用里干活，引入依赖加个 `@XxlJob` 就能用。
>
> 配任务时主要设三个东西：**调度类型**一般用 CRON 定时触发；**运行模式**用 BEAN，代码写在自己应用里；**路由策略**看场景——简单任务用"故障转移"或"轮询"，海量数据扫表用"分片广播"，N 台机器同时跑，每台取 `MOD(id, N)` 的分片，性能翻 N 倍还不重复。
