# 如何设计一个秒杀系统

> **秒杀的本质矛盾**：瞬间极高并发（100w 人抢 1000 件商品）vs 有限资源（DB 扛不住、库存不能超卖）。核心思路——**逐层拦截，尽量让请求在到达 DB 之前就被拦住**。

---

## 全链路架构

```
用户 → CDN/静态化 → 网关限流 → 验证码/防刷 → Redis 库存扣减 → MQ 下单 → DB 支付
  │        │           │           │            │              │          │
  │   ① 静态化     ② 限流      ③ 防刷      ④ 库存预减    ⑤ 异步下单  ⑥ 异步支付
  │   挡大部分     拒之门外    挡脚本      Redis原子扣   削峰填谷    最终一致
```

---

## 一、前端层：静态化 + 防提前暴露

| 手段 | 做什么 |
|------|--------|
| **页面静态化** | 秒杀页面提前生成纯 HTML，推送到 CDN，不经过应用服务器 |
| **秒杀地址隐藏** | 秒杀开始前 URL 是加密的动态地址（带随机 token），活动开始前接口不返回 |
> **注意：这不是短链接。** 短链接前端随时能拿到，目的只是压缩长度。秒杀 token 是**临时凭证**——活动开始前请求接口会返回 404，到点才下发 token。前端最终当然能拿到，但拿到时活动已经开始，脚本来不及反应。安全靠的是"不到点不给"，不是"不给你看"。
| **按钮防重复** | 点击后置灰 + 倒计时，防止用户狂点 |

```html
<!-- 秒杀按钮：点击后立即禁用，防止重复提交 -->
<button onclick="seckill()" id="btn">秒杀</button>
<script>
function seckill() {
    document.getElementById('btn').disabled = true;
    fetch('/seckill/submit?token=xxx', { method: 'POST' });
}
</script>
```

## 二、网关层：限流 + 验证码

> 100w 人抢 1000 件，99.9% 的人注定抢不到。尽早拒绝，别让他们打到应用层。

| 手段 | 做什么 |
|------|--------|
| **网关限流** | 整体 QPS 控制在系统能扛的范围，超出的直接拒绝 |
| **验证码** | 秒杀按钮点击后弹验证码，拦脚本 + 分散请求（用户输入需要时间） |
| **IP/用户限流** | 同一 IP 或用户 1 秒内只能请求 1 次 |

## 三、库存扣减：Redis + Lua 原子操作（最关键的一步）

> **绝对不能在 DB 层扣库存**——MySQL 行锁在秒杀场景下会成为瓶颈，几千个事务排队等锁。

```lua
-- 扣减库存 Lua 脚本（Redis 原子执行，不会超卖）
local key = KEYS[1]                     -- "seckill:stock:12345"
local limitKey = KEYS[2]                -- "seckill:bought:12345"
local userId = ARGV[1]

-- 1. 检查是否已抢过（防重复）
if redis.call('SISMEMBER', limitKey, userId) == 1 then
    return -1   -- 已抢过
end

-- 2. 检查库存
local stock = tonumber(redis.call('GET', key))
if stock == nil or stock <= 0 then
    return 0    -- 库存不足
end

-- 3. 扣减库存
redis.call('DECR', key)

-- 4. 标记已抢
redis.call('SADD', limitKey, userId)

return 1        -- 抢到
```

```java
// Java 调用
public SeckillResult seckill(String productId, String userId) {
    List<String> keys = Arrays.asList(
            "seckill:stock:" + productId,
            "seckill:bought:" + productId);
    
    Long result = redisTemplate.execute(
            SECKILL_SCRIPT, keys, userId);
    
    if (result == -1) return SeckillResult.fail("已抢过");
    if (result == 0)  return SeckillResult.fail("已售罄");
    
    // 4. 扣减成功后，发 MQ 异步创建订单
    mqTemplate.send("seckill-order", new SeckillMsg(userId, productId));
    return SeckillResult.ok("抢到，下单中");
}
```

**为什么用 Redis 而不是 DB：**

| | Redis | MySQL |
|---|---|---|
| 单机 QPS | 10w+ | 几千 |
| 原子操作 | Lua 脚本天然原子 | 行锁排队等锁 |
| 超卖风险 | ✅ Lua 保证不会 | 需要额外手段 |

## 四、下单：MQ 异步削峰

> Redis 扣完库存后，真正的下单逻辑（校验、生成订单、扣 DB 库存）全部异步做。

```
Redis 扣减成功 → 发 MQ → 消费者慢慢处理 → 生成订单 → 扣 DB 库存
   ↑ 毫秒级返回用户              ↑ 按 2000/s 消费，不冲击 DB
```

```java
// 消费者
@RocketMQMessageListener(topic = "seckill-order")
public class SeckillOrderConsumer implements RocketMQListener<SeckillMsg> {
    @Override
    public void onMessage(SeckillMsg msg) {
        // 1. DB 最终扣库存（和 Redis 对上账）
        int rows = db.update("UPDATE product SET stock = stock - 1 " +
                "WHERE id = ? AND stock > 0", msg.getProductId());
        if (rows == 0) { /* 数据不一致，告警 */ }
        
        // 2. 生成订单
        Order order = new Order(msg.getUserId(), msg.getProductId());
        orderMapper.insert(order);
        
        // 3. 通知用户抢单成功
        notifyService.push(msg.getUserId(), "恭喜抢到！请尽快支付");
    }
}
```

## 五、支付：延时关单回库存

| 手段 | 做什么 |
|------|--------|
| **支付超时** | 15 分钟内未支付自动取消，库存回退 |
| **延时关单** | 下单后发延时消息，15 分钟后检查是否已支付，未支付则回库存 |
| **支付回调幂等** | 防止重复回调导致重复扣款 |

```java
// 下单后发延时消息，15 分钟后关单
@PostMapping("/order/create")
public Result createOrder(OrderDTO dto) {
    Order order = orderService.create(dto);
    
    // 发延时消息：15 分钟后检查
    Message msg = new Message("order-timeout", order.getId().getBytes());
    msg.setDelayTimeLevel(16);  // 16 = 30min，实际按业务定
    rocketMQTemplate.send(msg);
    
    return Result.ok(order);
}
```

## 六、秒杀前准备

| 准备 | 做什么 |
|------|--------|
| **库存预热** | 活动开始前，商品库存加载到 Redis |
| **热点数据预热** | 商品信息、用户信息提前缓存 |
| **机器扩容** | 提前加机器，活动后缩容 |
| **压测** | 提前模拟秒杀流量，验证系统容量 |

## 面试答法（一条链路说清楚）

> 问：秒杀系统怎么设计？
>
> 答：核心思路是逐层拦截，尽可能让请求不到 DB 就结束。
>
> 第一层前端：页面静态化放 CDN + 秒杀地址加密，脚本拿不到。
>
> 第二层网关：限流 + 验证码，把 99% 请求拦在应用外。
>
> 第三层扣库存（最关键）：Redis + Lua 脚本原子扣库存，Redis 单机 10w QPS，不用等 MySQL 行锁。
>
> 第四层下单：扣成功发 MQ 异步下单，消费者按自己节奏慢慢写 DB，削峰填谷。
>
> 第五层支付：下单后 15 分钟未支付自动关单回库存。
>
> 核心一句话：库存扣减靠 Redis，下单靠 MQ 异步化，绝不让 MySQL 扛并发。

| 环节 | 核心技术 | 一句话 |
|------|---------|--------|
| 前端 | CDN 静态化 | 页面不走服务端 |
| 网关 | 限流 + 验证码 | 99% 拦在门外 |
| **库存** | **Redis + Lua 原子扣** | **最核心，绝不用 DB** |
| 下单 | MQ 异步 | 削峰填谷 |
| 支付 | 延迟关单 | 15 分钟不回就还库存 |
