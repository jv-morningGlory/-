# 如何设计一个短链接生成系统

> **什么是短链接**：把 `https://www.example.com/product/detail?id=12345&utm_source=wechat` 变成 `https://t.cn/A6xYz3Q`。用户访问短链接 → 服务端查原始长链接 → 302 重定向。

**为什么需要：**
- 长链接在短信/微博里占空间、难看、甚至被截断
- 短链接可以做点击统计（谁点了、多少次、什么设备）
- 链接被举报后可以封掉短链，长链不变

> **关联**：秒杀系统的地址隐藏也是 `token → 真实地址` 的映射，但目的不同——短链接是为了压缩和统计，秒杀 token 是为了"不到点不给"。参见 [如何设计一个秒杀系统](如何设计一个秒杀系统.md)。

---

## 常见疑问：短链接和长链接对前端来说不是一样的吗？

短链接系统——前端当然知道长链接，目的根本不是隐藏：

```
用户输入长链接 → 接口返回短链接 → 用户把短链接发微博
                                    ↑
                            目的：把 200 字链接压成 20 字
                            隐私？根本没打算藏
```

秒杀地址隐藏——防的是"还没开始就知道"：

```
活动开始前：
  前端请求接口 → 后端返回 404 / "活动未开始" → 拿不到真实地址
                                            ↑
                                    脚本没法提前准备请求

活动开始瞬间：
  前端请求接口 → 后端返回临时 token → 前端拼成秒杀 URL → 提交
                                   ↑
                          token 刚生成，1 秒后就失效
```

关键区别不在"短不短"，在**时机**：

| | 短链接 | 秒杀地址隐藏 |
|---|---|---|
| **前端能拿到吗** | 随时可以 | ⚠️ 开始前拿不到 |
| **隐藏什么** | 什么都不隐藏 | 隐藏的是**地址本身的存在** |
| **安全靠什么** | 不靠安全 | 靠"不到点不给" |
| **类比** | 门牌号缩写 | 密室，到点才开门 |

> 秒杀那个 token 严格说不是短链接，是**临时凭证**——类似一次性门票，到点才发，用完作废。前端当然最终能拿到，但拿到的时候活动已经开始了，脚本来不及反应。

## 一、核心流程

```
生成：用户提交长链接 → 生成唯一短码 → 存 DB → 返回短链接
访问：用户打开短链接 → 服务端根据短码查长链接 → HTTP 302 跳转
```

---

## 二、短码怎么生成？—— 核心算法

思路：**长链接 → 哈希摘要 → Base62 编码 → 取 7 位短码**

```
长链接：https://www.example.com/product/detail?id=12345
  ↓ MD5 / MurmurHash
哈希值：3f8a9b2c...  (128 位)
  ↓ Base62 编码 (A-Z a-z 0-9, 共 62 个字符)
短码：  A6xYz3Q     (7 位 = 62⁷ ≈ 3.5 万亿种组合，够用)
```

```java
// 短码生成核心代码
public String generateShortCode(String longUrl) {
    // 1. 哈希
    String md5 = DigestUtils.md5Hex(longUrl);        // "3f8a9b2c..."
    // 2. 取前 8 字节，转成 long
    long hash = Long.parseLong(md5.substring(0, 16), 16);
    // 3. Base62 编码（0-9a-zA-Z）
    return base62Encode(hash & Long.MAX_VALUE);       // "A6xYz3Q"
}
```

**Base62 字符集**：`0-9` (10) + `a-z` (26) + `A-Z` (26) = 62 个字符，URL 安全，不会出现 `+` `/` `=`。

| 短码长度 | 组合数 | 够用吗 |
|---------|--------|--------|
| 6 位 | 62⁶ ≈ 568 亿 | 中小规模 |
| **7 位** | 62⁷ ≈ **3.5 万亿** | ✅ 千万 DAU 也够 |
| 8 位 | 62⁸ ≈ 218 万亿 | 稳如老狗 |

## 三、哈希冲突怎么处理？

```java
public String createShortUrl(String longUrl) {
    // 先查是否已生成过（相同长链接返回相同短码，节省存储）
    String existing = db.findByLongUrl(longUrl);
    if (existing != null) return existing;

    String code = generateShortCode(longUrl);
    int retry = 0;
    while (db.existsByCode(code) && retry < 5) {
        // 冲突了，长链接末尾拼接随机盐重新哈希
        code = generateShortCode(longUrl + UUID.randomUUID());
        retry++;
    }
    // 存 DB
    db.save(code, longUrl);
    return code;
}
```

## 四、存储设计

| 方案 | 适用阶段 | 说明 |
|------|---------|------|
| **MySQL** | MVP / 小规模 | 表简单，`code` 建唯一索引 |
| **Redis** | 高频访问 | 热数据缓存，`code → longUrl`，KV 结构天然合适 |
| **MySQL + Redis** | 标准方案 | 写 MySQL，Redis 缓存热门短链 |

```sql
-- 核心表
CREATE TABLE short_url (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    code VARCHAR(8) NOT NULL UNIQUE,   -- 短码，建唯一索引
    url TEXT NOT NULL,                  -- 原始长链接
    created_at DATETIME DEFAULT NOW(),
    expire_at DATETIME,                 -- 过期时间，NULL = 永不过期
    click_count BIGINT DEFAULT 0,       -- 点击次数
    INDEX idx_code (code)
);
```

## 五、访问重定向

```java
@GetMapping("/{code}")
public void redirect(@PathVariable String code, HttpServletResponse response) {
    // 1. 先查 Redis 缓存
    String url = redisTemplate.opsForValue().get("short:" + code);
    if (url == null) {
        // 2. 缓存没有，查 DB
        url = db.findUrlByCode(code);
        if (url == null) {
            response.setStatus(404);
            return;
        }
        // 3. 回写缓存，设 TTL
        redisTemplate.opsForValue().set("short:" + code, url, 1, TimeUnit.HOURS);
    }
    // 4. 302 临时重定向（方便后续改目标）
    response.setStatus(302);
    response.setHeader("Location", url);
    // 5. 异步记录点击统计
    asyncLogClick(code);
}
```

> 为什么用 **302 临时重定向**而非 301？301 浏览器会缓存跳转目标，后续点击不经过你的服务端，点击统计就失效了。

## 六、系统架构

```
┌─────────┐    生成短链     ┌──────────┐   写   ┌─────┐
│  用户     │ ────────────→ │ 短链服务  │ ────→ │MySQL│
└─────────┘                └────┬─────┘       └─────┘
      │                         │
      │    访问短链              │ 查
      └────────────────────────→│ Redis（缓存热门）
                                │
                                │ 302 跳转
                                ↓
                          原始长链接
```

## 七、进阶考虑

| 问题 | 方案 |
|------|------|
| **高并发访问** | Redis 缓存热门短链 |
| **短码被遍历猜测** | 别用自增 ID，用哈希散列的随机码 |
| **链接过期** | DB 存 `expire_at`，查的时候判断 |
| **黑名单/封禁** | 短链被封后标记 `status=blocked`，跳转到警告页 |
| **点击统计** | 异步写入统计表，不拖慢重定向 |

> **一句话总结**：短链接 = 长链 MD5 → Base62 生成 7 位短码 → 存 DB → 访问时查短码拿到长链 → 302 跳转。核心是哈希 + Base62 + 冲突重试，高并发用 Redis 缓存。
