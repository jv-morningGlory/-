# 权限模型对比：ACL / RBAC / ABAC / PBAC

---

## 总览

| 模型 | 控制粒度 | 灵活度 | 管理复杂度 | 适用场景 |
|------|----------|--------|------------|----------|
| **ACL** | 资源级 | 低 | 低 | 文件系统、简单后台 |
| **RBAC** | 角色/功能级 | 中 | 中 | 企业应用（最主流） |
| **ABAC** | 属性级 | 高 | 高 | 多租户、云平台 |
| **PBAC** | 策略级 | 最高 | 最高 | 微服务、统一网关鉴权 |

---

## 一、ACL（Access Control List）

每个**资源**维护一张清单，记录哪些用户/组可以执行哪些操作。

### 实际场景：共享文档系统

像石墨文档、腾讯文档的「分享」功能就是典型的 ACL：

```
文档「Q2 季度营收.xlsx」的访问控制列表：
  → 张三： owner（读、写、删除、分享）
  → 李四： editor（读、写）
  → 王五： viewer（只读）
  → 市场部（组）： viewer（只读）
```

新建一篇文档时，创建者就是 owner，通过「分享给某人」就是在 ACL 中加一条记录。

### 表设计

```sql
-- 资源（文档）
CREATE TABLE doc (
    id          BIGINT PRIMARY KEY,
    title       VARCHAR(200),
    content     TEXT,
    owner_id    BIGINT          -- 创建者
);

-- ACL：谁对哪个资源有什么权限
CREATE TABLE doc_acl (
    id          BIGINT PRIMARY KEY,
    doc_id      BIGINT NOT NULL,       -- 哪个文档
    subject_type TINYINT NOT NULL,     -- 1=用户 2=部门/组
    subject_id  BIGINT NOT NULL,       -- 用户ID 或 部门ID
    permission  VARCHAR(20) NOT NULL,  -- read / write / admin
    UNIQUE KEY (doc_id, subject_type, subject_id)
);
```

> ACL 简单直观，但每个资源单独维护权限。当文档量达到百万级，每次新建文档都要手动设置权限，管理成本爆炸。这也是为什么 ACL 只适合小规模场景。

## 二、RBAC（Role-Based Access Control）

**基于角色的访问控制**，企业应用中最主流的模型。核心思路：**用户 → 角色 → 权限**。

### 实际场景：信贷 CRM 系统

一个信贷公司的 CRM 系统中，权限按岗位职责划分：

```
角色「信贷员」：  客户录入、风控查询、审批提交
角色「风控主管」：风控审批、风控报告导出、黑名单管理
角色「部门经理」：团队业绩查看、审批终审、报表导出
角色「系统管理员」：用户管理、角色管理、系统配置
```

张三入职当信贷员 → 分配「信贷员」角色 → 自动获得客户录入、风控查询等权限。
张三升为主管 → 去掉「信贷员」角色，分配「风控主管」角色 → 权限自动切换。

这就是 RBAC 的好处：**权限跟着角色走，人跟着岗位走**。

### 表设计（RBAC 标准五表）

```sql
-- 1. 用户表
CREATE TABLE sys_user (
    id          BIGINT PRIMARY KEY,
    username    VARCHAR(50) NOT NULL,
    name        VARCHAR(50),
    dept_id     BIGINT,                -- 所属部门
    status      TINYINT DEFAULT 1      -- 1=启用 0=禁用
);

-- 2. 角色表
CREATE TABLE sys_role (
    id          BIGINT PRIMARY KEY,
    role_name   VARCHAR(50) NOT NULL,  -- 如：信贷员、风控主管
    role_code   VARCHAR(50) NOT NULL,  -- 如：LOAN_OFFICER、RISK_MANAGER
    status      TINYINT DEFAULT 1
);

-- 3. 权限表（菜单 + 按钮级）
CREATE TABLE sys_permission (
    id          BIGINT PRIMARY KEY,
    parent_id   BIGINT DEFAULT 0,      -- 父级权限（树形结构）
    name        VARCHAR(100) NOT NULL, -- 如：客户管理、客户录入按钮
    type        TINYINT NOT NULL,      -- 1=菜单 2=按钮
    path        VARCHAR(200),          -- 前端路由路径
    api_url     VARCHAR(200),          -- 后端接口路径，如 /api/customer/**
    method      VARCHAR(10),           -- GET/POST/PUT/DELETE
    sort        INT DEFAULT 0
);

-- 4. 用户-角色关联表
CREATE TABLE sys_user_role (
    user_id     BIGINT NOT NULL,
    role_id     BIGINT NOT NULL,
    PRIMARY KEY (user_id, role_id)
);

-- 5. 角色-权限关联表
CREATE TABLE sys_role_permission (
    role_id       BIGINT NOT NULL,
    permission_id BIGINT NOT NULL,
    PRIMARY KEY (role_id, permission_id)
);
```

**查询某用户所有权限**：

```sql
SELECT DISTINCT p.api_url, p.method
FROM sys_user_role ur
JOIN sys_role_permission rp ON ur.role_id = rp.role_id
JOIN sys_permission p ON rp.permission_id = p.id
WHERE ur.user_id = #{userId}
  AND p.type = 2;   -- 只查按钮/接口级权限
```

> Spring Security 中通常登录后执行上面这条 SQL，把用户所有权限缓存到 Redis，后续请求直接从缓存校验。

## 三、ABAC（Attribute-Based Access Control）

不依赖角色，根据**属性**动态计算权限。属性来源包括主体、资源、操作、环境四个维度。

### 实际场景：多租户 SaaS 数据平台

一个 SaaS 数据分析平台，不同租户的数据必须隔离，且同一租户内不同部门看到的范围不同：

```
租户 A（某银行）的数据分析师 李四 要导出一份报表：

判断条件：
  ① 李四.部门 == 报表.归属部门          → ✓  同部门才能看
  ② 李四.职级 >= '高级分析师'            → ✓  职级够了才能导出
  ③ 当前时间 在 09:00~18:00             → ✓  工作时间才允许导出
  ④ 李四.今天导出次数 < 10              → ✓  有频率限制
  ⑤ 请求.IP 在公司内网段                → ✓  内网才能访问

全部满足 → 允许导出
```

这种场景用 RBAC 很难做，因为权限不是简单的「有/没有」，而是跟**上下文**强相关。

### 表设计

```sql
-- 属性定义
CREATE TABLE abac_attribute (
    id              BIGINT PRIMARY KEY,
    attr_code       VARCHAR(50) NOT NULL,   -- 如：user_dept, user_level, env_time
    attr_name       VARCHAR(100),
    attr_category   TINYINT NOT NULL,       -- 1=主体属性 2=资源属性 3=环境属性
    value_type      VARCHAR(20)             -- string / number / datetime
);

-- 用户属性值（主体属性）
CREATE TABLE abac_user_attr (
    id              BIGINT PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    attr_code       VARCHAR(50) NOT NULL,   -- 如：user_level
    attr_value      VARCHAR(200) NOT NULL,  -- 如：高级分析师
    UNIQUE KEY (user_id, attr_code)
);

-- 策略规则（核心）
CREATE TABLE abac_policy (
    id              BIGINT PRIMARY KEY,
    policy_name     VARCHAR(100) NOT NULL,  -- 如：报表导出策略
    resource_type   VARCHAR(50),            -- 资源类型：报表/数据集/API
    action          VARCHAR(50),            -- 操作：read/export/delete
    effect          TINYINT DEFAULT 1,      -- 1=允许 0=拒绝
    condition_json  TEXT,                   -- 条件表达式（JSON）
    priority        INT DEFAULT 0           -- 优先级，数值越大越优先
);

-- condition_json 示例：
-- {
--   "and": [
--     {"op": "eq",   "subject": "user_dept",  "resource": "res_dept"},
--     {"op": "gte",  "subject": "user_level", "value": "高级分析师"},
--     {"op": "between", "env": "env_time", "value": ["09:00", "18:00"]}
--   ]
-- }
```

> ABAC 的难点不在表设计，而在**策略引擎的实现**——需要解析 condition_json 并动态求值。通常借助 OPA、Casbin 等成熟框架。

## 四、PBAC（Policy-Based Access Control）

ABAC 的进一步工程化，将所有权限规则统一抽象为**策略**，由独立的**策略引擎**集中管理。

### 实际场景：微服务网关统一鉴权

一个电商平台有 20+ 个微服务，如果每个服务各自实现鉴权：

```
❌ 问题：
  用户服务自己校验 token + 权限
  订单服务自己校验 token + 权限
  支付服务自己校验 token + 权限
  ... → 权限逻辑散落在 20 个服务中，改一条规则要发版 20 次
```

引入 PBAC + 网关后：

```
客户端请求 → [API 网关] → 调用策略引擎（OPA） → 放行/拒绝
                                                    ↑
                                            统一的策略中心
                                            策略1：所有 /api/pay/** 必须POST
                                            策略2：商家只能看自己店铺的订单
                                            策略3：未实名用户不能发起退款
                                            策略4：运营后台只允许公司内网IP访问
```

改权限规则只需修改策略中心，不用动任何业务服务。

### 策略配置示例（Casbin）

```ini
# model.conf - 定义策略模型
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act, eft

[policy_effect]
e = some(where (p.eft == allow)) && !some(where (p.eft == deny))

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act
```

```ini
# policy.csv - 具体策略（通常存数据库）
p, admin,   /api/**,          *,      allow
p, editor,  /api/article/**,  GET,    allow
p, editor,  /api/article/**,  POST,   allow
p, viewer,  /api/article/**,  GET,    allow
p, *,       /api/pay/**,      POST,   deny     # 所有用户禁止直接调支付接口
```

## 五、权限流转（以 RBAC 为例）

权限不是静态的，在企业中有一套完整的**申请 → 审批 → 生效 → 回收**流程。

### 流转全景图

```
┌───────────────────────────────────────────────────────────────────┐
│                         权限生命周期                               │
│                                                                   │
│  员工入职 ──→ 初始角色分配 ──→ 权限生效                            │
│                               │                                   │
│                    ┌──────────┼──────────┐                        │
│                    ▼          ▼          ▼                        │
│               权限申请    角色变更    临时授权                      │
│                    │          │          │                        │
│                    ▼          ▼          ▼                        │
│               直属领导审批   HR审批   自动过期                     │
│                    │          │                                   │
│                    ▼          ▼                                   │
│               ┌─────────────────┐                                 │
│               │  权限生效/调整    │                                 │
│               └────────┬────────┘                                 │
│                        │                                          │
│            ┌───────────┼───────────┐                              │
│            ▼           ▼           ▼                              │
│       定期审计    岗位调动回收   离职回收                            │
└───────────────────────────────────────────────────────────────────┘
```

### 表设计（在 RBAC 五表基础上扩展）

```sql
-- 权限申请单
CREATE TABLE perm_apply (
    id              BIGINT PRIMARY KEY,
    applicant_id    BIGINT NOT NULL,         -- 申请人
    apply_type      TINYINT NOT NULL,        -- 1=申请角色 2=申请临时权限 3=角色变更
    target_role_id  BIGINT,                  -- 申请的目标角色
    reason          VARCHAR(500),            -- 申请理由
    status          TINYINT DEFAULT 0,       -- 0=待审批 1=已通过 2=已拒绝 3=已撤回
    approver_id     BIGINT,                  -- 审批人
    approve_time    DATETIME,
    create_time     DATETIME DEFAULT NOW()
);

-- 临时授权（有时效性的权限）
CREATE TABLE perm_temp_grant (
    id              BIGINT PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    role_id         BIGINT NOT NULL,
    grant_reason    VARCHAR(500),            -- 授权原因
    granted_by      BIGINT,                 -- 授权人
    expire_time     DATETIME NOT NULL,       -- 过期时间
    status          TINYINT DEFAULT 1        -- 1=生效 0=已回收
);

-- 权限变更日志（审计用）
CREATE TABLE perm_change_log (
    id              BIGINT PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    change_type     TINYINT NOT NULL,        -- 1=分配角色 2=移除角色 3=临时授权 4=回收
    role_id         BIGINT,
    operator_id     BIGINT,                  -- 操作人（系统/管理员）
    reason          VARCHAR(500),
    create_time     DATETIME DEFAULT NOW()
);
```

### 权限流转的几个关键节点

#### 1. 入职自动分配

```
新员工 → HR 系统录入（岗位：信贷员）
      → 自动调用权限服务分配「信贷员」角色
      → 记录变更日志（change_type=1, operator=系统）
```

#### 2. 权限申请审批

```
张三（信贷员）想导出风控报告 → 没有权限
  → 提交权限申请单（apply_type=1, target=风控主管角色）
  → 直属领导审批
    → 通过：给张三临时授予该角色，设置过期时间（如7天）
    → 拒绝：申请单状态改为已拒绝
  → 过期后定时任务自动回收，记录日志
```

#### 3. 岗位调动

```
张三从信贷员升为风控主管：
  → HR 系统发起角色变更（apply_type=3）
  → 移除旧角色「信贷员」
  → 分配新角色「风控主管」
  → 两条变更日志（移除 + 分配）
```

#### 4. 离职回收

```
张三离职：
  → HR 系统触发离职流程
  → 权限服务：禁用账号（status=0）+ 移除所有角色 + 回收所有临时权限
  → 一次性全部回收，避免权限残留
```

#### 5. 定期审计

```sql
-- 查询：拥有敏感角色但超过 90 天未登录的用户
SELECT u.username, r.role_name, u.last_login_time
FROM sys_user u
JOIN sys_user_role ur ON u.id = ur.user_id
JOIN sys_role r ON ur.role_id = r.id
WHERE r.role_code IN ('ADMIN', 'DATA_EXPORT')
  AND u.last_login_time < DATE_SUB(NOW(), INTERVAL 90 DAY)
  AND u.status = 1;
```

> 审计发现长期未使用的权限应当主动回收，这是等保合规的基本要求。

## 六、选型建议

| 场景 | 推荐模型 | 原因 |
|------|----------|------|
| 共享文档 / 文件系统 | ACL | 权限跟着资源走，简单直接 |
| 企业内部系统（CRM、ERP、OA） | RBAC | 岗位和权限对应清晰，五表模型成熟 |
| 多租户 SaaS / 数据平台 | ABAC | 需要结合部门、职级、时间等多维属性动态判断 |
| 微服务架构 / 统一网关 | PBAC | 策略集中管理，业务服务无需关心鉴权逻辑 |
