# 并发安全三大特性：原子性、可见性、有序性

> 一个方法是否线程安全，取决于它对**共享可变状态**（成员变量 / 静态变量）的操作，是否同时满足三大特性：**原子、可见、有序**。三性缺一不可。

---

## 一、三大特性分别是什么

### 1. 原子性（Atomicity）

> 一组操作在执行过程中**不可被中断、不可被分割**——别的线程要么看到它还没开始，要么看到它已结束，绝不会看到执行了一半。

- **本质**：操作之间**不能被插队**。
- **反面**：`count++` 看着一行，实际是"读 → 改 → 写"三步，三步之间能被别的线程插入 → 丢更新。

### 2. 可见性（Visibility）

> 一个线程对共享变量的修改，能**及时被其他线程看到**。

- **本质**：改动要**同步出去**给别的线程。
- **反面**：每个线程有自己的工作内存（CPU 缓存），普通变量的写可能停留在当前线程缓存里，不立即同步到主内存 → 别的线程读到旧值。

### 3. 有序性（Ordering）

> 程序**实际执行的顺序**和**代码编写的顺序**一致，防止指令重排序导致逻辑错乱。

- **本质**：**顺序不能被偷偷打乱**。
- **反面**：编译器 / CPU 为提升性能会重排序（单线程下结果不变，即 as-if-serial；多线程下会破坏逻辑），例如 `value = 42; ready = true;` 可能被重排成 `ready` 先变 true。

### 总览

| 特性 | 一句话 | 失败的典型表现 |
|------|--------|----------------|
| **原子性** | 操作不被插入 | `count++` 丢更新 |
| **可见性** | 改动别人看得到 | `while(running)` 死循环 |
| **有序性** | 顺序不被打乱 | `ready` 先 true，`value` 还是旧值 |

## 二、不保证三大特性的反面 Demo

### 1. 没保证原子性

```java
// ❌ count++ 非原子,多线程下丢更新
private int count = 0;
public void inc() {
    count++;   // 读 count → +1 → 写回,三步之间能被插入
}
// 100 个线程各调 1 万次,期望 count = 100 万,实际可能 98 万
```

修复：

```java
// ✅ 方案1:Atomic(CAS)
private final AtomicInteger count = new AtomicInteger();
public void inc() { count.incrementAndGet(); }

// ✅ 方案2:synchronized
public synchronized void inc() { count++; }
```

### 2. 没保证可见性

```java
// ❌ running 改了,工作线程看不到,死循环停不下来
private boolean running = true;
public void run() {
    while (running) { doWork(); }   // 可能永远读不到 false
}
public void stop() {
    running = false;   // 改了,但停留在当前线程缓存,没同步出去
}
```

修复：

```java
// ✅ volatile:写立即刷主存,读强制从主存读
private volatile boolean running = true;
```

### 3. 没保证有序性

```java
// ❌ value = 42 和 ready = true 可能被重排
int value = 1;
boolean ready = false;

// 线程1
void writer() {
    value = 42;       // ①
    ready = true;     // ②  可能被重排到 ① 前面!
}

// 线程2
void reader() {
    if (ready) {                    // 看到 ready = true
        System.out.println(value);  // 却可能输出 1(本该 42)
    }
}
```

修复：

```java
// ✅ ready 加 volatile,既防重排又保证可见:
//    ① value = 42 不会重排到 ② ready = true 之后
//    且通过 happens-before,reader 看到 ready = true 时 value 必定是 42
private volatile boolean ready = false;
```

## 三、保证三大特性的手段

### 1. 保证原子性

- `synchronized` / `Lock`：互斥锁，临界区整体原子（多变量也行）
- `Atomic*`（CAS）：单变量的"读-改-写"原子
- ⚠️ `volatile` **不能**保证原子性（救不了 `++`）

> **复合操作的坑**：单步原子 ≠ 组合原子。`if (!map.containsKey(k)) map.put(k, v)` 两步各自原子，组合起来仍不安全，要用 `putIfAbsent` 这类原子复合方法。

### 2. 保证可见性

- `volatile`：写立即刷主存，读强制从主存读
- `synchronized`：释放锁时刷主存，获取锁时清空本地缓存
- `final`：构造完成后，字段值对所有线程可见
- `Atomic*`：底层是 volatile 字段，天然保证可见

### 3. 保证有序性

- `volatile`：插入内存屏障，禁止前后指令重排（写管前面、读管后面）
- `synchronized`：临界区被锁包围，里面的操作"出不去、进不来"
- `final`：防止"对象未构造完就被别的线程看到"的重排

### 总览：各手段保证哪些特性

| 手段 | 原子性 | 可见性 | 有序性 |
|------|:---:|:---:|:---:|
| `volatile` | ❌ | ✅ | ✅ |
| `synchronized` / `Lock` | ✅ | ✅ | ✅ |
| `Atomic*`（CAS） | ✅（单变量） | ✅ | ✅ |
| `final` | —（不可变，无需） | ✅ | ✅ |

## 四、实战心智模型：从单机到分布式

> 前三节讲的是**单 JVM 内**如何保证三性。真实业务（秒杀、抢购）往往是**多节点 + 多中间件**，单机的三性思维会失效——必须升级到分布式视角。

### 1. 单机三性，在分布式下如何失效

| 单机现象 | 分布式失效点 | 根因 |
|---------|------------|------|
| `volatile` 让别的**线程**看得到 | 别的**节点**是另一个 JVM，看不到 | JVM 内手段跨不了进程 |
| `synchronized` 保证临界区原子 | 多节点各锁各的，锁不住别人 | 锁的覆盖范围只到一个 JVM |
| `count++` 复合操作非原子 | `SELECT → 判断 → UPDATE` 同样非原子 | 同样的 check-then-act |

> **结论**：单机靠 JVM 内手段让"别的线程"看见 / 互斥;分布式下"别的节点"是另一个进程,任何 JVM 内手段都无效,必须靠**中心化组件(Redis / MySQL)**或**分布式锁**。

### 2. 处置优先级：按问题形态选「最轻手段」

> 不是"同一问题的方案排序",而是"**问题是什么形态 → 落到对应的最轻手段**"。永远选能搞定的最轻一个。

| 共享状态形态 | 典型例子 | 最轻手段 | 保证的特性 |
|------------|---------|---------|-----------|
| 能不共享 | 不可变对象 / `ThreadLocal` / 分桶分片 | **不共享** | 无需同步,代价 0,最优 |
| 标志位(只赋值不组合) | `running = false` | `volatile` | 可见 + 有序 |
| 单变量读-改-写 | 计数器 `count++` | **CAS / Atomic** | 原子 + 可见 + 有序 |
| 多步复合操作 | "有库存就扣" check-then-act | **原子性下沉** | 整体原子 |
| 多变量强一致 / 长临界区 | 转账(扣 A 加 B) | **锁** | 互斥保证一致 |

> ⚠️ **锁是最后手段,不是首选**。优先级:不共享 > `volatile` / `CAS` > 原子性下沉 > 锁。

### 3. 原子性下沉:复合操作的正确解法

> **复合操作**(如"查库存 + 判断 + 扣减")本身**非原子**,是超卖、丢更新的根源。不要在应用层加锁,而是**借助中心化组件的原子能力,把它压成一条原子操作**。

```sql
-- ❌ 应用层 check-then-act(非原子,三步之间能被插入 → 超卖):
--   Integer stock = redis.opsForValue().get(key);
--   if (stock > 0) redis.opsForValue().decrement(key);

-- ✅ 原子性下沉到数据库:带 stock > 0 条件的 UPDATE,DB 行锁保证原子且跨节点
UPDATE seckill_stock SET stock = stock - 1 WHERE goods_id = #{goodsId} AND stock > 0
```

```lua
-- ✅ 原子性下沉到 Redis:一条 Lua 脚本,Redis 单线程保证整体原子
if tonumber(redis.call('get', KEYS[1])) > 0 then
    redis.call('decr', KEYS[1])
    return 1
else
    return 0
end
```

> **为什么下沉**:Redis / MySQL 是**中心化单点**,单条命令天然 ①原子 ②跨节点一致 ③临界区最短——**最小粒度 + 最强一致 + 最高并发,三者兼得**。

### 4. 两个易混辨析

**①「颗粒度越大越安全」→ 应为「越容易写对」**

安全的本质是"所有共享状态的访问都被正确同步",与粒度无关。粗锁只是**省心**(不容易漏掉某个访问点),不是**更安全**;一把细锁只要看住对应状态,一样安全。

**②「粒度与效率对立」→ 只对悲观锁成立**

- **悲观锁**(`synchronized` / `FOR UPDATE`)靠互斥,粒度与并发度此消彼长。
- **乐观锁(CAS)**靠"冲突重试"而非互斥,低中冲突下几乎无串行点——**安全 + 高并发兼得,打破对立**。
- 影响**效率**的,**临界区长度**往往比粒度更关键:优化的第一刀常是"缩短临界区",而非"细化锁"。

---

## 一句话总结

> 并发安全 = 共享可变状态的操作 **原子 + 可见 + 有序**，三性缺一不可。按场景选手段：
>
> - 要**单变量标志位**的可见 + 有序 → `volatile`
> - 要**单变量计数 / CAS** 的全套 → `Atomic`
> - 要**多变量一致 / 大段临界区**的全套 → `synchronized`
> - **初始化后不再变** → `final`
