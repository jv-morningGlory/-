一个并发场景是否安全，通过三大特性来判断：

**原子性**：一组操作执行过程"不可中断、不可分割"，别的线程要么看到它刚开始、要么看到已结束，绝不会看到执行了一半。

**Java 层保证手段**：
- `synchronized` / `Lock`：互斥锁，临界区整体原子（多变量也行）
- `Atomic*`（CAS）：单变量的"读-改-写"原子
- ⚠️ `volatile` 不能保证原子性（救不了 `i++`）

**SpringBoot 跨账户转账（A 扣 B 加）**：
- 要么都成功、要么都失败 → 用 `@Transactional` 保证
- ⚠️ 边界：`@Transactional` 只管"全做或全不做 + 失败回滚"，**不管并发竞态**——并发下读到的值可能已被别人改过，竞态要靠锁 / 条件更新 / CAS 解决
- **Redis 操作**：Redis 没有事务回滚，失败要靠 **catch 中补偿/逆向操作**（最终一致性，不属于原子性）
- **需要发消息**：用 **事务消息**（如 RocketMQ）保证"本地事务 + 发消息"原子

> **核心心智模型**：凡是"判断 + 执行"的组合，首选**原子性下沉**（SQL 条件更新 / lua 脚本，让存储层保证原子）；无法下沉时，再**上锁**（synchronized / FOR UPDATE）把整段逻辑包成临界区。下沉优先于上锁，因为下沉无锁、性能更好。


**可见性**：一个线程修改了共享变量，别的线程能立即看到，不会读到旧值。

**Java 层保证手段**：
- `volatile`：写完立即刷主内存，读强制从主内存读（靠**内存屏障**落地）
- `synchronized`：释放锁时刷主内存，获取锁时清空本地缓存
- `final`：对象构造完成后，字段值对所有线程可见
- `Atomic*`：底层是 volatile 字段，天然保证可见

**SpringBoot 场景**：
- ⚠️ 先分清两个层面——
  - **同 JVM 多线程间**（如 `@Async`、线程池里的线程）：还是 Java 层的 volatile/synchronized，**不靠中间件**
  - **跨节点共享变量**（多台机器都要读到最新值）：这才是中间件的活，靠 Redis / MQ 广播 / 分布式锁——但**这已不是 JMM 可见性，是分布式数据一致性**

> **核心认知**：可见性是 JVM 内存模型的概念，作用域是"同进程多线程"。SpringBoot 没有自己的一套可见性机制，单机多线程照搬 Java 层；跨节点的"实时性"是另一个问题域（分布式一致性），别和可见性混为一谈。

---

**有序性**：程序实际执行顺序和代码编写顺序一致，防止编译器/CPU 的指令重排序在多线程下破坏逻辑。

**Java 层保证手段**：
- `volatile`：插入内存屏障禁止重排——写管"前面"（它前面的写不能跑到它后面），读管"后面"（它后面的读写不能跑到它前面）
- `synchronized`：临界区被锁包围，里面的操作"出不去、进不来"，整体不会被外部重排打乱
- `final`：防止"对象未构造完就被别的线程看到"的重排（构造完成前字段值不泄漏）

**SpringBoot 场景**：
- ⚠️ 有序性没有 SpringBoot 层特有手段，和可见性一样靠 Java 层
- 它在 SpringBoot 里最常以两个坑出现：
  1. **DCL 单例**：`instance = new Singleton()` 可能重排成"先赋引用、再初始化字段"→ 别的线程拿到半构造对象。修复：`instance` 加 `volatile`
  2. **对象逸出**：构造函数里把 `this` 发布出去 → 别的线程看到未构造完的对象。修复：构造函数里别泄漏 `this`，关键字段用 `final`

> **核心认知**：有序性最隐蔽——单线程下重排无害（as-if-serial，结果不变），**只有多线程下才暴露**。所以它不是"会不会出错"，而是"多线程下会不会出错"。最经典的坑都是"半构造对象被别人看到"，防御靠 `volatile` 的内存屏障或 `final`。








# 并发安全三大特性：原子性、可见性、有序性

> 一个方法是否线程安全，取决于它对**共享可变状态**（成员变量 / 静态变量）的操作，是否同时满足三大特性：**原子、可见、有序**。三性缺一不可。

---

## 一、三大特性分别是什么

### 1. 原子性（Atomicity）

> 一组操作在执行过程中**不可被中断、不可被分割**——别的线程要么看到它还没开始，要么看到它已结束，绝不会看到执行了一半。

- **本质**：操作之间**不能被插队**。
- **反面**：`count++` 看着一行，实际是"读 → 改 → 写"三步，三步之间能被别的线程插入 → 丢更新。

### 2. 可见性（Visibility）

> 一个线程对共享变量的修改，能**及时被其他线程看到**。

- **本质**：改动要**同步出去**给别的线程。
- **反面**：每个线程有自己的工作内存（CPU 缓存），普通变量的写可能停留在当前线程缓存里，不立即同步到主内存 → 别的线程读到旧值。

### 3. 有序性（Ordering）

> 程序**实际执行的顺序**和**代码编写的顺序**一致，防止指令重排序导致逻辑错乱。

- **本质**：**顺序不能被偷偷打乱**。
- **反面**：编译器 / CPU 为提升性能会重排序（单线程下结果不变，即 as-if-serial；多线程下会破坏逻辑），例如 `value = 42; ready = true;` 可能被重排成 `ready` 先变 true。

### 总览

| 特性 | 一句话 | 失败的典型表现 |
|------|--------|----------------|
| **原子性** | 操作不被插入 | `count++` 丢更新 |
| **可见性** | 改动别人看得到 | `while(running)` 死循环 |
| **有序性** | 顺序不被打乱 | `ready` 先 true，`value` 还是旧值 |

---

## 二、不保证三大特性的反面 Demo

### 1. 没保证原子性

```java
// ❌ count++ 非原子,多线程下丢更新
private int count = 0;
public void inc() {
    count++;   // 读 count → +1 → 写回,三步之间能被插入
}
// 100 个线程各调 1 万次,期望 count = 100 万,实际可能 98 万
```

修复：

```java
// ✅ 方案1:Atomic(CAS)
private final AtomicInteger count = new AtomicInteger();
public void inc() { count.incrementAndGet(); }

// ✅ 方案2:synchronized
public synchronized void inc() { count++; }
```

### 2. 没保证可见性

```java
// ❌ running 改了,工作线程看不到,死循环停不下来
private boolean running = true;
public void run() {
    while (running) { doWork(); }   // 可能永远读不到 false
}
public void stop() {
    running = false;   // 改了,但停留在当前线程缓存,没同步出去
}
```

修复：

```java
// ✅ volatile:写立即刷主存,读强制从主存读
private volatile boolean running = true;
```

### 3. 没保证有序性

```java
// ❌ value = 42 和 ready = true 可能被重排
int value = 1;
boolean ready = false;

// 线程1
void writer() {
    value = 42;       // ①
    ready = true;     // ②  可能被重排到 ① 前面!
}

// 线程2
void reader() {
    if (ready) {                    // 看到 ready = true
        System.out.println(value);  // 却可能输出 1(本该 42)
    }
}
```

修复：

```java
// ✅ ready 加 volatile,既防重排又保证可见:
//    ① value = 42 不会重排到 ② ready = true 之后
//    且通过 happens-before,reader 看到 ready = true 时 value 必定是 42
private volatile boolean ready = false;
```

## 三、保证三大特性的手段

### 1. 保证原子性

- `synchronized` / `Lock`：互斥锁，临界区整体原子（多变量也行）
- `Atomic*`（CAS）：单变量的"读-改-写"原子
- ⚠️ `volatile` **不能**保证原子性（救不了 `++`）

> **复合操作的坑**：单步原子 ≠ 组合原子。`if (!map.containsKey(k)) map.put(k, v)` 两步各自原子，组合起来仍不安全，要用 `putIfAbsent` 这类原子复合方法。

### 2. 保证可见性

- `volatile`：写立即刷主存，读强制从主存读
- `synchronized`：释放锁时刷主存，获取锁时清空本地缓存
- `final`：构造完成后，字段值对所有线程可见
- `Atomic*`：底层是 volatile 字段，天然保证可见

### 3. 保证有序性

- `volatile`：插入内存屏障，禁止前后指令重排（写管前面、读管后面）
- `synchronized`：临界区被锁包围，里面的操作"出不去、进不来"
- `final`：防止"对象未构造完就被别的线程看到"的重排

### 总览：各手段保证哪些特性

| 手段 | 原子性 | 可见性 | 有序性 |
|------|:---:|:---:|:---:|
| `volatile` | ❌ | ✅ | ✅ |
| `synchronized` / `Lock` | ✅ | ✅ | ✅ |
| `Atomic*`（CAS） | ✅（单变量） | ✅ | ✅ |
| `final` | —（不可变，无需） | ✅ | ✅ |


valatile  ：
