# 信贷CRM风险画像系统 - 面试经验总结

## 一、项目概述

**项目名称：** 财信信贷CRM系统 - 风险画像模块 (Risk Profiling)

**项目定位：** 面向大型金融机构的**信贷风险指标管理与风险画像系统**。服务于财信集团及旗下子公司，帮助风控部门构建风险评估模型，对企业/主体进行多维度的风险自动化打分，最终生成风险画像报告和看板。

**系统解决的核心问题：**
- 金融机构需要定期（按月）对持有的信贷资产进行风险评估
- 评估模型需要灵活可配（不同主体、不同类型的风险维度、不同的记分卡规则）
- 需要支持批次计算、数据校验、结果发布、历史追溯的完整流程

**项目规模：** 后端约 200+ Java 类，50+ Mapper XML，涉及约 20+ 张数据库表

**团队分工：**

- 同事（liangbo）：负责记分卡打分规则引擎、批次计算流程、指标校验逻辑、仪表盘等
- 其他同事：指标管理模块、配置管理模块、Kafka 消费等

## 二、核心业务模块详解

### 模块 1：风险画像模型配置

**业务描述：**

用户创建一个风险评估模型，需要经过多个步骤：
1. 创建模型基本信息（名称、版本、适用主体）
2. 配置风险维度（从风险维度分类树中选择维度，配置打分卡类型）
3. 配置每个维度下的指标（从指标库中选择指标）
4. 配置打分卡规则（每个打分卡配具体的打分规则）
5. 最终激活模型，模型激活后即可用于批次计算

模型有四种状态：编辑中(0) -> 未生效(1) -> 生效中(2) -> 停用。整个配置过程支持分步保存（草稿模式）和一次性提交（正式模式）。

**核心实现：RiskProfilingBizServiceImpl**

`updateRiskDimInfo` 方法是整个模块最核心的方法，实现了维度配置的**删除-新增-更新**三步原子操作：

```java
@Transactional(rollbackFor = ServiceException.class)
public Boolean updateRiskDimInfo(UpdateRiskDimInfoReq req) {
    // 1. 参数校验
    RiskProfilingUtil.validateArgument(req, req.getOperateType());
    // 2. 获取模型中已有的配置ID列表
    List<Long> configIdList = riskProfilingRiskDimConfigService.listByModelId(modelId)...
    // 3. 删除 - 删除用户移除的维度配置及关联数据
    this.clearConfig(req.getDeleteConfigIdList(), configIdList);
    // 4. 新增 - 插入新添加的维度配置
    this.addConfig(req.getModelId(), req.getAddRiskDimInfoDtoList(), riskDimClassTreeList);
    // 5. 更新 - 先删后插的方式更新已有配置
    this.updateConfig(req.getModelId(), req.getUpdateRiskDimInfoDtoList(), ...);
    // 6. 如果是正式提交(operateType != 0)，进行业务校验
    if (!Objects.equals(0, optionType)) {
        this.validateConfigBiz(req.getModelId());  // 校验业务规则
        this.clearConfigBiz(req.getModelId());     // 清理旧规则
    }
}
```

`validateConfigBiz` 校验规则包含：
- 维度不可重复
- 必须包含单一风险维度及其子维度
- 子维度权重和必须等于100
- 总体维度必须满足 5 个、单一风险子维度必须满足 8 个

**技术难点与实现：**

| 难点 | 说明 | 解决方案 |
|------|------|---------|
| **草稿与正式分离** | 用户可能分多次配置，也可能一次完成。草稿不校验业务规则，正式提交才校验 | 设计 `operateType` 参数控制（0=草稿、1=正式），草稿阶段跳过 `validateConfigBiz` 和 `clearConfigBiz` |
| **树形结构递归处理** | 风险维度有父子层级关系（如单一风险维度下含8个子维度），子维度可能还有子维度 | `insertRiskDimInfo` 方法递归处理，通过 `parentId` 构建层级关系，`hasSubDimClass` 标记是否有子维度 |
| **维度与指标一致性校验** | 用户选择的指标必须属于对应维度分类，不同维度不能混用指标 | `checkDimIndex` 方法递归校验：通过 `CrmCollUtils.validateElements` 判断指标ID列表是否全都在维度分类的合法指标范围内 |
| **更新时的数据一致性** | 更新维度配置需要"先删旧的、再插新的"，同时不能影响其他维度的配置 | 每条更新记录独立在一个循环中处理（先删后插），整个方法用 `@Transactional` 保证原子性 |

### 模块 2：批次计算引擎（跑批）

**业务描述：**

模型激活后，系统需要定期（按月/手动触发）对主体进行风险评估计算。整个计算流程是：

1. 触发跑批（系统自动或手动） -> 创建 `RiskProfilingBatchLog` 记录
2. 调用 LiteFlow 规则引擎执行 `scorecard` 链
3. 结果保存到 `RiskProfilingBatchDetail`（维度得分）+ `RiskProfilingBatchDetailIndex`（指标明细）
4. 检查环节：校验哪些指标数据缺失或异常 -> `RiskProfilingBatchCheck`
5. 人工确认发布（publish），发布后可被仪表盘查询

**核心实现：RiskProfilingBatchLogServiceImpl.startBatch()**

```java
public void startBatch(String staticTime, Long modelId, ...) {
    // 1. 校验模型是否存在且已生效
    RiskProfilingModelInfo modelInfo = riskProfilingModelInfoService.getById(modelId);
    if (!THREE_STR.equals(modelInfo.getModelStatus())) {
        throw new ServiceException("模型未生效！");
    }
    // 2. 构建流程请求参数 & 创建批次日志
    RiskProfilingFlowRequest request = new RiskProfilingFlowRequest();
    request.setModelId(modelId).setStaticTime(staticTime).setBatchOrOnline(0);
    RiskProfilingBatchLog batchLog = new RiskProfilingBatchLog()...;
    save(batchLog);
    // 3. 更新主体最新画像信息
    riskProfilingBatchSubjectLatestService.updateSubjectLatest(...);
    // 4. 执行 LiteFlow 规则引擎
    request.setBatchId(batchLog.getId());
    LiteflowResponse response = flowExecutor.execute2Resp(
        "scorecard", request,
        RiskProfilingFlowResult.class,    // 一级维度结果上下文
        SingleRiskResult.class            // 单一风险结果上下文
    );
    // 5. 发送检查消息
    riskProfilingBatchCheckService.sentCheckMessage(...);
}
```

**LiteFlow 流程编排：**

```xml
<chain name="scorecard">
    <!-- 第一步：迭代所有一级风险维度，并行执行 -->
    ITERATOR(dimConfigIterator).parallel(true).DO(
        <!-- 如果是单一风险维度(dimId=16)，走特殊分支 -->
        IF(dimConfigBoolean.tag("16"), singleRiskNode, notSingeRiskNode)
    );
</chain>

<chain name="notSingeRiskNode">
    <!-- 根据记分卡类型(1/2/3/4)路由到不同打分组件 -->
    SWITCH(scorecardSwitch).TO(
        generalScorecard.tag("1"),
        eventScorecard.tag("2"),
        strategicScorecard.tag("3"),
        concentrationScorecard.tag("4")
    );
</chain>

<chain name="singleRiskNode">
    THEN(
        <!-- 对单一风险的子维度逐一打分 -->
        ITERATOR(singleRiskIterator).DO(
            SWITCH(scorecardSwitch).TO(...)
        ),
        <!-- 汇总子维度得分，按权重计算最终得分 -->
        singleRisk
    );
</chain>
```

**四种记分卡的打分逻辑：**

| 记分卡 | 业务逻辑 | 核心技术点 |
|--------|---------|-----------|
| **通用记分卡** | 最高分扣减模式：先找最高分，按指标的风险级别计数扣减 | `highestScore - (deduction * count)`，保底最低分 |
| **事件记分卡** | 类似通用，但按"命中次数"而非"指标个数"计算扣减 | 需校验指标值是否为整数，若格式错误记录日志并抛出异常 |
| **战略记分卡** | 按风险状况(Situation)分组权重，取最大权重组对应的分数 | 先按权重分组聚合 -> 多组同权重时比较最大单指标权重 -> 仍相同取最轻风险 |
| **集中度记分卡** | 每个指标单独打分 + 权重加权。分未超限/超目标/超预警/超容忍四种公式 | 指标分两类：一类(计算分)二类(扣分)，公式如 `100 - (指标值-目标值)/(预警值-目标值)*比例` |

**技术难点与实现：**

| 难点 | 说明 | 解决方案 |
|------|------|---------|
| **并行打分与结果聚合** | 多个维度并行计算，但最终结果需汇总到单一风险维度 | LiteFlow `parallel(true)` 并行 + `CopyOnWriteArrayList` 线程安全集合 + `SingleRiskCmp` 汇总组件 |
| **试算与正式分离** | 试算不能落库、正式必须落库 | `batchOrOnline` 参数控制：1=试算（`saveBatchDetailAndIndex` 直接返回 null），0=正式 |
| **指标数据完整性校验** | 不同频率的指标（日/周/月/季/半年/年）取数逻辑不同，且需处理节假日 | `AbstractIndexCheckEvent` 模板方法模式：根据频率分支计算周期最后一天 + 节假日回退到工作日 |
| **时期早于模型生效时间** | 如果补跑的期次早于模型生效时间，应该跳过 | `processBatch` 中比较 `staticTime` 和 `modelInfo.getStartTime()`，小于则跳过 |

### 模块 3：模型激活与补跑机制

**业务描述：**

用户将模型从未生效状态激活为生效状态时，需要：
1. 校验模型业务配置完整性（维度、权重等）
2. 确保同一主体只能有一个生效模型
3. 从模型生效起始月份自动补跑过去月份的批次数据（不含当前月及未来）

**核心实现：**

```java
public Boolean activateModel(ActivateModelReq req) {
    return synchronousEvent.getWithLock(ACTIVE_MODEL_KEY, () -> {
        // 1. 校验模型存在且状态为"未生效"
        // 2. 校验业务配置完整性
        riskProfilingBizService.validateConfigBiz(modelId);
        // 3. 校验同一主体无其他生效模型（一个主体只允许一个）
        RiskProfilingModelInfo activeModel = this.getOne(
            queryWrapper.eq(DOMAIN_ID, domainId).eq(MODEL_STATUS, ACTIVE)
        );
        if (activeModel != null) {
            throw new ServiceException("该主体下有生效中的模型");
        }
        // 4. 更新模型状态为生效
        this.updateById(modelInfo.setModelStatus(ACTIVE)...);
        // 5. 补跑过去月份的批次
        DateRange range = DateUtil.range(startTime, endTime, DateField.MONTH);
        for (DateTime date : range) {
            riskProfilingBatchLogService.startBatch(...);
        }
    });
}
```

**技术难点与实现：**

| 难点 | 说明 | 解决方案 |
|------|------|---------|
| **并发激活冲突** | 同一主体同一时间被多人激活 | Redis 分布式锁 `synchronousEvent.getWithLock(ACTIVE_MODEL_KEY, ...)` |
| **补跑范围精确计算** | 从生效月开始到上月，不包括当前月 | Hutool `DateUtil.range(start, end, MONTH)` 生成月份范围 |
| **一个主体一个生效模型** | 防止多模型导致计算结果冲突 | 唯一性校验：查询同主体同状态下是否有已生效模型 |

### 模块 4：批次发布与取消

**业务描述：**

跑批完成后，计算结果处于"未发布"状态。需要人工确认风险状况描述后发布。发布逻辑：
1. 检查同主体同期次不能发布多个
2. 将旧的已发布批次改为非发布状态
3. 将新批次设为已发布，并记录发布操作到 `publish_record` 表（形成操作链）
4. 取消发布时，从操作链恢复到上一版本

**核心实现：**

```java
public Boolean publishBatchLog(PublishBatchLogReq req) {
    synchronousEvent.getWithLock(PUBLISH_BATCH_LOG_KEY, () -> {
        // 一个主体同期次仅支持发布一个
        if (checkSet.contains(domainId + staticTime)) {
            throw new ServiceException("一个主体同个画像期次仅支持发布一个!");
        }
        // 先把该主体同期次已发布的批次全部取消
        this.update(updateWrapper.eq(DOMAIN_ID, domainId)
            .eq(STATIC_TIME, staticTime).eq(BATCH_BIZ_STATUS, 1)
            .set(BATCH_BIZ_STATUS, 2));
        // 将新批次设为已发布
        this.update(updateWrapper.eq(ID, batchId)
            .set(BATCH_BIZ_STATUS, 1).set(PUBLISH_TIME, new Date()));
        // 记录发布操作链
        publishRecordService.push(domainId, staticTime, batchId, ...);
    });
}
```

**技术难点与实现：**

| 难点 | 说明 | 解决方案 |
|------|------|---------|
| **发布操作链** | 同一主体同期次可多次发布（换批次），取消时需要恢复到上一个 | `RiskProfilingBatchPublishRecord` 表维护 `preId`（前驱ID）形成链表 |
| **取消校验** | 只能取消最新的发布记录，不能跳过 | `publishRecordService.getLast(domainId, staticTime)` 获取最新记录，校验是否与当前批次一致 |
| **并发发布冲突** | 多人同时对同一主体操作 | Redis 分布式锁防并发 |

### 模块 5：模型复制

**业务描述：**

用户可以复制一个已有的模型，快速创建新模型。复制涉及 8 张关联表的全量数据拷贝：

1. `model_info` - 模型基本信息
2. `risk_dim_config` - 风险维度配置
3. `risk_dim_config_index_relation` - 维度-指标关联
4. `scorecard_basic` - 记分卡基本信息
5. `config_scorecard_relation` - 配置-记分卡关联
6. `general_scorecard_rule` - 通用记分卡规则
7. `event_scorecard_rule` - 事件记分卡规则
8. `strategic_scorecard_rule` - 战略记分卡规则
9. `index_weight` - 指标权重

**核心实现：**

```java
// RiskProfilingBizServiceImpl.copyModelInfo()
public Boolean copyModelInfo(Long modelId, String iamUserId) {
    // 1. 复制模型基本信息，生成新模型名称 (原名称_copyN)
    riskProfilingModelInfoService.copyByModelId(modelId, iamUserId);
    // 2-9. 各 Service 通过 CopyModelContextHolder 获取新旧ID映射来复制
    riskProfilingRiskDimConfigService.copyByModelId(modelId);
    riskProfilingRiskDimConfigIndexRelationService.copyByModelId(modelId);
    ... // 共8个Service
    copyModelContextHolder.remove(); // 清理 ThreadLocal
}
```

**技术难点与实现：**

| 难点 | 说明 | 解决方案 |
|------|------|---------|
| **跨表ID映射** | 复制后每条记录的主键都变了，关联表需要正确引用新ID | `CopyModelContextHolder` (ThreadLocal) 存储各类ID的映射Map（oldId -> newId），各Service的copy方法从中获取映射关系 |
| **模型名称自动生成** | 不能与已有复制模型重名 | 数据库正则查询 `modelName + "_copy" + 数字` 的当前最大值，+1 |
| **8表复制的事务一致性** | 任一表复制失败需要整体回滚 | `@Transactional` + `ServiceException` 触发回滚 |

**CopyModelContextHolder 设计：**

这是一个典型的**上下文传递模式**实现。因为复制操作分散在多个 ServiceImpl 中，无法通过入参一一传递新旧ID，使用 ThreadLocal 作为"隐式参数"在线程内传递，各 Service 从 Holder 取数据，调用方最后 `remove()` 清理。

### 模块 6：指标管理子系统

**业务描述：**

指标管理是风险画像的数据基础，覆盖指标的全生命周期管理。这是项目中数据表最多的子系统（30+ Mapper XML），包含以下子模块：

**6.1 指标预警子模块**

当指标值超过目标值(1)、预警值(2)或容忍值(3)时，系统自动生成预警记录。核心数据流：

```
index_info (指标定义)
  -> index_trend_log (趋势日志+版本快照)
    -> index_warning_basic (预警主表)
      -> index_warning_info (预警详情)
      -> index_warning_metric (去重控制，值未变化则跳过)
```

**预警状态机：** NOT_STARTED(0,未发起) -> SAVED(1,暂存) -> IN_PROGRESS(2,在处理中) -> COMPLETED(3,完成)

**初始化逻辑（IndexWarningBasicServiceImpl.init）：**
1. 删除同一期次下状态为 NOT_STARTED/SAVED 的旧数据（保留 IN_PROGRESS/COMPLETED 的）
2. 从 index_trend_log 查询超限指标（index_result IN ('1','2','3') 且 index_type='formula'）
3. 通过 index_warning_metric 去重：最新趋势值未变化则跳过
4. 查找 previousId（上一期次的处置任务ID，实现跨期次关联）
5. 每批 500 条分批保存
6. 生成消息通知相关人员

**6.2 指标处置子模块**

前置任务状态机：IN_PROGRESS(2,审批中) -> COMPLETED(3,审核通过) / ROLLBACK(4,退回) / REVOKE(-1,撤销)

**前置任务提交（IndexWarningPreDisposalBizServiceImpl.commit）：**
- 检查是否已有 crmPreTaskId（不可重复提交）
- 检查是否有在途修订任务
- 检查是否有在途处置完成任务
- 检查只能提交同一监测主体的指标
- 使用 Redis SET 做分布式锁防止同一指标并发操作

**6.3 指标修订子模块**

与预警对称，差异点：
- 修订只针对 `fill_type='1'` 的指标（需要人工填写）
- 修订不限制超限结果范围，所有指标都可被修订
- 修订前后版本关联通过 `IndexRevisePreRevisionRelation` 表维护

**6.4 中台状态同步**

通过 Kafka 消费中台回写的状态消息，使用组合键 `taskId + staticTime + indexDcId` 关联本地数据：
- 过滤脏数据：本地 userUpdateTime > 中台 updateTime 时跳过
- 使用 MySQL `INSERT ... ON DUPLICATE KEY UPDATE` 批量写入
- 状态为 COMPLETED 时自动完成处置流转：更新预警状态 -> 插入处置完成记录 -> 更新处置阶段 -> 记录操作流水

**6.5 指标版本管理**

- 每次指标变更在 `index_info_version` 写入快照，通过 `batch_version` 区分版本
- `is_latest=1` 标记最新版本
- 支持版本对比：通过 `BeanCompareUtil.compareDiffFields` 逐字段对比，分为新增(add)、删除(delete)、变更(diff)三类

**技术难点：**

| 难点 | 说明 | 解决方案 |
|------|------|---------|
| **多级并发控制** | 同一指标被多人同时操作 | Redis SET 业务锁 + SynchronousEvent 同步包装 + MySQL ON DUPLICATE KEY |
| **MySQL变量模拟窗口函数** | MySQL 8.0以下没有 ROW_NUMBER()，需要按 indexDcId 分组取最新记录 | `@row_num := IF(@prev_index_dc_id = index_dc_id, @row_num + 1, 1)` 用户变量实现 |
| **组合键关联** | 中台和本地系统使用不同ID体系 | `taskId + staticTime + indexDcId` 组合键贯穿预警/修订/操作记录 |
| **去重机制** | 防止指标值未变化时重复生成预警 | index_warning_metric 表记录上次预警时的指标值，对比后决定跳过或更新 |
| **暂存数据版本迁移** | 新一期数据初始化时，上一期暂存数据需迁移到新记录 | updateSaved 方法将旧 basicId 的 info 复制到新 basicId |
| **操作流水全追踪** | 处置和修订的每条操作需记录 | IndexDisposalAndReviseOperateRecord 表统一记录，bizType 分5类 |
| **节假日处理** | 不同频率指标的取数时间窗口需考虑节假日 | AbstractIndexCheckEvent 模板方法，按频率分支计算周期最后一天 + 节假日回退到工作日 |

### 模块 7：仪表盘查询

**业务描述：**

### 模块 8：多数据源动态切换

**业务描述：**

项目同时连接 MySQL 和 PostgreSQL，不同业务表的 Mapper 需要路由到不同的数据库。

**实现方案（自研）：**

```java
// 1. 自定义注解标记数据源
@DataSource("master")  // 或 "slave" / "postgresql"

// 2. AOP 切面拦截所有 Mapper/Service 调用
@Before("target(BaseMapper) || target(IService)")
public void intercept(JoinPoint point) {
    // 从类/方法上读取 @DataSource 注解
    String dbType = resolveDataSource(target, method);
    // 设置到 ThreadLocal
    DbContextHolder.setDbType(dbType);
}

// 3. DynamicDataSource 根据 ThreadLocal 中的 key 返回对应 DataSource
public class DynamicDataSource extends AbstractRoutingDataSource {
    protected Object determineCurrentLookupKey() {
        return DbContextHolder.getDbType() == null ? "master" : ...;
    }
}
```

**与 MyBatis-Plus 官方方案的对比：**
- 官方 `dynamic-datasource-spring-boot-starter` 更开箱即用
- 自研方案更灵活（自定义注解、可与现有框架深度整合）

### 1. LiteFlow 规则引擎

**项目用法：**

通过 `flow.xml` 定义打分链流程，包含迭代器(ITERATOR)、平行执行(parallel)、条件分支(IF)、路由切换(SWITCH)：

```xml
<chain name="scorecard">
    ITERATOR(dimConfigIterator).parallel(true).DO(
        IF(dimConfigBoolean.tag("16"), singleRiskNode, notSingeRiskNode)
    );
</chain>
<chain name="notSingeRiskNode">
    SWITCH(scorecardSwitch).TO(
        generalScorecard.tag("1"), eventScorecard.tag("2"),
        strategicScorecard.tag("3"), concentrationScorecard.tag("4")
    );
</chain>
```

LiteFlow 规则存储在 Nacos 配置中心，通过 `liteflow-rule-nacos` 插件支持动态下发和热更新。

**Q1: LiteFlow 的工作原理是什么？和传统 if-else 有什么区别？**

- LiteFlow 基于**组件化 + 规则编排**思想，每个节点是独立可复用的组件（NodeComponent），流程通过 XML/JSON 配置编排而非硬编码
- 优势：流程可视化、节点解耦、支持并行执行（`parallel(true)`）、动态更新规则（Nacos 热更新）
- 传统 if-else：逻辑硬编码在代码中，改流程需要改代码重新发布

**Q2: LiteFlow 的 Switch 节点和 If 节点有什么区别？**

- If 节点(`NodeBooleanComponent`)：返回 true/false，两条分支
- Switch 节点(`NodeSwitchComponent`)：返回字符串，按 tag 匹配多路分支（类似 switch-case）
- 项目用 `ScorecardSwitchCmp.processSwitch()` 返回 `"tag:1/2/3/4"` 路由到不同记分卡

**Q3: 项目中的 LiteFlow 规则存在哪里？如何实现热更新？**

- 使用 `liteflow-rule-nacos` 插件，规则存储在 Nacos 配置中心
- 修改 Nacos 中的 `flow.xml` 后，LiteFlow 自动检测变更并重新加载，无需重启服务
- 适用于业务规则频繁变化的场景

**Q4: LiteFlow 的上下文机制是怎样的？如何传递数据？**

- 请求数据：`this.getRequestData()` 获取调用时传入的参数对象 (`RiskProfilingFlowRequest`)
- 上下文Bean：`this.getContextBean(XxxResult.class)` 获取流程级上下文，在多个组件间共享
- 循环对象：`this.getCurrLoopObj()` 获取当前迭代元素
- 项目中分两个上下文：`RiskProfilingFlowResult`（一级维度结果）和 `SingleRiskResult`（单一风险结果）

**Q5: LiteFlow 如何实现并行执行？有什么注意事项？**

- XML 中配置 `parallel(true)` 即可开启并行
- 项目中对一级维度迭代时并行执行各维度打分
- 注意：并行组件内的共享数据必须用线程安全集合，项目中 `RiskProfilingFlowResult` 使用 `CopyOnWriteArrayList`
- 注意：并行执行时事务不再适用，项目中将事务控制放在调用 LiteFlow 之前（创建 batchLog），LiteFlow 链中只做查询和计算结果保存

**Q6: LiteFlow 的常用组件类型有哪些？**

- `NodeComponent`：普通执行组件（如 `process()` 方法）
- `NodeBooleanComponent`：条件判断组件（`processBoolean()` 返回 boolean）
- `NodeSwitchComponent`：路由切换组件（`processSwitch()` 返回 tag 字符串）
- `NodeIteratorComponent`：迭代器组件（`processIterator()` 返回 Iterator）

### 2. Spring Cloud + OpenFeign 微服务

**项目用法：**

- soa-crm-api 模块定义 Feign 接口，使用 `@FeignClient` 注解
- soa-crm-service 模块通过 `@EnableFeignClients` 扫描外部 API 并实现内部 API
- 统一返回格式 `RpcResponse<T>` 封装返回值

```java
@FeignClient(value = "soa-crm-service", path = "api/router/risk_profiling/model_info")
public interface RiskProfilingModelInfoApi {
    @GetMapping("/set_steps")
    RpcResponse<Boolean> setSteps(@RequestParam("modelId") Long modelId, ...);
}
```

**Q1: Feign 的原理是什么？**

- Feign 基于动态代理 + Ribbon 负载均衡，将 HTTP 调用伪装成本地方法调用
- 底层通过 `ReflectiveFeign` 生成代理对象，执行时通过 `Encoder/Decoder` 序列化/反序列化请求和响应
- 调用链路：代理对象 -> 拦截器 -> Ribbon 选服务实例 -> HTTP 客户端发请求

**Q2: 服务注册和发现用的是什么？**

- `@EnableDiscoveryClient` + Nacos
- 服务启动时向 Nacos 注册（服务名、IP、端口）
- Feign 调用时从 Nacos 拉取服务列表，Ribbon 做客户端负载均衡

**Q3: 如何处理 Feign 调用失败？**

- 超时配置、重试配置
- Fallback/Hystrix 降级（服务熔断降级）
- 熔断器状态机：关闭 -> 打开 -> 半开 -> 关闭

**Q4: 你们的 API 返回格式是怎么统一的？**

- 内部框架 `cxsk-framework` 封装了 `RpcResponse<T>`，包含 code、message、data 三个字段
- Controller 实现通过 `FeignUtil.response(() -> service.doSomething())` 统一包装

**Q5: Feign 接口定义在 api 模块，实现在 service 模块，这种分包有什么好处？**

- api 模块只定义接口和 DTO，可以独立发布 Maven 包给其他服务引用
- 符合**接口隔离原则**，消费者只依赖接口不依赖实现
- 项目中的 Feign 接口分两种：内部接口（实现在自己的 service 模块）和外部接口（调用其他微服务）

### 3. 多数据源动态切换

**项目用法：** 基于 `AbstractRoutingDataSource` + ThreadLocal + AOP 实现：

```java
// 1. ThreadLocal 上下文
public class DbContextHolder {
    private static final ThreadLocal<String> contextHolder = new ThreadLocal<>();
    public static void setDbType(String key) { contextHolder.set(key); }
    public static String getDbType() { return contextHolder.get(); }
    public static void clearDbType() { contextHolder.remove(); }
}

// 2. 动态数据源
public class DynamicDataSource extends AbstractRoutingDataSource {
    protected Object determineCurrentLookupKey() {
        Object dbType = DbContextHolder.getDbType();
        DbContextHolder.setDbType(null); // 用完立即清理
        return dbType == null ? "master" : dbType;
    }
}

// 3. AOP 切面自动设置
@Aspect
public class DataSourceAspect {
    @Before("target(BaseMapper) || target(IService)")
    public void intercept(JoinPoint point) {
        // 读取类/方法上的 @DataSource 注解，设置到 ThreadLocal
        DbContextHolder.setDbType(dbType);
    }
}
```

**Q1: 多数据源切换的原理是什么？**

- Spring 的 `AbstractRoutingDataSource` 维护一个 `Map<Object, DataSource>`
- 每次获取数据库连接时，调用 `determineCurrentLookupKey()` 获取 key
- 从 Map 中取出对应的 DataSource 返回连接

**Q2: 为什么要用 ThreadLocal？有什么风险？**

- 保证多数据源切换的线程安全，每个线程独立持有自己的数据源标识
- 风险1：ThreadLocal 内存泄漏（key 是弱引用但 value 是强引用），需在 finally 中调用 `remove()`
- 风险2：使用线程池时，线程复用会导致上一次请求的数据源标识残留，代码中 `setDbType(null)` 是为了清理

**Q3: 如果某业务需要同时操作两个数据库的事务怎么办？**

- 单节点多数据源的痛点：Spring 的 `DataSourceTransactionManager` 只能绑定一个数据源
- 解决方案：分布式事务（Seata AT/TCC 模式）或最终一致性方案（本地消息表 + 定时补偿）

**Q4: 你们项目的多数据源方案和 MyBatis-Plus 官方的 dynamic-datasource 有什么不同？**

- 官方方案更开箱即用，通过 `@DS` 注解无缝切换
- 自研方案通过 AOP 切面 + 自定义 `@DataSource` 注解，与公司框架 `cxsk-framework` 整合
- 自研方案的 `determineCurrentLookupKey()` 中每次调用后立即清空 ThreadLocal，强制默认走 master，避免遗漏注解时出问题

### 4. MyBatis + MyBatis-Plus

### 5. Kafka 消息队列

**项目用法：** 配置了 Kafka consumer 端，用于接收上游系统消息（指标数据变更通知、批次检查等）。

关键配置项：`bootstrap-servers`、`group-id`、`enable-auto-commit`、`max-poll-records`、`concurrency`、`ack-mode`

**Q1: Kafka 怎么保证消息不丢失？**

- 生产者：`acks=all`（等待所有副本同步确认）、`retries` 重试、`enable.idempotence=true` 幂等
- Broker：`min.insync.replicas >= 2`、`unclean.leader.election.enable=false`
- 消费者：手动提交 offset、先处理业务再提交 offset

**Q2: 消息重复消费怎么处理？**

- 消费端做幂等：数据库唯一键约束、Redis 记录消费状态、业务状态机防重
- 项目中的幂等思路：批次计算前先查是否已有同主体同期次的批次记录

**Q3: max-poll-records 和 concurrency 参数怎么调优？**

- `max-poll-records`：一次 poll 拉取的消息数，影响批处理吞吐量
- `concurrency`：并发消费者线程数，对应分区数
- 经验：并发数 ≤ 分区数，poll 记录数不宜过大（避免处理超时触发 rebalance）

**Q4: Kafka rebalance 的触发条件和影响？**

- 触发条件：消费者加入/退出组、超时未发送心跳(`session.timeout.ms`)、消费处理时间过长(`max.poll.interval.ms`)
- 影响：rebalance 期间消费者组暂停消费，可能导致消费延迟
- 优化：增大 `max.poll.interval.ms`、使用 cooperative 协议减少中断

### 6. MapStruct 对象转换

**Q1: MapStruct 和 BeanUtils.copyProperties 有什么区别？**

- MapStruct：**编译期**生成转换代码（纯 getter/setter 调用），性能接近手写，编译期暴露字段不匹配
- BeanUtils：**运行时**反射，性能差约 10-100 倍
- 项目定义多个 `@Mapper` 接口，Maven 编译时通过 `mapstruct-processor` 生成实现类

**Q2: MapStruct 如何处理字段映射和数据转换？**

- 字段名不一致：`@Mapping(source="xxx", target="yyy")`
- 类型转换：自动转换基本类型，复杂转换用 `expression` 或自定义方法
- 嵌套对象：用 `.` 链式访问（如 `source="a.b.name"`）

## 五、面试话术模板

### 项目介绍（1分钟版）

> 我最近做的是一个信贷CRM系统的风险画像模块，主要功能是为金融机构构建风险评估模型。用户可以在系统里自定义风险维度（比如信用风险、市场风险、操作风险等），每个维度绑定不同的记分卡规则（通用、事件、战略、集中度四种），配置指标后系统对主体进行自动打分，生成风险画像报告和看板。
>
> 技术上用的 Spring Cloud 微服务架构，数据库是 MySQL + PostgreSQL 双库，规则引擎用 LiteFlow 做打分流程编排（支持并行计算和动态热更新），消息队列用 Kafka，还有一个自研的基于 AOP 的多数据源动态切换方案。
>
> 我在里面主要负责模型配置管理（创建/保存/激活/复制）、记分卡基本管理、批次发布取消、仪表盘后端查询等功能的前后端开发。

### 难点亮点（任选一个深入讲）

> **最有挑战的是模型的逐步保存和发布机制。** 用户配置一个评估模型可能分多次完成（可能先配5个维度，下次再加2个），也可能一键完成。我设计了一个 operateType 参数控制草稿/正式两种模式——草稿不校验业务规则，正式提交时才校验维度权重、数量等硬约束。
>
> 核心方法是 `updateRiskDimInfo`，它要在一个事务里完成**删除-新增-更新**三步原子操作。特别是更新维度时不能简单 update，因为维度和指标是多对多关系，需要"先删旧的关联、再插新的关联"。
>
> 业务校验方面，我写了 `validateConfigBiz` 方法，校验维度不重复、单一风险维度必须有8个子维度、子维度权重和必须等于100等规则。
>
> 另外还有一个**模型复制**功能，复制涉及8张关联表的全量数据拷贝。这里的关键问题是如何在跨 Service 的操作中传递新旧 ID 映射。我设计了一个 `CopyModelContextHolder`（ThreadLocal），各 Service 的 copy 方法从 Holder 读取映射关系，复制完成后统一清理。
